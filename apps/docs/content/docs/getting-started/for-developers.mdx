# For developers

This is the orientation page for the engineer (or consultant) about to work
on the platform. It assumes you've read
[Platform overview](/docs/getting-started/platform-overview) and
[Key concepts](/docs/getting-started/concepts).

If you are the literal **successor to the previous IT Manager**, read
[Handover](/docs/handover) before you read anything else.

## Prerequisites

- **Bun 1.3.1** (exact version). Run `bun -v` to confirm. The repo uses Bun
  workspaces and the `catalog:` protocol — npm or pnpm will not work.
- **Node 22+** is installed by Bun automatically but make sure your IDE uses
  the right version.
- **Git** with access to the [biso-no/biso-sites](https://github.com/biso-no/biso-sites)
  repository.
- **An Appwrite project** to point at. You can either:
  - Use the shared dev project (ask for the keys), or
  - Spin up your own local Appwrite via Docker and seed it from
    `packages/api/appwrite.config.json`. See
    [Integrations / Appwrite](/docs/integrations/appwrite).
- **`.env.local` files** for each app. The required vars are documented at
  [Operations / Environment variables](/docs/operations/environment-variables).

## Quick start

```bash
git clone https://github.com/biso-no/biso-sites.git
cd biso-sites
bun install
bun run dev
```

`bun run dev` runs every app's dev server in parallel through Turborepo:

| App | URL |
|---|---|
| `web` | http://localhost:3000 |
| `admin` | http://localhost:3001 |
| `docs` | http://localhost:3002 |
| `api` | http://localhost:3003 |

To run only one app: `bun run dev --filter=admin`.

The full step-by-step is at [Developing / Local setup](/docs/developing/local-setup).

## The five things to internalise before your first PR

1. **All data access goes through `@repo/api`.** Never import `appwrite` or
   `node-appwrite` directly in app code. The `db` proxy in `@repo/api/server`
   JSON-clones results so they survive the RSC boundary — bypassing it is
   how you get "objects can't be passed to client component" errors.

2. **Default to Server Components.** Mark `"use client"` only when you need
   state, effects, or browser APIs. Server actions are the preferred mutation
   path.

3. **Roles are derived from Azure AD teams; never check Appwrite labels.**
   Use `getUserAuthContext()` in admin and `getLoggedInUser()` in web. See
   [Auth and roles](/docs/architecture/auth-and-roles).

4. **Every content list action filters by `campus_id` (and often
   `department_id`).** The canonical pattern is in
   `apps/admin/src/app/(portal)/_actions/pages.ts` — `applyScopeQueries()`.
   If you write a list endpoint that doesn't scope, you'll leak data across
   campuses.

5. **`next build` does not type-check.** Both Next.js apps set
   `typescript: { ignoreBuildErrors: true }` because of legacy generated
   types. Run `bun run check-types` before merging. The pre-commit hook
   catches lint with Biome/Ultracite but not types.

## Where the source of truth lives

| For… | Look at… |
|---|---|
| Database schema (tables, columns, indexes, permissions) | `packages/api/appwrite.config.json` (auto-generated by `appwrite pull`; don't hand-edit) |
| Row types & enums | `packages/api/types/appwrite.ts` (regenerate with `appwrite types -l ts ./types`) |
| Admin role / nav rules | `apps/admin/src/lib/roles.ts` |
| Public site middleware (anonymous sessions) | `apps/web/src/proxy.ts` |
| Sidebar items | `apps/admin/src/app/(portal)/sidebar.tsx` |
| Block registry | `packages/editor/src/blocks/registry.ts` |

When the docs and the code disagree, **the code is right**. Open a PR to
fix the docs.

## Commands you'll run constantly

```bash
bun run dev                       # everything
bun run dev --filter=admin        # one app
bun run check-types               # required before merging
bun run lint
bun x ultracite fix               # repo-wide format + autofix
bun run build                     # production build of every app
```
