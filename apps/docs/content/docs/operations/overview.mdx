# Operations overview

This section is the runbook for keeping BISO's platform alive in production.
If you've inherited this stack and you're trying to figure out what actually
needs to be running and where, start here.

## What's deployed

The platform is a Turborepo monorepo. In production there are **four Next.js
apps** plus a backend:

| App | Port (dev) | Purpose | Notes |
|-----|-----------|---------|-------|
| `apps/web` | 3000 | Public student-facing site (biso.no) | `output: "standalone"` |
| `apps/admin` | 3001 | Internal CMS for BISO staff | `output: "standalone"` |
| `apps/api` | 3003 | JWT REST service consumed by `web` | `output: "standalone"` |
| `apps/docs` | 3002 | Developer documentation (this site) | Static-deployable |

All three operational apps (`web`, `admin`, `api`) are built with
`output: "standalone"` so they ship as self-contained Node bundles suitable
for containerised hosting.

The fifth piece — and the one whose uptime matters most — is the
**Appwrite backend** at `appwrite.biso.no`. If Appwrite is down, every app is
down. See [/docs/integrations/appwrite](/docs/integrations/appwrite).

## Hosting

Production today runs on **Appwrite Sites** (self-hosted), which in turn
runs on a **Webdock** VM. Every Next.js app — `web`, `admin`, `api`,
`docs` — is a separate Appwrite Site on that instance. Deploys are
driven by a single GitHub Actions workflow that detects which apps
changed and uploads only those.

For the full deployment walkthrough see
[Deployment](/docs/operations/deployment). For ownership and billing
detail see [Handover / Domains and hosting](/docs/handover/domains-and-hosting).

## Build pipeline

```bash
bun run build                  # build everything
bun run build --filter=web     # build a single app
bun run check-types            # the only signal that catches type errors
```

Important: both Next.js apps set `typescript.ignoreBuildErrors: true` in
`next.config.ts`. **`next build` will succeed with broken types.** Always run
`bun run check-types` in CI before shipping.

App-specific scripts for Appwrite Sites builds live in the root
`package.json` (`build:web:appwrite`, `build:admin:appwrite`,
`build:api:appwrite`, `build:docs:appwrite`).

`apps/api` additionally has a `deploy:prep` script that flattens the
standalone output and copies it to the monorepo root — see
[deployment](/docs/operations/deployment).

## Mental model

The platform is best thought of as **three Next.js apps in front of one
Appwrite project**. If you can reason about Appwrite (collections,
permissions, sessions, functions) and you can keep three Node apps running
behind their respective domains, you can run BISO.

What the platform does *not* have:

- No external message queue. Background work runs either as Appwrite
  Functions or as cron-triggered Next.js routes.
- No separate database. Appwrite TablesDB is the entire data layer.
- No external auth provider. Appwrite is the identity provider, with Azure
  AD as an OAuth source for staff.
- No external file storage. Appwrite Storage holds uploaded files.
- No built-in scheduler. Cron is external (see
  [cron-and-scheduled-tasks](/docs/operations/cron-and-scheduled-tasks)).
- No first-party telemetry. Health endpoints exist; everything else is
  Appwrite logs + your hosting provider's logs.
