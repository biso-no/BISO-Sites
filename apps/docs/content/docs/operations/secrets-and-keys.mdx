# Secrets and keys

Every secret the platform uses, organised by integration, with a rotation
procedure for each one. If you suspect a leak, jump straight to
[Rotation procedures](#rotation-procedures).

## Storage

- **Production secrets** live in the hosting provider's secret manager, not
  in git. See [environment-variables](/docs/operations/environment-variables)
  for the per-app list.
- **Local dev** uses `apps/<app>/.env.local`, which is gitignored.
- **A sealed reference copy** of production values should exist in BISO's
  shared password manager so that the platform can be rebuilt from scratch.

## Naming conventions

Secret groups are prefixed by provider:

| Prefix | Provider |
|--------|----------|
| `APPWRITE_*` | Appwrite |
| `AZURE_*` | Azure AD / Microsoft Graph |
| `SHAREPOINT_*` | SharePoint (technically also Graph, kept separate by domain) |
| `VIPPS_*` | Vipps MobilePay |
| `STRIPE_*` | Stripe |
| `PINECONE_*` | Pinecone |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` | AI providers |
| `WC_*` | WooCommerce (legacy proxy) |
| `WEBDOCK_API_KEY` | Webdock hosting |
| `ENTUR_SYNC_SECRET` / `CRON_SECRET` | Internal bearer tokens for cron endpoints |

## Special cases

### Session cookies

`APPWRITE_SESSION_COOKIE` is the name of the cookie used to persist the
Appwrite session. `web` uses `a_session_biso`; `admin` uses
`a_session_biso_admin`. Changing the cookie name immediately invalidates
every existing session — it is effectively a global logout. Treat the
cookie names as semi-secret configuration and do not change them casually.

### `CRON_SECRET` and `ENTUR_SYNC_SECRET`

These are bearer tokens for the cron-only HTTP endpoints. They exist so
that the cron endpoints can be safely public-routed. If either leaks, an
attacker can repeatedly trigger the underlying job — at worst this clears
your own session reservations or burns Entur API quota.

## Rotation procedures

The general process for every external provider is:

1. Generate a new key in the provider's dashboard.
2. Update the value in the hosting provider's secret manager.
3. Redeploy each app that uses the key.
4. Confirm the new key works (test the affected feature).
5. Revoke the old key in the provider's dashboard.
6. Update the sealed reference in the password manager.

Per-integration specifics:

| Key | Provider | Rotate via | Affected apps | Reference |
|-----|----------|-----------|---------------|-----------|
| `APPWRITE_API_KEY` | Appwrite Console | Project → Integrations → API Keys | web, admin, api | [/docs/integrations/appwrite](/docs/integrations/appwrite) |
| `OPENAI_API_KEY` | OpenAI platform.openai.com → API keys | web, admin, api | [/docs/integrations/openai](/docs/integrations/openai) (if present) |
| `ANTHROPIC_API_KEY` | console.anthropic.com → Settings → API keys | admin | — |
| `AZURE_APP_ID` / cert | Azure portal → App registrations → Certificates & secrets | web, admin, api | [/docs/integrations/azure-ad](/docs/integrations/azure-ad) (if present) |
| `SHAREPOINT_CLIENT_SECRET` | Same Azure app as above (it's one app) | web, admin, api | [/docs/integrations/sharepoint](/docs/integrations/sharepoint) (if present) |
| `VIPPS_CLIENT_SECRET` / `VIPPS_SUBSCRIPTION_KEY` | Vipps Developer Portal | web, admin, api | [/docs/integrations/vipps](/docs/integrations/vipps) (if present) |
| `STRIPE_SECRET_KEY` | dashboard.stripe.com → Developers → API keys | web, admin, api | [/docs/integrations/stripe](/docs/integrations/stripe) (if present) |
| `STRIPE_WEBHOOK_SECRET` | dashboard.stripe.com → Webhooks → endpoint | web, api | — |
| `PINECONE_API_KEY` | app.pinecone.io → API Keys | web, admin, api | [/docs/integrations/pinecone](/docs/integrations/pinecone) (if present) |
| `WEBDOCK_API_KEY` | webdock.io → API | web (if it manages infra) | — |
| `CRON_SECRET` / `ENTUR_SYNC_SECRET` | Generate a fresh random string (`openssl rand -base64 32`) | web, api | [/docs/operations/cron-and-scheduled-tasks](/docs/operations/cron-and-scheduled-tasks) |

## If a key leaks

1. **Revoke first, ask questions later.** Always revoke the leaked key
   before investigating the leak.
2. Rotate using the procedure above.
3. Check the relevant provider's audit log for usage of the leaked key.
4. Open an incident — see
   [/docs/operations/incident-response](/docs/operations/incident-response).
5. Write a post-mortem.

## What never goes in git

- Any value listed in
  [environment-variables](/docs/operations/environment-variables) other
  than the `NEXT_PUBLIC_*` ones.
- `.env.local`, `.env.production`, or any `.env` file with real values.
- Screenshots that include URLs containing tokens.
- Logs that include request headers.
