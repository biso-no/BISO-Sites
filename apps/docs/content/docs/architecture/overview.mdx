# Architecture overview

The BISO Sites platform is a **Turborepo monorepo** with four Next.js apps,
nine shared packages, one Appwrite project, and a handful of external
services. This page gives you the system shape; subsequent pages drill in.

## Topology

```
                                        ┌─────────────────────┐
                                        │   Azure AD / M365   │
                                        │   security groups   │
                                        └──────────┬──────────┘
                                                   │ sync at login
                                                   ▼
   students/visitors ─────────► apps/web ──────► Appwrite ◄────── apps/admin ──── BISO staff
                                  │           (auth, DB,            │
                                  │            teams, storage,      │
                                  │            functions,           │
                                  │            messaging)           │
                                  │                                 │
                                  ▼                                 ▼
                              apps/api ◄──────────────────── apps/api
                              (JWT REST)                     (admin endpoints)
                                  │
                                  ├──► OpenAI       (expense OCR, translation)
                                  ├──► Anthropic    (admin assistant, page copilot, screening)
                                  ├──► Vipps/Stripe (payments)
                                  ├──► 24SevenOffice(membership, ledger)
                                  ├──► SharePoint   (documents)
                                  ├──► Pinecone     (resume embeddings)
                                  └──► Entur        (transit departures)
```

The **public site (`apps/web`)** is anonymous-friendly: a middleware wraps
every visitor in an Appwrite anonymous session before any request hits a
page. The **admin app (`apps/admin`)** is locked down to authenticated BISO
staff and gates every route by Azure-AD-derived role. The **`apps/api`**
service exists for two reasons:

1. To host CPU/IO-heavy work (PDF generation, OCR streaming, bulk imports)
   off the path of student page loads.
2. To expose stable, JWT-authenticated endpoints that mobile/external
   clients could in principle use.

The `docs` app is independent — it reads MDX from `apps/docs/content/` and
serves it with [Fumadocs](https://fumadocs.dev).

## The single Appwrite project

Everything data-related funnels through one Appwrite project:

- **Database** — One database (`app`) with ~60 tables. The schema is
  defined in `packages/api/appwrite.config.json` (auto-generated by
  `appwrite pull`) and **must** be modified via the Appwrite Console or CLI
  — never by hand-editing the JSON.
- **Auth** — Email/password, magic links, OAuth (Microsoft, Google,
  Facebook, Apple).
- **Teams** — Two uses:
  1. **Role derivation**: at every login, `syncM365Permissions()` mirrors
     the user's Azure AD security-group memberships into Appwrite teams
     (`SG-App-Campus-Oslo`, `SG-App-Dept-Career`, etc.). The admin app
     reads team memberships to compute roles. Appwrite user **labels** are
     read but no longer consulted for role checks.
  2. **Row-level ACLs**: `$permissions` on rows is granted to teams (e.g.
     "only members of `Career` can update this job's row").
- **Storage** — Buckets for page imagery, recruitment CV uploads, etc.
- **Functions** — Appwrite Functions for things that need direct
  service-key access (e.g. campus board members lookup).
- **Messaging** — Outbound email + push notifications.

Everything in app code goes through `@repo/api`. There is no direct import
of `appwrite` or `node-appwrite` allowed.

## How requests flow

### A student visits a page on `apps/web`

1. The visitor hits `https://biso.no/oslo/career` (for example).
2. `apps/web/src/proxy.ts` (Next middleware) checks for the
   `a_session_biso` cookie. If absent, it redirects to
   `/api/auth/anonymous?redirect=/oslo/career`, which calls
   `createAdminClient()` to mint an anonymous Appwrite session, sets the
   cookie, and redirects back.
3. The catch-all `(public)/[...slug]/page.tsx` calls `getPage(slug, locale)`
   in `@repo/api/page-builder`.
4. `getPage()` joins `pages` and `page_translations`, filters by status =
   published and visibility = public, deserialises the `puck_document`
   JSON column into a `PageDoc`, and returns it.
5. The page renders the `PageDoc` through `@repo/editor`'s render entry
   point. Each block component is a Server Component by default; data-
   bound blocks (eventList, jobList, …) call back into server actions to
   fetch their list.

### A staff member edits a page in `apps/admin`

1. They sign in at `/auth/login`. Sign-in goes through
   `account.createOAuth2Token` (Microsoft OAuth) and lands on
   `(auth)/auth/oauth/route.ts`, which awaits `syncM365Permissions()` before
   setting the cookie.
2. The `(portal)/layout.tsx` calls `getUserAuthContext()` and redirects to
   `/auth/login` if the call returns null.
3. They navigate to `/pages` (the listing) and then `/pages/[id]`. The
   `(editor)/pages/[id]/layout.tsx` enforces the same auth gate.
4. The page loads `getPageEditorById(id)`, hands the result to
   `<EditorShell>`, and the editor takes over (drag-drop, AI copilot,
   locale switcher, save button).
5. Saving calls `savePageDraft({ id, doc, locale, ctx })` (a server action
   in `_actions/pages.ts`). That action:
   - Calls `requireAuth()` / `getUserAuthContext()`.
   - Scopes the page row to the user's campus.
   - Upserts `pages` and the `page_translations` row's `draft_document`.
   - Calls `logAuditEvent()` and `revalidatePath()`.
6. Publishing copies `draft_document` → `puck_document` and flips
   `is_published`.

### A student buys a shop item

1. Anonymous user adds items to the cart (cart is server-stored via
   `cart_reservations`).
2. They go to `/shop/checkout` and submit the order form. The
   `checkoutWithCart()` server action validates stock, applies member
   discounts (verified against 24SevenOffice), creates an `orders` row,
   and calls `createVippsCheckoutSession()` from `@repo/payment/vipps`.
3. The user is redirected to Vipps, completes payment.
4. Vipps redirects them back to `/api/checkout/return?orderId=...`. That
   route verifies the session with Vipps, updates the order to `paid`, and
   posts the transaction to 24SevenOffice via
   `postShopTransaction()`.
5. The user lands on `/shop/order/{id}` to see the confirmation.

The legacy `/api/checkout/webhook` returns 410 Gone — newer flows use the
return URL pattern, not webhooks.

## Layered packages

```
   apps/web   apps/admin   apps/api   apps/docs
       │         │            │           │
       └────┬────┴──────┬─────┘           │
            │           │                 │
       @repo/api   @repo/editor   @repo/ui   @repo/i18n
            │           │            │           │
            │       @repo/ai   @repo/payment  @repo/connectors
            │           │            │           │
            └───── @repo/shared (utils, types) ──┘
                              │
                  @repo/typescript-config (tsconfig presets)
```

Apps depend on packages; packages can depend on each other but the
direction is mostly downward. The most-imported package is `@repo/api` —
treat it as the platform's standard library for data access.

## Where the code lives

| Concern | Path |
|---|---|
| Public site routes | `apps/web/src/app/{(public),(protected),(auth)}/` |
| Public site middleware (anonymous sessions) | `apps/web/src/proxy.ts` |
| Public site server actions | `apps/web/src/app/actions/`, `apps/web/src/lib/actions/` |
| Admin routes | `apps/admin/src/app/{(portal),(editor),(auth),(protected)}/` |
| Admin server actions | `apps/admin/src/app/(portal)/_actions/` |
| Admin role rules | `apps/admin/src/lib/roles.ts` |
| Admin sidebar config | `apps/admin/src/app/(portal)/sidebar.tsx` |
| Admin API route handlers | `apps/admin/src/app/api/` |
| Standalone REST service | `apps/api/src/app/api/` |
| Block editor | `packages/editor/src/` |
| Block registry | `packages/editor/src/blocks/registry.ts` |
| Appwrite wrapper | `packages/api/src/{server.ts,client.ts,page-builder.ts}` |
| DB schema (source of truth) | `packages/api/appwrite.config.json` |
| Generated row types | `packages/api/types/appwrite.ts` |
