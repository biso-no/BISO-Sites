# Packages

The `packages/` directory holds the library layer of the monorepo.
This page covers each package at the architecture level — what it
exists for, the key abstractions, and why it lives separately. For
full APIs and option references, follow the links to
`/docs/packages/*`.

The rough dependency direction is:

```
   apps/*  ──►  @repo/{api, editor, ui, ai, payment, connectors, i18n}
                          │
                          └────►  @repo/shared, @repo/typescript-config
```

Apps depend on packages; packages can depend on each other but the
direction is mostly downward. The two leaves (`shared` and
`typescript-config`) have no internal dependencies.

---

## `@repo/api`

**Purpose.** Single source of truth for backend access. Wraps the
Appwrite SDK (both `appwrite` for the browser and `node-appwrite` for
servers), exports generated row types, and provides higher-level
helpers for things like the draft/publish flow.

**Key abstractions.**

- `createSessionClient()` (server, user-scoped via the
  `a_session_biso` / `a_session_biso_admin` cookie).
- `createAdminClient()` (server, service-key).
- `createClient()` (browser).
- `@repo/api/page-builder` — `getPage()`, `getPageEditorById()`,
  `savePageDraft()`, `publishPage()`, `unpublishPage()`.
- Generated row types in `packages/api/types/appwrite.ts` (regenerate
  with `appwrite types -l ts ./types`).
- Re-exports `ID`, `Query`, `Permission`, `Role`, `OAuthProvider`,
  and the `Models` namespace.

**Why it exists separately.** Centralizing Appwrite access means we can
swap SDK versions, add telemetry, or enforce typed-row guarantees in
one place. App code that imports `appwrite` or `node-appwrite`
directly is a code-review red flag.

**Full reference:** [`/docs/packages/api`](/docs/packages/api)

## `@repo/editor`

**Purpose.** The in-house block editor. `apps/admin` uses its
`EditorShell` to edit pages; `apps/web` imports `./render` to render
the same `PageDoc` JSON read-only. Same package, two surfaces.

**Key abstractions.**

- `EditorShell` — the 4-pane editor (topbar, palette, canvas,
  inspector).
- `PageDoc` and `PageMeta` — the persisted page shape.
- Block registry (`BLOCK_LIBRARY`, `allBlocks()`, `getBlock(type)`)
  with ~37 registered block types.
- Zustand store with Immer middleware (`useEditorStore`).
- `./ai` — copilot system prompt + tool schemas
  (`pageEditorTools`, `PageEditorToolName`).

**Why it exists separately.** Page editing is non-trivial UI: drag and
drop, undo/redo, multi-locale state, AI copilot, draft vs published
documents. Pulling it out of `apps/admin` lets `apps/web` reuse the
render path without bringing along editor-only deps.

**Full reference:** [`/docs/packages/editor`](/docs/packages/editor)
and the architecture deep-dive at
[Editor architecture](/docs/architecture/editor-architecture).

## `@repo/ui`

**Purpose.** Shared React component library: buttons, dialogs, popovers,
inputs, the design tokens that go with them. Built on
[Radix UI](https://www.radix-ui.com) primitives and Tailwind CSS.

**Key abstractions.** A flat catalogue of components — `Button`,
`Dialog`, `DropdownMenu`, `Tooltip`, form controls, etc. Each is
imported by name; **no barrel files** that re-export everything (perf
and tree-shaking).

**Why it exists separately.** Both `web` and `admin` need consistent
buttons, dialogs, and forms. Without a shared package they would
drift — one app would adopt a new Radix release before the other and
either visual or accessibility bugs would creep in.

**Full reference:** [`/docs/packages/ui`](/docs/packages/ui)

## `@repo/ai`

**Purpose.** Vercel AI SDK configuration, provider clients, React
hooks, and tool schemas. Used by:

- The admin page editor's copilot.
- The admin-wide assistant.
- The expense OCR pipeline in `apps/api`.
- The translation endpoint at `/api/translate-page`.
- Recruitment screening flows.

**Key abstractions.** Provider setup (`anthropic`, `openai`), a
`useChat` wrapper hook, server-side helpers for streaming + tool
calls, and tool registries grouped by surface.

**Why it exists separately.** Keeps provider keys, models, and prompt
fragments in one place. Swapping `claude-opus-4-7` for `claude-opus-5`
should be a one-line change in this package, not a search-and-replace
across two apps.

**Full reference:** [`/docs/packages/ai`](/docs/packages/ai)

## `@repo/connectors`

**Purpose.** External integrations that need shared client code.
Currently:

- **Azure AD + Microsoft Graph** — security-group lookups, user
  hydration, mail.
- **24SevenOffice** — membership verification, ledger postings,
  invoice queries. Token refresh stored in the `24so_tokens`
  Appwrite table.
- **SharePoint** — document storage and lookups for the admin app.
- **WooCommerce** — merch product catalogue surfaced through
  `apps/api`.

**Key abstractions.** One client class per integration, each with its
own auth handshake and a thin retry/error policy. They expect their
credentials to come from environment variables.

**Why it exists separately.** Both `web` and `admin` (and sometimes
`api`) need at least one of these integrations. Putting them in a
package keeps token handling, retry logic, and types out of app code.

**Full reference:** [`/docs/packages/connectors`](/docs/packages/connectors)

## `@repo/payment`

**Purpose.** Payment providers: **Vipps MobilePay** (the primary,
Norwegian, mobile-first checkout) and **Stripe** (fallback /
international).

**Key abstractions.** A provider-agnostic `createCheckoutSession()` /
`verifyReturn()` API where possible. Vipps-specific helpers
(`createVippsCheckoutSession`, `verifyVippsReturn`) live alongside.

**Why it exists separately.** Payment integrations have unusual
testing requirements (sandbox creds, return-URL flows), and isolating
them makes it easier to reason about which code runs server-only
versus what could be exposed.

**Full reference:** [`/docs/packages/payment`](/docs/packages/payment)

---

## `@repo/i18n`

**Purpose.** [`next-intl`](https://next-intl.dev) v3 config plus the
message bundles for `no` and `en`. ~43 namespaces under
`packages/i18n/messages/{locale}/{namespace}.json`.

**Key abstractions.** A locale list, the default locale (`no`), the
`getRequestConfig` setup, and helpers for switching the user's locale
preference (stored in Appwrite account `prefs.locale`).

**Why it exists separately.** Both apps need the same locales and the
same UI strings; splitting the bundles would invite divergence.

This handles **UI-string** translation only. **Content** translation
(pages, events, jobs, etc.) is a different mechanism — see
[Translations](/docs/architecture/translations).

**Full reference:** [`/docs/packages/i18n`](/docs/packages/i18n)

---

## `@repo/shared`

**Purpose.** Cross-cutting utilities, shared types, and helpers that
don't belong to a specific provider integration. Recruitment helpers,
date/locale formatters, slug utilities, generic Zod schemas, the
`SocialPlatform` enum.

**Why it exists separately.** Without it, we'd duplicate a date
formatter and a slug helper in three places. Add to this package when
the code is useful in multiple apps but doesn't justify a top-level
package of its own.

**Full reference:** [`/docs/packages/shared`](/docs/packages/shared)

---

## `@repo/typescript-config`

**Purpose.** Shared `tsconfig` presets — one for Next.js apps, one for
React libraries, one for Node packages. Every workspace extends one of
these.

**Why it exists separately.** Compiler options drift fast. Pinning them
in a package means you change `target` or `moduleResolution` once and
the entire monorepo follows.

**Full reference:** [`/docs/packages/typescript-config`](/docs/packages/typescript-config)
