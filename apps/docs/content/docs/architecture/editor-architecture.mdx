# Editor architecture

`@repo/editor` is the in-house block editor that powers page editing
in `apps/admin` and page rendering in `apps/web`. It is the largest
single package in the monorepo and the most opinionated piece of
the platform. This page covers its shape in enough depth that you
could rewrite a block, add a new one, or wire the editor into a new
host app without getting lost.

If you're new: read [Editor architecture overview in the package
docs](/docs/packages/editor) first; this page assumes you know what a
"block" is.

## Why it exists

The admin used to edit pages with [Puck](https://puckeditor.com), an
open-source block editor. We replaced it for four reasons:

1. **Block type control.** Our block library has 30 types with strong
   typing and AI metadata. Defining them in our own registry is
   simpler than fitting Puck's API.
2. **AI integration.** The page copilot needs to know about block
   types, their props, and which fields are translatable. That's
   easier when the registry is ours.
3. **Draft / publish state.** Per-locale `draft_doc` and
   `published_doc` columns require coordinated save/publish actions
   that didn't map cleanly onto Puck's model.
4. **Multi-locale workflow.** Switching locales mid-edit, translating,
   and tracking `translation_status` is built in from the start.

The package and its API are entirely ours. The page model was
redesigned in 2026 (sections and columns instead of a flat block list,
a page header, themes); the old `draft_document` / `puck_document`
columns are unused and wait for removal.

## Package surface

`packages/editor/package.json#exports`:

```jsonc
{
  ".":         // Editor entry: EditorShell, registry helpers, store, types
  "./render":  // Read-only renderer used by apps/web
  "./blocks":  // Side-effecting block-registration imports
  "./theme/styles.css": // CSS variables
  "./ai":      // Copilot helpers (system prompt, tools)
  "./types":   // Full TypeScript schema
}
```

The split matters because `apps/web` should not pull in the editor UI
(dnd-kit, Zustand store, inspector code). It imports only `./render`
and `./blocks` — the latter for the side-effect of registering block
components on the renderer's registry.

### Root export

```ts
import {
```

### Tech stack

| Concern | Library |
|---|---|
| State | `zustand` + `immer` middleware |
| Drag and drop | `@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/modifiers` |
| Forms / schema | `zod` |
| AI | `@ai-sdk/react`, `ai` |
| CSS | Custom theme using CSS variables |

No CSS-in-JS, no styled-components, no Emotion. Theme tokens are CSS
variables defined in `./theme` and consumed via class names.

## The PageDoc shape

The persisted unit of work is a `PageDoc`:

```ts
interface PageDoc {
  version: 2;
  header?: PageHeader; // the page's only <h1>; absent on headerless pages
  sections: Section[]; // each: layout + 1 to 4 columns of blocks
  meta: PageMeta;
}

interface Section {
  id: string;
  anchor?: string;
  layout: SectionLayout; // columns, background, spacing, align, tablet, phone
  columns: Column[];
}

interface Column {
  id: string;
  blocks: Block[]; // discriminated union over 30 block types
}

interface PageMeta {
  title: string;
  slug: string;
  description?: string;
  department: string;
  status: "draft" | "published";
  // Colour theme: absent follows the department, null resets to BISO,
  // an object is { dark, accent } (checked for contrast on load).
  theme?: { dark: string; accent: string } | null;
}
```

`Block` is a discriminated union with `type` as the discriminator.
Each block carries its own props plus an `id` (and a hide-on-phone flag).
Layout is not a block: a section's `layout.columns` is one of `1`,
`1-1`, `2-1`, `1-2`, `1-1-1` or `1-1-1-1`, with a white, tinted, dark
or photo background. Column grids respond to the page's container
width (tablet up to 1023px, phone up to 639px), and a tablet section
either stays side by side or stacks, with an optional phone order.

`PageDoc` is serialized as JSON and stored in
`page_translations.draft_doc` or `.published_doc`. The same shape is
read back by `getPage()` for rendering. Documents from the old
flat-list editor are converted on load by `normalizePageDoc`, so both
shapes read cleanly. Rich text is sanitised on the server at save, in
the admin loader and at render, and in the editor preview.

## Block registry

Every block type is registered via `registerBlock()`. The registry
lives in `packages/editor/src/blocks/registry.ts` and is populated by
side-effect imports under `packages/editor/src/blocks/`. The palette's
groups and the AI's block list are both derived from it. The host app
imports `@repo/editor/blocks` once at module load and gets the whole
library registered.

A registry entry looks like this:

```ts
registerBlock({
  type: "callout",
  label: "Callout",
  description: "An info box with an icon",
  category: "Tell a story",
  group: "text", // palette group

  // For the AI copilot
  aiHint: "A highlighted info or warning box.",
  aiProps: ["title", "body"],

  // Default block when the user drops it onto the canvas
  empty: () => emptyBlock("callout"),

  // Three components:
  Render:       CalloutRender,    // What's drawn in the canvas + on the public site
  Inspector:    CalloutInspector, // Props editor in the right pane
  PaletteThumb: CalloutThumb,     // Thumbnail in the left palette
});
```

`aiProps` lists the prop keys the copilot may set with its tools. The
`group` (`text`, `media`, `structure`, `people`, `live`, `actions` or
`extras`) decides where the block appears in the palette. A guard test
fails any block that breaks the visual rules, and another keeps every
`blocks/*/index.tsx` out of `"use client"`.

### Adding a new block

1. Implement `Render`, `Inspector`, `PaletteThumb` under
   `packages/editor/src/blocks/<name>/`.
2. Add a Zod schema for its props.
3. Call `registerBlock({...})` in the block's `index.ts`.
4. Add the type to the `BlockType` union and block interface in
   `packages/editor/src/editor/types.ts`, and import it in
   `packages/editor/src/blocks/index.ts` so it loads when the host
   imports `@repo/editor/blocks`.

See [Adding an editor block](/docs/developing/adding-an-editor-block)
for the full steps.

## State: the Zustand+Immer store

`packages/editor/src/store.ts` holds everything the editor needs at
runtime.

```ts
interface EditorState {
  // Document
  doc: PageDoc;                   // header + sections + meta

  // Selection / UI
  selection: string | null;       // selected block id
  selectedSectionId: string | null;
  mode: "edit" | "preview";
  viewport: "desk" | "tab" | "mob";
  inspectorTab: "block" | "page" | "outline";
  themePreview: PageTheme | null; // transient drag preview, never saved
  hoveredId: string | null;
  copilotOpen: boolean;

  // Save lifecycle
  saving: boolean;

  // History
  past: PageDoc[];
  future: PageDoc[];

  // many more mutation methods (header, sections, meta), all written
  // with Immer drafts
  setMeta: (patch: Partial<PageMeta>) => void;
  insertBlock: (type: BlockType, target?: InsertTarget) => string;
  moveBlock: (blockId: string, target: InsertTarget) => void;
  moveBlockToNewSection: (blockId: string, sectionIndex: number) => void;
  insertSection: (columns?: SectionColumns, index?: number) => string;
  moveSection: (id: string, beforeSectionId?: string) => void;
  setSectionLayout: (id: string, patch: Partial<SectionLayout>) => void;
  setProp: (id: string, path: string, value: unknown) => void;
  setTheme: (theme: PageTheme | null) => void;
  removeBlock: (id: string) => void;
  duplicateBlock: (id: string) => void;
  select: (id: string | null) => void;
  // ...
}
```

Mutations use Immer drafts and go through `editor/operations.ts`. Every
mutation pushes the previous document onto `past`, so undo and redo
work across columns. A theme drag repaints the canvas through
`themePreview` and adds exactly one undo step when it ends.

`useEditorStore` exposes the store to React. Components subscribe
with selectors for fine-grained re-renders.

## `EditorShell` — the host contract

`EditorShell` is the React component the host (`apps/admin`) drops
into a route. It does not own the document on disk — the host does.
The shell calls back into the host for every persistence operation.

```ts
interface Props {
  initial: PageEditorState;       // metadata + all locale translations
}

// Provided through EditorCallbacksContext:
interface EditorCallbacks {
  activeLocale: EditorLocale;
  locales: EditorLocaleOption[];
  departments: EditorDepartment[];
  campuses: EditorCampus[];
  lockedMeta?: { campus?: boolean; department?: boolean; slug?: boolean };

  // Persistence callbacks
  savePage:     (doc: PageDoc, locale: EditorLocale) => Promise<StoredMeta | undefined>;
  uploadFile:   (fd: FormData) => Promise<{ fileId: string; url: string }>;
  onPublish?:   (locale: EditorLocale) => Promise<PublishOutcome | undefined>;
  onUnpublish?: (locale: EditorLocale) => Promise<void>;
  onLocaleChange:     (locale: EditorLocale) => void;
  onTranslateLocale?: (target: EditorLocale) => Promise<void>;
  translatingLocale?: EditorLocale | null;
  onExit?: () => void;
}
```

`lockedMeta` is how a host pins fields. Unit and project pages lock
slug and department, because both encode the page's binding to a
department and changing either would orphan it. `savePage` returns what
the server stored (`StoredMeta`: the slug it settled on, the department,
whether it dropped a stale theme), and `onPublish` returns a
`PublishOutcome` (`themeCopied`), so the editor follows the server.

This contract is intentional: the editor is host-agnostic. The host
decides what "save" means (the admin app upserts
`page_translations`), what "publish" means (copies
`draft_doc` → `published_doc`), and what "translate" means
(calls the `/api/translate-page` endpoint).

### The 4-pane layout

```
┌──────────────────────────────────────────────────────────┐
│  Topbar: title, slug, locale switcher, save state, publish│
├────────┬──────────────────────────────────────┬──────────┤
│        │                                      │          │
│ Palette│            Canvas (dnd-kit)          │ Inspector│
│ (left) │                                      │ (right)  │
│        │                                      │          │
└────────┴──────────────────────────────────────┴──────────┘
```

- **Topbar.** Document metadata, save indicator, publish/unpublish
  buttons, locale switcher (including "Translate this locale" for the
  AI pipeline). Publish and the language switch are disabled, with a
  reason, while the page's theme fails the contrast check.
- **Palette.** Block library in seven groups, with thumbnails, plus a
  layout picker for new sections. Drag from here onto the canvas, or
  add to a chosen column.
- **Canvas.** Renders the header, then the sections, each with its
  columns of blocks. `dnd-kit` drags sections, and blocks within and
  between columns or into a new section. Clicking a block or section
  selects it. The canvas wears the effective theme (page, else
  department, else BISO) as inline variables on `.pe-frame`.
- **Inspector.** Three tabs: "Block" (the block's `Inspector`, or the
  section's settings), "Page" (title, slug, description, department,
  Theme panel) and "Outline" (the section tree). Section settings cover
  columns, background, spacing, column alignment, tablet side-by-side
  or stacked, phone order, hide on phone and link name.

### Auto-save

`EditorShell` debounces calls to `savePage()` at **800 ms** after the
last change. The host's `savePage` writes to `draft_doc`. The
"Save" button in the topbar flushes immediately.

Saves are serialised, and Publish waits for a pending save. Leaving the
editor starts a save and prompts while one is pending, in flight, failed
or blocked. If the theme fails the contrast check, autosave pauses with
"Not saved: theme colours fail the contrast check". See
[Pages publish flow](/docs/architecture/pages-publish-flow#what-a-save-will-and-wont-do).

There is **no auto-publish**. Publishing always requires an explicit
button press because it's a state change with consequences (visibility
on `biso.no`, audit log entry, possibly notifications).

## The AI copilot

`@repo/editor/ai` exports the copilot's building blocks:

```ts
import {
  buildSystemPrompt,
  pageEditorTools,
  type PageEditorToolName,
} from "@repo/editor/ai";
```

- **`buildSystemPrompt({ doc, locale, ... })`** assembles the system
  prompt with the current document's block summary, the registered
  blocks' `aiHint`s and `aiProps`, and the active locale.
- **`pageEditorTools`** is the tool registry exposed to the model.
  It includes tools for inserting sections and blocks into columns,
  updating block props, moving and removing blocks, and setting or
  resetting the page theme within the contrast rules.
- **`PageEditorToolName`** is the union of tool names — useful for
  typed routing on the host's side.

When the copilot calls a tool, the host (admin) executes it against
the same Zustand store the user is editing. The user can see and undo
the result like any other change.

## Render path

`apps/web` imports from `@repo/editor/render` (`SectionView`,
`PageHeaderView`, `BlockView`, `normalizePageDoc`) and
`@repo/editor/blocks`. The shared pipeline is
`renderPublishedEditorPage` in `apps/web/src/lib/published-editor-page.tsx`.
The catch-all, unit pages and `/projects/<slug>` all go through it:

```tsx
import "@repo/editor/blocks"; // side-effect: registers block renderers

// In a Server Component:
const page = await getPage(slug, locale);
```

The page's header renders first, then each section through
`SectionView`, which lays out the columns and renders each block's
`Render` component. Server Components by default; only blocks that
*need* client interactivity opt in with a `"use client"` boundary.
Every link in a block goes through `safeHref`.

### Themes on the site

A page's effective theme (page, else department, else BISO) renders as
the first element of the page. The nav, page header, Dark and Photo
sections, forms band and footer take the theme's dark; buttons, links
and stat numbers take the accent or its derived on-white shade. Body
text on white stays navy under any theme, and a theme equal to BISO's
own colours applies no overrides. Because Next keeps the previous page
mounted in a hidden Activity, the style is a small client component
that switches its sheet off when hidden and on when shown.

The colour maths live in `packages/shared/utils/page-theme.ts`: WCAG
contrast, the two checks (dark at least 7:1 on white, accent at least
4.5:1 on dark), the nearest passing shade, and the derived tokens
(`--biso-deep-raised|sunken|edge|ink-muted`, `--biso-ink`). Colours
that fail never reach CSS, and save rejects a failing theme.

### Uploads

The editor's `uploadFile` posts to the admin's upload routes. Files up
to one Appwrite chunk (5 MiB) go in one request. Larger files to the
`media` bucket go in 5 MiB chunks with `?chunk=1`
(`apps/admin/src/lib/chunked-upload.ts`), because Appwrite Sites cannot
carry a bigger single request. The first chunk creates the file and
returns an HMAC token that binds the file, user, type, size and name;
later chunks must repeat matching terms, arrive in order, and come from
the admin's own origin. Every body is read under a byte cap, stale
partial uploads are swept, and every upload is audit-logged. Allowed
types and per-kind limits live in `apps/admin/src/lib/upload-buckets.ts`.
In the `media` bucket, images may be up to 10 MB, documents up to 25 MB
and video (mp4, mov, webm) up to 250 MB, which is also the bucket's own
limit. Only buckets written with the service key accept chunks, so the
`content` bucket keeps single requests (images and PDF up to 10 MB).

Importantly: `apps/web` does **not** pull in `EditorShell`, the
Zustand store, or `dnd-kit`. The export split keeps the bundle clean.
