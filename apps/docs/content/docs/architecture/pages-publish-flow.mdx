# Pages publish flow

This page is the canonical reference for how a page goes from "blank
slate in the editor" to "live on biso.no". It covers the data model,
the server actions in `@repo/api/page-builder`, the per-locale
independence of draft and publish state, and what the public site
actually reads.

If you're new, [Editor architecture](/docs/architecture/editor-architecture)
explains the editor that drives this flow.

## Two tables, four states

Pages are split across two Appwrite tables:

```
pages                              page_translations
─────                              ─────────────────
$id            (PK)                $id              (PK)
slug                               page_id          → pages.$id
status                             locale           "no" | "en"
visibility                         draft_doc        PageDoc v2 JSON
campus_id                          published_doc    PageDoc v2 JSON (published)
department_id                      is_published     boolean
translation_refs[]                 status           "draft" | "published"
...                                ...
```

A single page (`pages.$id`) typically has two `page_translations`
rows — one for `no`, one for `en`. Each translation row carries
**both** `draft_doc` and `published_doc` columns.

The four columns/flags together encode the lifecycle:

| State | `draft_doc` | `published_doc` | `is_published` |
|---|---|---|---|
| Brand new | empty `PageDoc` | empty | `false` |
| Editing | latest editor state | empty | `false` |
| First publish | (copied below) | published `PageDoc` | `true` |
| Editing a published page | new draft in progress | last-published `PageDoc` | `true` |
| Republish | (copied below) | new `PageDoc` | `true` |
| Unpublish | unchanged | unchanged | `false` |

The key idea: `draft_doc` is what the editor is writing to;
`published_doc` is what the public site reads. Publishing copies one
to the other.

## Why two documents

You might ask: "Why not just edit the published JSON in place?"
Because:

1. **Atomicity.** A multi-hour editing session shouldn't be
   half-visible on biso.no. The draft is invisible to the public
   until publish.
2. **Rollback.** When you unpublish, the last-published JSON stays in
   `published_doc` — you can re-publish the same revision without
   re-doing work.
3. **Per-locale independence.** Norwegian and English are separate
   rows. You can publish Norwegian today, keep editing English, and
   publish English next week.

## Column names

The two columns are `draft_doc` and `published_doc`. The redesigned
editor stores `PageDoc` **version 2** in them: an optional `header`,
then `sections`, each with one to four `columns` that hold the blocks,
plus `meta` (see
[Editor architecture](/docs/architecture/editor-architecture#the-pagedoc-shape)).
Documents saved by the old editor (a flat block list) still load,
because `normalizePageDoc` converts them on read.

The older `draft_document` and `puck_document` columns are still in the
table. Nothing reads or writes them. They wait for the cutover, after
which they can be removed. Do not use them.

## The server actions

All of these live in `@repo/api/page-builder`:

```ts
// Public site — render a published page by slug + locale
getPage(slug: string, locale: Locale): Promise<{ doc: PageDoc; ... } | null>

// Admin reads — page metadata only or by id
getPageById(id: string, locale: Locale): Promise<...>

// Admin editor — full state for the editor (metadata + every locale's
// draft and published documents)
getPageEditorById(id: string): Promise<PageEditorState>

// Editor save
savePageDraft({ id, doc, locale, ctx }): Promise<void>

// Publish one locale
publishPage({ id, locale }): Promise<void>

// Unpublish one locale
unpublishPage({ id, locale }): Promise<void>
```

### `getPage(slug, locale)` — the public read

The public catch-all `(public)/[...slug]/page.tsx` calls this. It:

1. Looks up the `pages` row by `slug`.
2. Filters by `status = "published"` and `visibility = "public"`.
3. Finds the matching `page_translations` row for the locale.
4. Returns `published_doc` deserialized into a `PageDoc`. A row
   marked published but with no `published_doc` is not served; the
   draft is never used as a fallback.

If any check fails, returns `null` → 404. **The public site never
reads `draft_doc`.**

### `getPageEditorById(id)` — the editor's load

The admin's editor route calls this. It returns the whole edit state:

```ts
type PageEditorState = {
  page: PagesRow;                            // metadata
  translations: Record<Locale, {
    draftDocument:     PageDoc | null;
    publishedDocument: PageDoc | null;
    isPublished: boolean;
    status: "draft" | "published";
  }>;
};
```

The editor hydrates `<EditorShell initial={...}>` from this.

### `savePageDraft({ id, doc, locale, ctx })`

Called by `EditorShell` via the `savePage` callback, debounced at
800 ms. The action:

1. Calls `requireAuth()` / `getUserAuthContext()`.
2. Checks `ctx.resolvedCampusIds` includes the page's `campus_id`.
3. Upserts the `pages` row (metadata changes).
4. Upserts the `page_translations` row for `(page_id, locale)`,
   writing `doc` to `draft_doc`.
5. Writes to `audit_logs`.
6. Refreshes the admin's `/pages` list.

It does **not** touch `published_doc`, `is_published`, the page's
`status` or the rows' read permissions: only `publishPage` and
`unpublishPage` change those, so a save that lands while a publish or
unpublish is on its way cannot undo it. A new page starts as a draft.
Saving a draft is invisible to the public site.

### `publishPage({ id, locale })`

What "publish" really does:

1. Auth + scope check.
2. Reads `draft_doc` from the matching
   `page_translations` row.
3. Writes that JSON to `published_doc`.
4. Sets `is_published = true`, `status = "published"`.
5. Updates the parent `pages.status` if needed.
6. If the page carries an explicit theme, copies it to the page's
   department row (see [Themes and the department](#themes-and-the-department)).
7. Audit log, then refreshes the website (see
   [Refreshing the public site](#refreshing-the-public-site)).

After this call, `getPage()` will return the freshly published
content on the next read.

### `unpublishPage({ id, locale })`

Flips `is_published = false` and `status = "draft"` on the
translation row. **Does not** clear `published_doc` — that means a
later re-publish without changes can just flip the flag back.

The parent `pages.status` may also be flipped to `draft` if no locale
is published.

## What a save will and won't do

Saving is built so that it can never undo a publish:

- Saves are serialised per page: the first one creates the page, later
  ones update it using the stored slug.
- A save never changes publish state. Only publish and unpublish do.
- **Publish** waits for a pending save. Leaving the editor starts a
  save and warns while one is pending, in flight, failed or blocked.
- A save is refused, with a plain sentence, if the page's theme fails
  the contrast check. While that is true autosave pauses and Publish is
  disabled.
- Two tabs on different languages cannot overwrite each other's text,
  and a stale tab cannot re-attach a theme that has moved to the
  department.
- A draft save on a page that is already published rewrites that page's
  live title and description (long-standing behaviour).

## Themes and the department

`PageMeta.theme` has three states: absent (follow the department),
`null` (reset to BISO) and an object `{ dark, accent }`. Publishing a
page with an explicit theme copies it to the `departments` row through
the admin client, after the publish permission check, with an audit
event, and removes it from the page's own documents. An absent theme
never touches the department, and a stored theme that fails the
contrast check never blocks the publish. Unpublishing a page does
**not** clear its department's theme.

## Refreshing the public site

Publish, unpublish, archive and the auto-translation refresh call
`notifyWebsite()` from `apps/admin/src/lib/web-revalidate.ts` with the
tag `pages`, plus `departments` when a publish just wrote a theme to the
department. That posts the cache tags to
`apps/web/src/app/api/revalidate/route.ts`, authenticated with
`CRON_SECRET` in the `x-cron-secret` header. The website then drops
the cached data for those tags, and the sitemap follows. The
call is best effort: it never throws and gives up after 3 seconds, so a
slow website cannot stall a publish. If `NEXT_PUBLIC_WEB_BASE_URL` or
`CRON_SECRET` is missing in the admin, it logs a warning and skips.

## Project and unit pages

Some slugs belong to the admin, not to the public catch-all:

- `units/<slug>`: a unit's own page, served by the unit route.
- `projects/<slug>`: a project page, served by `/projects/<slug>` when
  a published editor page exists at exactly that slug, and by the coded
  hub otherwise. The catch-all never serves anything under `projects/`.

A project is either a **hub** (Fadderullan, Karrieredagene,
Bergensbaneløpet: many campus units, the page has no department) or a
**national project** (Winter Games, bound to the national Wintergames
unit). Hub pages are created, saved, published, unpublished and
archived by global admins only, with the campus pinned to none.
National project pages are edited by the unit's board. The mapping
lives in `packages/shared/utils/project-units.ts` (`PROJECT_UNIT_SLUGS`,
`projectPageSlug`). Once a national project's page exists, the unit URL
redirects to `/projects/<slug>`.

A department member can edit, save and publish the page bound to their
own department even when their campus team doesn't match the page's
campus (`apps/admin/src/lib/page-access.ts`). This applies only when the
department name is unambiguous, and it doesn't widen any list or read
scope.

## Per-locale independence

Each call to `publishPage` and `unpublishPage` takes a `locale`.
There is no "publish all locales" primitive. That's deliberate:

- A common workflow is to publish Norwegian immediately and run
  AI translation for English, then human-review English before
  publishing it separately.
- Translation status is tracked per locale (see
  [Translations](/docs/architecture/translations)).
- A campus admin who only writes Norwegian shouldn't accidentally
  publish stale English.

If you ever build an "publish all" UI affordance, implement it as a
loop over locales — don't bypass `publishPage`.

## What the public site filters

The catch-all renders a page only when:

```ts
page.status === "published" &&
page.visibility === "public" &&
translation.is_published === true &&
translation.published_doc !== null
```

`visibility` lets us mark a page as `internal` or `member` (the
admin handbook describes these). Internal pages render only when the
viewer is signed in to admin; member pages render only for verified
members.

## Common pitfalls

- **Editing `published_doc` directly.** Don't. The editor only writes
  to `draft_doc`. If you patch `published_doc` from a server
  action, you bypass the publish lifecycle and the audit trail.
- **Bumping `status` without copying the doc.** If you flip
  `is_published = true` but didn't copy `draft_doc` into
  `published_doc`, the public site renders the *previous* publish.
  Always go through `publishPage()`.
- **Forgetting to refresh the website.** The public site uses Next's
  cache. A new code path that changes page state must call
  `notifyWebsite(["pages"])`, or visitors see the old
  page until the cache expires.
- **Cross-locale assumptions.** A page being "published" is not a
  single boolean — it's per locale. Code that says
  `page.isPublished` is a smell; the truth lives on
  `page_translations`.
