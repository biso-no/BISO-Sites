# Stripe

<Callout type="warn">
**Current status (handover snapshot): Stripe is not in production.**
BISO does not have a live Stripe account. The `@repo/payment/stripe`
module, the checkout-flow branch that picks Stripe, and the env vars
listed below are all scaffolded so the path can be turned on quickly
if international card payments become a priority — but nothing on
biso.no calls Stripe today. Vipps handles every order.

If you're picking up this codebase: do **not** spend time provisioning
a Stripe account unless leadership has decided to offer card payments.
And before enabling it, sanity-check the checkout UI, the return URL,
and the order status flow end-to-end in test mode — the scaffold has
not been exercised against a real account in a while.
</Callout>

## Why it's scaffolded

[Stripe](https://stripe.com) is in the codebase as the obvious "what if
we ever need international card payments" answer. We default to
[Vipps MobilePay](/docs/integrations/vipps-mobilepay) because effectively
all BISO shop buyers are Norwegian students, and Vipps is the dominant
local payment method. Stripe would only matter if BISO started selling
to non-Norwegian audiences at scale.

## What it is

The card-payment platform you've already heard of. We use Stripe Checkout
(the hosted checkout page) rather than building card-input UI ourselves —
that keeps PCI scope out of our infrastructure entirely.

## Why we use it

Two reasons:

1. **Fallback** for users who can't or won't pay with Vipps.
2. **International** purchases — students with non-Norwegian cards still go
   through Stripe fine, where Vipps may not support them.

## Cost shape

Per-transaction percentage + flat fee, standard Stripe pricing. Slightly
higher than Vipps per transaction; lower volume than Vipps. No fixed
monthly cost.

## Configuration

| Var | Purpose |
|---|---|
| `STRIPE_SECRET_KEY` | Server-side API key. Server-only. |
| `STRIPE_PUBLISHABLE_KEY` | Browser-safe key. Only used if we render a Stripe Element directly. |
| `STRIPE_WEBHOOK_SECRET` | Signing secret used to verify inbound webhooks. |

The publishable key is allowed in client bundles. The secret key must
never appear in a Client Component or in any code path that compiles for
the browser.

## Where it lives in the codebase

- `@repo/payment/stripe` — server helpers:
  - `createStripeCheckoutSession()` — start a hosted-checkout session and
    return the redirect URL.
  - `constructStripeWebhookEvent()` — signature-verify and parse an inbound
    webhook payload.

The shop in `apps/web` is the only consumer.

## Checkout flow

1. User picks "Pay with card" in the shop checkout.
2. Server calls `createStripeCheckoutSession()` with the cart contents and
   a success / cancel URL pair.
3. User is redirected to Stripe's hosted checkout.
4. After payment, Stripe redirects back to our success URL.
5. **Stripe sends a webhook** to our webhook endpoint with the
   `checkout.session.completed` event.
6. Our handler verifies the signature with `STRIPE_WEBHOOK_SECRET`, marks
   the order paid, and posts the transaction to
   [24SevenOffice](/docs/integrations/24sevenoffice).

Unlike Vipps, the source of truth for "is this order paid" is the
**webhook**, not the return URL. Stripe's pattern is webhook-driven and
their signature verification is reliable.

## Webhook signature verification

Every webhook handler must call `constructStripeWebhookEvent()` before
trusting the payload. The helper takes the raw request body, the
`Stripe-Signature` header, and `STRIPE_WEBHOOK_SECRET`, and returns a
typed event (or throws if the signature is invalid).

Never parse `request.body` and act on it without going through the helper.
The webhook URL is reachable from anywhere on the internet and unsigned
events should be rejected silently.

## Refunds

Refunds are issued from the **Stripe Dashboard**, not from the admin app.
Same reasoning as Vipps: refunds are accounting events. After issuing a
refund, reverse the corresponding journal entry in 24SO manually.

## Failure modes

- **`STRIPE_WEBHOOK_SECRET` is wrong or missing** — every webhook is
  rejected; orders never get marked paid. Users see a charged card and a
  pending order. This is the failure mode to test for after any deploy.
- **Stripe API down** — checkout-session creation fails; the Stripe button
  errors out. Users can still pay with Vipps.
- **Webhook endpoint unreachable** — Stripe retries with exponential
  backoff for up to several days. As long as you get the endpoint back
  online within that window, queued events will replay automatically.
- **Mismatched key environments** — test keys hitting live webhooks (or
  vice versa) fail signature verification.

## Rotation

**API key rotation:**

1. In the Stripe Dashboard, create a new secret key.
2. Update `STRIPE_SECRET_KEY` in the deploy environment.
3. Restart the web app.
4. Revoke the old key in the Dashboard.

**Webhook secret rotation:**

1. In the Stripe Dashboard, roll the webhook signing secret for the
   relevant endpoint. Stripe lets the old and new secrets both work for a
   limited overlap window — use it.
2. Update `STRIPE_WEBHOOK_SECRET`, restart.
3. Confirm in the Dashboard that recent events are being delivered
   successfully, then expire the old secret.

Don't rotate both at once. Roll one, verify the system is healthy, then
roll the other.

## Test mode

Stripe has its own test mode keyed by which API key you use — keys
prefixed `sk_test_…` and `pk_test_…` hit the test environment and you can
use Stripe's documented test card numbers (e.g. `4242 4242 4242 4242`).
No separate env-var toggle is needed; just use test keys for development.

## Swapping the vendor

Stripe is wrapped in `@repo/payment/stripe` with a similar shape to the
Vipps helpers. Replacing it with another card processor (Adyen, Braintree,
etc.) would be a few days of work plus webhook re-plumbing. We've kept the
checkout-session shape generic enough that a second provider can sit
alongside Vipps and Stripe without disturbing the order model.
