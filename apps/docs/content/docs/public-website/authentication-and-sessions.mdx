# Authentication and sessions

The public site treats everyone as a session holder — even visitors who have never logged in. This lets the data layer work the same way for guests and members, and means the cart, locale preference, and view history follow a single Appwrite account. Logging in promotes that anonymous account to a real one.

## Two states a visitor can be in

| State | Has session cookie? | Has a real email / verified name? | What they can do |
|-------|---------------------|-----------------------------------|------------------|
| **Anonymous** | Yes (minted automatically) | No | Browse, add to cart, register for events, buy from the shop. |
| **Authenticated** | Yes | Yes | Everything above, plus `/profile`, `/applications`, `/fs`. |

The classification is done by `getAuthStatus()`, which calls a session authenticated only when `hasEmail || (hasRealName && emailVerification)`. An anonymous session is *not* authenticated even though it has a cookie.

## Anonymous sessions

There is no middleware and no session is minted on page view: cookieless clients (crawlers, link unfurlers, uptime monitors) used to each trigger a fresh anonymous Appwrite account. An anonymous session is provisioned **lazily**, by `ensureAnonymousSession()` in `apps/web/src/lib/anon-session.ts`, only inside an action that must write rows owned by the visitor (the cart today). Locale and selected campus live in plain cookies and need no account at all.

### The session cookie

| Setting | Value |
|---------|-------|
| Cookie name | `a_session_biso_web` (override via `APPWRITE_SESSION_COOKIE`); never `a_session_biso`, which is Appwrite's own cookie name for the project |
| Domain (prod) | `.biso.no` — shared across `biso.no`, `admin.biso.no`, and any other subdomain. |
| SameSite | `lax` in local dev, `none` (with `Secure`) in prod, because the OAuth return is a cross-site navigation. |
| Lifetime | Long — Appwrite manages expiry. |

Because the cookie is on `.biso.no`, a user logged in on the admin site is also "logged in" on the public site (subject to roles). In dev, the apps run on different ports but share `localhost`.

## Logging in

The login page is `/auth/login`. It offers two ways in:

| Method | Who | Notes |
|--------|-----|-------|
| **Sign in with BI student account** | BI students | Appwrite's OIDC provider, configured against BI's Microsoft Entra tenant. The primary path: it signs in or creates the account **and** connects it to the student in one go. |
| **Login link** | Everyone else (alumni, partners, guests) | Emailed magic link, no OAuth needed. Refused for `@biso.no` staff addresses, which sign in at admin.biso.no. |

The Google, Facebook and Apple buttons were removed in October 2026 at the Branding Committee's request. Identities linked through them are not deleted, but there is no button for them any more.

### How the BI sign-in works

1. `signInWithBiStudent` (`apps/web/src/lib/server.ts`) asks Appwrite for an OAuth2 **token** for the `oidc` provider, with `/auth/oauth` as the success URL and `/auth/login?bi_login=failed` as the failure URL, then redirects the browser to BI's sign-in.
2. Appwrite exchanges the code with BI's tenant and calls the provider's **userinfo endpoint**, which is this project's own route: `apps/api` → `/api/auth/bi-userinfo`. Appwrite learns that endpoint from the provider's well-known URL, so that URL is also this project's: `apps/api` → `/api/auth/bi-oidc/openid-configuration`, which serves Microsoft's discovery document for BI's tenant (`BI_OIDC_WELL_KNOWN_URL`) with the userinfo endpoint swapped, and refuses a multi-tenant document. That route forwards Appwrite's bearer token to Microsoft's userinfo endpoint and returns the same claims with `email_verified: true` for any `@bi.no` address. Appwrite's generic OIDC adapter only trusts an email that carries that claim, and Microsoft never sends it; without the route, a student whose bi.no address already belonged to a BISO account could not sign in with BI at all. With it, Appwrite signs in the account that holds the BI identity, otherwise the account that holds the bi.no email (attaching the identity), otherwise creates one. No outside token can be injected: Appwrite fetches the token itself and Microsoft answers for the account it belongs to. Two conditions keep the domain check honest, though. The provider's authorize and token URLs in the Appwrite console must be BI's tenant-specific endpoints (`login.microsoftonline.com/<BI tenant id>/…`), never `/common` or `/organizations`: with a multi-tenant endpoint another tenant's admin could give a user a `mail` of `x@bi.no`, and Microsoft's userinfo `email` is that unverified `mail` attribute. And a browser that still holds an Appwrite session of its own (left by the retired link flow) makes Appwrite attach the identity to that account instead of any of the three cases above, which is why every BI sign-in button clears it first.
3. `/auth/oauth` turns the token into a session, then runs `syncBiStudentIdentityAfterSignIn`. Because the merge is by email and Appwrite's email/password sign-up is open, someone could register a student's bi.no address with a password ahead of time and wait for the student to sign in into "their" account; the sync detects a BI identity minutes old on an older account that has a password, ends every other session and replaces the password with a random one. (Turning email/password sign-up off in the Appwrite console removes the attack altogether; the web app only ever uses BI and login links.) The sync then reads the account's identities through the admin client, parses the `s<number>@bi.no` address into `user.student_id`, looks the student up in BI's directory for `bi_employee_id` (the Finago customer key) and stamps `bi_linked_at`. An account with no profile row yet is sent through onboarding (`/onboarding?linked=1` when the BI link landed); an account that has one lands where it was headed. A returning student whose profile already carries the student number and directory record skips the directory lookup and the write. A refused or failed link (for example the BI account is already linked to another BISO account) is shown as a toast via `?link_error=…` by `BiSignInNotice` in the root layout.

One consequence to know about: the profile row the sync creates is what the protected layout checks to decide whether onboarding is done, so a new student who abandons onboarding is not sent back to it.

### Mobile app

The BISO app signs in with the same OIDC provider, through Appwrite's mobile OAuth flow, so it ends up with an Appwrite session for the same account the web would use. The app cannot call the web's `/auth/oauth` route, so after sign-in it calls `POST /api/auth/bi-sync` on `apps/api` with its Appwrite JWT as a bearer token. The route runs the same `syncBiStudentIdentityAfterSignIn` from `@repo/shared/utils/bi-identity-sync`. When a pre-registered password account is locked out, the JWT's session is the one kept, but only if it is a BI sign-in: the route looks the session up with the admin client and requires its provider to be `oauth2` (the app's session made from the OAuth2 token) or `oidc`. A password (`email`) or login-link (`magic-url`) session, or one the lookup cannot find, gets no lockout at all, so whoever set the password cannot use this route to end the student's session and keep their own. It returns `{ success: true, studentId, hasEmployeeId, campusHint }`, or a `200` with `{ success: false, error }` for a domain outcome (`no_bi_identity`, `invalid_bi_email`, `directory_unavailable`, `already_linked`, `sync_failed`, `not_authenticated`). A missing or rejected JWT is a `401`.

`directory_unavailable` is a partial success: `student_id` is written and the account counts as linked, only the directory enrichment (`bi_employee_id`) is missing, and the membership join gate offers a retry. The lookup goes to BI's tenant, so `apps/api` needs `BI_AZURE_TENANT_ID`, `BI_AZURE_CLIENT_ID` and `BI_AZURE_CLIENT_SECRET` (see [Environment variables](/docs/operations/environment-variables)); without them every app sign-in ends in `directory_unavailable`.

### There is no account linking

Earlier versions let a student "link" their BI account to an account created with a private email, through a browser-side Appwrite session and an OAuth link. That is gone: the link helpers, `/api/auth/bi-link`, `/membership/link` and the onboarding link step were removed in October 2026. Wherever the site finds a signed-in account without a BI identity (the onboarding student step, the membership gate, the member portal), it offers **Sign in with BI** instead, which signs that account out and starts the BI sign-in (`switchToBiSignIn`). Membership follows the student number in Finago, so it is on the BI account automatically; orders and tickets stay on the old account, which still opens with a login link.

<Callout type="warn">
The Appwrite console's OIDC provider has no field for the userinfo endpoint; it only takes a **Well-known URL** and discovers the endpoints from it. Set that URL to `https://<api host>/api/auth/bi-oidc/openid-configuration`, with `BI_OIDC_WELL_KNOWN_URL` on the API app pointing at BI's tenant-specific Microsoft document. With Microsoft's own well-known URL configured instead, every student whose bi.no address already belongs to an account is refused with `general_bad_request`, and the login page asks them to use a login link and report it.
</Callout>

## Protected routes

The protected route group (`/profile`, `/applications`, `/fs/*`) is gated by `apps/web/src/app/(protected)/layout.tsx`. That layout calls `getLoggedInUser()` and, if no real account is present, triggers Next's `unauthorized()`. With `authInterrupts` enabled, this renders `apps/web/src/app/unauthorized.tsx` — a 401 page that prompts the visitor to log in and bounces them back afterwards.

## Where the user's identity is used

| Surface | What it does with the user |
|---------|----------------------------|
| Cart / checkout | Anonymous accounts can have a cart. The Appwrite user ID owns the cart reservations and order rows. |
| Event registration | Anonymous OK. Member pricing only applies if the account is verified and matches a Finago customer. |
| Job applications | Requires login. The applicant's user ID is stored on the `job_applications` row. |
| Locale preference | Persisted to `prefs.locale` on the Appwrite account, anonymous or not. |
| Membership check | The `/api/membership` endpoint matches the account email against Finago — only meaningful once authenticated. |

## Logout

Logging out clears the session cookie. The next page load triggers the middleware again, mints a fresh anonymous session, and continues. There is no in-between "logged out" state from the data layer's perspective.

## Server-side helpers

For developers, the relevant helpers live in `@repo/api/server`:

| Helper | Use |
|--------|-----|
| `createSessionClient()` | User-scoped Appwrite client. Reads the cookie. |
| `createAdminClient()` | Service-key client. Used by `/api/auth/anonymous` and other privileged routes. |
| `getLoggedInUser()` | Returns the current Appwrite `User` or throws. |
| `getAuthStatus()` | Returns `{ isAuthenticated, hasEmail, … }` for nuanced gates. |

Never instantiate the Appwrite SDK directly in app code — see the [`@repo/api` package docs](/docs/packages/api).
