Read this before you add a table or a column, write a query, or change who can read something. All of BISO's data lives in one Appwrite project. The schema is checked in as `packages/api/appwrite.config.json`, and the row types generated from it are in `packages/api/types/appwrite.ts`. The apps reach Appwrite only through `@repo/api` ([Code layout](/developers/change-it/code-layout#conventions-that-matter) has the clients).

## Databases, buckets and topics

`appwrite.config.json` defines two databases with 103 tables between them:

| Database id | Name | Tables |
|---|---|---|
| `app` | App | 101. Everything the apps use. Queries name it as the database id, for example `db.getRow<Users>("app", "user", user.$id)`. |
| `24so` | Finago | 2: `departments` and `auth_tokens`. The 24SevenOffice connector keeps its login token in `auth_tokens`. |

Both databases have a table called `departments`. The committed types have one `Departments` type, for the `app` table, and none for the `24so` one. See [Types](#types).

The same file also defines four storage buckets (`media`, `documents`, `expenses` and `resumes`), the `scheduled-dispatch` function, and 50 messaging topics for push notifications: one for each kind of notice (general, news, events, jobs and shop), each campus or all of BISO, and each language.

## Tables by area

These are the main tables in `app`.

| Area | Tables | Notes |
|---|---|---|
| People | `user`, `public_profiles`, `student_id`, `tour_progress` | `user` holds one profile row per Appwrite account, with the account's `$id` as its row id. It holds the campus, departments, student id, BI ids and language. |
| Campuses and units | `campus`, `campus_data`, `campus_metadata`, `departments`, `department_board`, `department_socials`, `partners`, `funding_programs` | Campus ids are fixed strings: Oslo `1`, Bergen `2`, Trondheim `3`, Stavanger `4`, National `5`. `departments` mirrors the 24SevenOffice chart of accounts, so `active` doesn't mean public. The website also filters with `isPublicUnit` from `@repo/shared/utils/unit-visibility`. |
| Content | `pages`, `page_translations`, `page_drafts`, `news`, `events`, `documents`, `document_versions`, `content_translations`, `announcements`, `form_submissions`, `notices`, `event_attendees`, `event_rsvps`, `event_segments`, `segment_members`, `large_event`, `large_event_item` | `pages` and `page_translations` hold the block editor's published pages, and `page_drafts` holds the drafts. `event_rsvps` holds students' answers to an event (`going`, `maybe` or `not_going`), one per student per event. It has no table-level permissions. The website and the api write each answer with the service key, and the row's only permission is read for the student who answered (`packages/shared/utils/event-rsvp.ts`). |
| Jobs and recruitment | `jobs`, `job_applications`, `job_application_answers`, `candidate_profiles`, `job_interviews`, `job_interview_participants`, `job_interview_scorecards`, `recruitment_booking_tokens` | Applicants' personal data. See [Permissions](#permissions). |

Orders also carry lock columns (`transition_lock`, `finago_posting_lock`, `membership_fulfilment_lock`, `refund_lock`). | Membership and member pass | `memberships`, `member_roster`, `membership_texts`, `member_pass_scanners`, `member_pass_scanner_links`, `member_pass_scans` | `memberships` is the plan catalogue. `member_roster` is a display-only copy, rebuilt every night from 24SevenOffice. 24SevenOffice, not Appwrite, decides who is a member. |
| Benefits | `campus_benefits`, `benefit_partners`, `benefit_codes`, `benefit_reveals`, `benefit_interactions` | Every benefit is one `campus_benefits` row, with a `section` of `member`, `career`, `social`, `safety` or `business`. |
| Expenses | `expense`, `expense_attachments`, `expense_approvals`, `expense_approval_issues`, `expense_cost_types`, `ledger_accounts` | |
| Notifications | `content_notifications`, `user_notifications` | `announcements` (under Content) holds manual and automatic pushes. `content_notifications` has one row per content item. `user_notifications` keeps each user's read and cleared state. |
| Operations | `audit_logs`, `approval_requests`, `m365_turnover_jobs`, `m365_remediation_snapshot`, `m365_team_sync`, `feature_flags`, `varsling_settings`, `app_versions`, `page_view_events` | `audit_logs` has no permissions at all, so only the service key can read it. `m365_team_sync` holds each staff user's saved team list, which the admin and the API check before they give a role ([Auth and roles](/developers/change-it/auth-and-roles#the-saved-team-list)). It has no permissions either. |

The BISO app uses some of them, such as `chats`, `chat_messages`, `typing_indicators`, `product_favorites` and `saved_jobs`. Search BISO-Flutter before you remove any table.

## Key relationships

- **Who owns a content row.** `news`, `events`, `jobs`, `pages`, `webshop_products`, `campus_benefits`, `announcements` and `documents` each have a `campus` and a `department` relationship column. Those are the owner. The tables also keep a plain `campus_id`, and `news`, `events`, `jobs` and `pages` a `department_id`, from before the relationships existed. The admin's access checks use the relationships, and fall back to the plain columns only when a caller asks for that (`apps/admin/src/lib/content-authorization.ts`). When you write a content row, set the relationships and the plain columns to the same ids, as `packages/api/page-builder.ts` does.
- **People.** A `user` row links to many `departments`, to a `campus`, and to one `student_id` row.
- **Translations.** `news`, `events` and `webshop_products` link to `content_translations` through `translation_refs`. `jobs` and `departments` use `translations`, and `campus_benefits` uses `contentTranslations`. A unique index allows one `content_translations` row per content type, content id and language. Pages use `page_translations` instead, with one row per page and language (also a unique index).
- **Page drafts.** A `page_translations` row holds only what's live: `published_doc`, the title and the description. Each translation's draft (the editor's JSON, title and description) is in `page_drafts`, in the row whose id is the translation row's id. A save writes the draft row and leaves the translation row as it is. `publishPage` in `packages/api/page-builder.ts` copies the draft onto the translation row, and refuses with `Nothing to publish for <locale>` rather than replace a live page with an empty document. The old draft columns on `page_translations`, `draft_doc`, `puck_document` and `draft_document`, are left from before: `migrate:page-drafts` moves what they hold into `page_drafts` and empties them ([Packages](/developers/reference/packages#maintenance-scripts)). Until it has run, the editor falls back to a translation's `draft_doc` when it has no draft row, and a published page's translation row can still hold an unpublished draft in `draft_doc`, readable like the rest of the row. Run it.
- **Recruitment.** A job has applications. Each application has a candidate profile, answers and interviews, and each interview has participants and scorecards.
- **Shop.** An order has order items, each pointing at a product and a variation, with answers to the product's custom fields. Refunds belong to an order and have refund lines, each pointing at an order item.

## Permissions

In Appwrite, each table has its own permissions and a row-security switch. A table-level permission covers every row in the table. A row's own permissions only count when row security is on. BISO uses four patterns.

### Content rows: visibility only

The admin sets a content row's read permission from its status:

- a published row gets `read("any")`, so anyone can read it;
- a draft, archived or unpublished row gets no read, so only the service key can read it.

Pages get theirs from `buildPageRowPermissions()` in `packages/api/page-builder.ts`, and news, products and documents from `buildContentRowPermissions()` in `apps/admin/src/lib/utils.ts`. Events and benefits have their own rules in `packages/shared/utils/content-read-permissions.ts`:

- an event is readable by everyone when it's published or cancelled (`eventReadPermissions`). Members-only events are no exception: the flag limits who can join, not who can see. Events copied from Tickster follow the same rule.
- a benefit is readable by everyone when it's published (`benefitReadPermissions`).

Translation rows in `content_translations` carry their own read, which follows their parent's type and status (`translationReadPermissions`):

| Parent | Translation readable by everyone when the parent is |
|---|---|
| Event | Published or cancelled |
| News, product or benefit | Published |
| Job | Published. Operations Unit and HR can always read it. |
| Department | Always |

So any code that publishes or unpublishes a parent must then call `restampTranslationReads()` from `apps/admin/src/lib/content-translation-reads.ts`. It rewrites the read entries of every translation of that item and keeps the rest.

This works only when row security is on and the table itself grants no read. A table-level `read("any")` lets anyone read every row, whatever the row's own permissions say. `pages`, `page_translations`, `events`, `campus_benefits` and `content_translations` have row security on and no table-level read, and `packages/api/appwrite-config-permissions.test.ts` fails if that changes. Some other content tables still grant read at table level: see [Known issues](#known-issues).

Pages still have a members-only variant, which gives read access to a `biso-members` team instead of everyone. That team isn't used, so ignore it. Apart from a few fixed grants, no team mirrored from a Microsoft group (`sg-app-*`) goes into a content row's permissions, so those permissions don't change when the groups do. The fixed grants are:

- read for Operations Unit and HR on job translations;
- update and delete for Operations Unit on events copied from Tickster, and on their translations;
- on `form_submissions`, read, update and delete for Operations Unit, plus read and update for the team chosen on the page's form block (`apps/web/src/app/api/form/submit/route.ts`).

For pages, the rule is: **only published pages are publicly readable.**

### Writing content: the admin decides

Staff don't write content rows with their own session. The admin checks the user's role and campus in code, then writes with the service key (`createAdminClient`). The content-permissions design calls the admin "the only authoring boundary". So the admin's own checks are what stop someone editing another campus's content. Keep them on every new action.

### Recruitment: Operations Unit and HR only

The seven recruitment tables (`job_applications`, `job_application_answers`, `candidate_profiles`, `job_interviews`, `job_interview_participants`, `job_interview_scorecards`, `recruitment_booking_tokens`) give only `create`, and only to the `sg-app-dept-operationsunit` and `sg-app-dept-hr` teams. Each row then gets read, update and delete for those two teams. `packages/api/appwrite-config-permissions.test.ts` fails if the schema file grants anything else.

### Operational tables: team grants

Some operational tables still give access to whole teams at table level. For example, `orders` is readable by Operations Unit and by the four `sg-app-dept-ledelsen*` teams. `feature_flags` gives write access to Operations Unit only. Other tables are service-only: `audit_logs` has no permissions at all, `benefit_codes` has no table-level permissions while the admin writes each code row with none (`apps/admin/src/app/(portal)/_actions/benefits.ts`), and `m365_team_sync` and `page_drafts` have none on the table or on their rows.

### What the schema tests enforce

`packages/api/appwrite-config.test.ts` and `appwrite-config-permissions.test.ts` read `appwrite.config.json` and fail when:

- a table or bucket grants `create("any")` or `create("users")`. The one allowed exception is `create("users")` on `user`, because the BISO app may still rely on it;
- a table grants access to a team called `admin`;
- a table or bucket grants anything to a team id that isn't on the test's list: `sg-app-campus-national`, `sg-app-dept-operationsunit`, `sg-app-dept-hr` and the four `sg-app-dept-ledelsen*` teams. The list must also hold no id that nothing grants to;
- `pages`, `page_translations`, `events`, `campus_benefits` or `content_translations` has row security off or a table-level read;
- `m365_team_sync` or `page_drafts` has row security off or any permission;
- the `resumes` or `expenses` bucket has no list of allowed file types, or allows files of 100 MB or more.

### Live permissions can drift from the file

Signing in to the admin can change permissions. When the Microsoft group sync creates the team for a new `SG-App-Dept-*` group, it gives that team update and delete rights on the matching `departments` rows. For the HR team, it adds `create` on the recruitment tables (`apps/admin/src/lib/m365-sync.ts`, `apps/admin/src/lib/team-provisioning.ts`). So the live project can differ from `appwrite.config.json`. Check the Appwrite console when the two must match.

Rows keep the permissions they were written with. When the rules above change, rows written before keep their old read until something writes them again. `reconcile:row-permissions` in `packages/shared` rewrites the read entries on existing rows of `pages`, `page_translations`, `campus_benefits`, `events` and `content_translations` to what the code writes now. [Packages](/developers/reference/packages#maintenance-scripts) has how to run it.

## Known issues

- **Some content tables still grant read to anyone at table level.** `appwrite.config.json` gives a table-level `read("any")` to `news`, `jobs`, `documents` and `document_versions`, which have row security on, and to `webshop_products`, which has row security off. A product's child tables, `product_variations` and `product_custom_fields`, grant the same read, also with row security off. While that grant stands, anyone can read every row in those tables through the API, drafts included, whatever the row's own permissions say. The translations follow their parent's status, so a draft's translated text stays hidden, but the parent row doesn't. All of these tables also grant `create` to some `sg-app-dept-*` teams. The repo doesn't record whether the live tables match the file. Check each table's permissions in the Appwrite console.
- **Don't apply the content-permission cutover.** `packages/api/scripts/cutover-content-permissions.ts` removes every table-level permission, `create` grants included, from ten content tables at once. It refuses any table whose live row security is off, and reports it as an error. In the schema file, `pages` and `page_translations` now have row security on, and `webshop_products` still doesn't. Don't apply it: that stays the owner's call, and it must never run together with `reconcile:row-permissions`. By default the script is a dry run: it lists what it would remove and changes nothing. It reads `apps/admin/.env.local`, so check which project that file names first.
- **Saving a draft changes a published page's address and owner at once.** `savePageDraft` in `packages/api/page-builder.ts` writes the slug, campus and department to the `pages` row on every save. On a published page, a change to any of them takes effect before anyone publishes.

## Types

`packages/api/types/appwrite.ts` holds a type for every table's row and every enum, except three tables added after the types were last generated: `event_rsvps`, `m365_team_sync` and `page_drafts`. Regenerate the types to add them. Until then the code declares its own row shapes: in `packages/shared/utils/event-rsvp.ts`, as `M365TeamSyncRow` in `apps/admin/src/lib/authorization.ts` and `apps/api/src/lib/admin-auth.ts`, and as `PageDraftRow` in `packages/api/page-builder.ts`. Use the types as the type parameter on every read:

```ts
import { createSessionClient } from "@repo/api/server";
import type { Pages } from "@repo/api/types/appwrite";

const { db } = await createSessionClient();
const page = await db.getRow<Pages>("app", "pages", pageId);
```

For writes to a table with relationship columns, use `createTypedRow` and `updateTypedRow` from `@repo/api/write`, with an input type from `packages/api/types/inputs.ts`. The generated types describe a relationship as the whole related row, which is wrong for input: on write, Appwrite takes the related row or just its id. `inputs.ts` is written by hand.

The `db` from every server client returns plain objects, so rows can be passed from a Server Component to a Client Component.

### Regenerate the types

```bash
cd packages/api
bun run types:generate
```

The script does three things:

1. It runs `appwrite types -l ts ./types`.
2. It renames the CLI's `appwrite.d.ts` to `appwrite.ts`.
3. It renames `24SevenOfficeAuthTokens` to `TwentyFourSevenOfficeAuthTokens`. The CLI names that type after the unused `app` table `24so_tokens` ("24 Seven Office Auth tokens"), and a TypeScript type name can't start with a digit. The `24so` table `auth_tokens` comes out as `AuthTokens` and isn't renamed.

The script also tries to rename a second `Departments` type, for the `24so` table, to `TwentyFourSevenOfficeDepartments`. Today's CLI output has no second `Departments`, so that step changes nothing.

Don't run the bare CLI command, even though the root `CLAUDE.md`, the app `CLAUDE.md` files and the comment at the top of `appwrite.ts` quote it. Without the renames, `24SevenOfficeAuthTokens` breaks `check-types`, and `appwrite.d.ts` is left behind.

It worked when `packages/api/types/appwrite.ts` has your change, no `appwrite.d.ts` is left in `packages/api/types`, and `bun run check-types` passes.

## Schema changes and what never to hand-edit

Never edit these by hand:

- `packages/api/types/appwrite.ts`: regenerate it.
- `apps/*/next-env.d.ts`: Next.js writes it.
- `apps/web/appwrite.json` and `apps/web/database.json`: old stubs. The real schema is in `packages/api`.

`appwrite.config.json` is also listed as "do not touch" in the root `CLAUDE.md`, because the Appwrite CLI writes it: the rule there is to change the schema in Appwrite and regenerate the file. In practice, schema changes have been made by editing it in a reviewed pull request, with the owner's approval. The owner then runs `appwrite push tables` from `packages/api`, runs `bun run types:generate`, and commits the new types.

<Callout type="warn">
`appwrite push` from `packages/api` changes the production project, because that is the project the file names. Push only with the owner's approval. If the CLI offers to recreate or delete an existing column, stop: recreating a column wipes it on every row. Make that change by hand in the console instead.
</Callout>
