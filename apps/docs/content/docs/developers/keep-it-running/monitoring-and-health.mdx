Use this page to find out whether the platform is healthy, and where to look when it isn't. Sentry is the first place to look: it collects errors, slow requests, scheduled-job check-ins and uptime checks for the four apps and the three functions, and emails the owner when something breaks. Better Stack still checks that the site can be reached. The health endpoints, the logs in the Appwrite console and the admin's operations page are the fallback when Sentry itself has nothing. Some things still alert nobody, so read [What isn't monitored](#what-isnt-monitored) before you trust a quiet inbox.

## Sentry

### The projects

There is one project per deploy unit, so an issue's id shows where it came from.

| Project | What it shows |
|---|---|
| `biso-web` | The website: server errors and traces, browser errors and page loads, problem reports, and recordings from visitors who agreed. |
| `biso-admin` | The admin: the same as the website, plus the test error from the operations page. |
| `biso-api` | The api: server errors and traces, the Appwrite call timings, payment, order and expense counts, and the AI calls it makes. |
| `biso-docs` | These docs: errors and page loads for staff and developers, and the docs assistant's AI calls. |
| `biso-functions` | The three Appwrite functions: errors, and the cron monitors for the scheduled jobs. |

The older `appwrite` and `react-native` projects are empty leftovers. Ignore them.

### What is sent

- **Errors.** Every unhandled error in the apps' server code and in the browser, and the errors the three functions report themselves. Each has a readable stack trace (source maps are uploaded when the app is built) and the release it came from. A release is named `biso-<app>@<first 12 characters of the commit>`.
- **Request traces.** One trace for each server request. Server traces are kept in full on every app. Browser page loads are kept for 25% of visits on the website and docs and for every visit on the admin. A trace shows where a slow request spent its time, including each call to Appwrite.
- **Server logs.** Only the `warn` and `error` lines the apps write, such as `[request-error]` and `[appwrite] slow request`. Lines at other levels stay in the Appwrite console.
- **Business counts.** These exact names, each a count or a single value with a short list of labels (`provider`, `kind`, `app`, `client`, `outcome`) and nothing else:

  | Name | What it counts |
  |---|---|
  | `payment.completed` | A payment that went through |
  | `payment.failed` | A payment that didn't. Its `outcome` is `failed` or `cancelled`. Only `failed` raises an alert. |
  | `orders.stuck` | A value, not a count: how many orders are stuck as pending |
  | `push.sent` and `push.failed` | Pushes Appwrite accepted, and pushes it refused |
  | `expense.submitted` and `expense.booking_failed` | Reimbursements sent in, and bookings in 24SevenOffice that failed |
  | `appwrite.slow_request` and `appwrite.timeout` | Appwrite calls that took 2 seconds or more, and calls cut off after 8 seconds |

- **AI calls.** Each call to a model sends a span with the feature (for example `api.receipt-extract`), the model, the token counts and, on failure, the type of error. Never the prompt, the answer, a file or a tool's input.
- **Cron monitors.** The functions report each run as a check-in. See [Scheduled jobs](#scheduled-jobs-and-uptime) below.
- **Uptime checks.** Sentry calls the health endpoints every 5 minutes.
- **Recordings.** Only for visitors on the website and the admin who said yes in the bar at the foot of the page. A visitor who says no, or never answers, is never recorded. Everything in a recording is masked: text and inputs show as `***`, and images, media and links that can carry personal data are blocked. Recordings are deleted after 90 days.
- **Problem reports.** A visitor can press **Rapporter et problem** (Report a problem) in the website's footer, or the same option in the admin, and write what went wrong. The text goes to Sentry linked to the error and recording, if there are any. It never takes the visitor's name or email.

With no DSN set, a Site sends nothing and the consent bar, the privacy settings link and the problem report link are hidden. See [Secrets and environment](/developers/keep-it-running/secrets-and-environment#sentry).

### What is never sent

Sentry is a third party, and BISO's students trust it with nothing personal. The apps remove these before anything leaves the server or the browser, in `packages/observability/src/scrub.ts`:

- **People.** No names, no email addresses, no IP addresses. A signed-in user is known only by their Appwrite user id.
- **Cookies, headers and bodies.** No cookies, no request or response headers, no request bodies, and no database query values.
- **Query strings.** `?` and what follows it is cut from every address. A parameter like `secret=…` or `userId=…` inside free text is replaced with `[redacted]`.
- **Numbers that identify someone.** Norwegian bank account numbers, national ID numbers (fødselsnummer), IBANs and email addresses are replaced with `[redacted]` wherever they appear in an event, log line or span.
- **Links that work as keys.** The part after `/fs/approve/`, `/recruitment/book/`, `/scan/` and `/shop/order/` is replaced, because whoever holds one of those links needs no sign-in.
- **Variables.** No variable values in stack frames, and no source code around a frame.
- **AI content.** No prompts, answers or tool inputs.
- **Recordings.** None without a yes. Pages that show personal data, such as the recruitment booking page and the admin's scanner, are never recorded even after a yes.

Two settings in the Sentry account back this up with a second layer: "Prevent storing of IP addresses" and extra scrubbing rules for the same patterns. If you add something new to an event, a log line or a metric, check it against this list first. The same rules protect the functions: their reporter is a copy of the scrubber, and a test keeps the two in step.

### Scheduled jobs and uptime

- **Cron monitors** are in the `biso-functions` project. scheduled-dispatch checks in on each run (`scheduled-dispatch`, every 5 minutes), and so does each job it calls: `dispatch-<target>`, such as `dispatch-content-notifier` and `dispatch-orders-reconcile`. A `dispatch-<target>` monitor appears the first time that target runs in production. member-roster-sync checks in once a night (`member-roster-sync`). A run that fails or doesn't check in turns its monitor red.
- A failed target also reports an error event tagged `target`, which doesn't alert anyone by itself. The monitor is what alerts, so a single failed run doesn't raise two alerts.
- **Uptime checks** call `https://biso.no/api/health`, `https://admin.biso.no/api/health`, `https://api.biso.no/api/health` and `https://api.biso.no/api/health/ready`, which tells you that Appwrite answers. A check that fails twice in a row turns red. The last one costs one Appwrite request each time. Add `https://docs.biso.no/api/health` when docs is live.

[Scheduled jobs](/developers/keep-it-running/scheduled-jobs#how-sentry-watches-them) explains how the functions report.

### The alerts

Alerts go by email to the owner, and only for the `production` environment. Add Sentry's Microsoft Teams integration in the Sentry account if you want them in Teams.

| Alert | Fires when |
|---|---|
| A site is down or a scheduled job failed | An uptime check or a cron monitor fails, or a new error appears in the web, admin, api or functions project |
| A fixed error came back | An issue you marked resolved happens again in any app |
| Someone reported a problem | A new report arrives from the website or the admin. It's immediate. |
| Payments, stuck orders and error spikes | 3 or more failed payments in 15 minutes, any stuck order for a whole hour, or an error spike (over 50 errors in 10 minutes on the website or the api, over 30 on the admin) |
| High-priority issues | Sentry's built-in rule for each project |

Most alerts send at most one email every 30 minutes, and the metric alert one an hour.

### The dashboard

**BISO platform health** is a Sentry dashboard of errors per project, new issues, web vitals, the slowest server routes, Appwrite calls and timeouts, payments, pushes, expense bookings, AI calls by feature and problem reports. Its definition is in `scripts/sentry/platform-health-dashboard.json`, and the repo is the source of truth. To create it or put it back after someone edits it in Sentry:

```bash
SENTRY_DASHBOARD_TOKEN=<personal token> bun scripts/sentry/apply-dashboard.ts
```

The token is a personal auth token with the `org:write` scope. `scripts/sentry/README.md` has the details, and `bun test scripts/sentry` checks the definition.

### Send a test error

A global admin can check the link from the admin to Sentry. Open **Innstillinger** (Settings), then **Driftshelse** (Operations health). The Sentry row shows whether `NEXT_PUBLIC_SENTRY_DSN` is set. Press **Send testfeil til Sentry** (Send test error to Sentry). The page shows an event id, and the error appears in `biso-admin` within a minute. If it says Sentry is not configured, the admin was built without a DSN.

### Cost and limits

BISO's plan has a monthly limit on errors, spans, recordings and logs, and no pay-as-you-go. Over the limit, Sentry drops data and never bills. In Sentry, open **Stats** to see the usage. If a limit is near, lower a rate in `packages/observability/src/options.ts`, where `SAMPLE_RATES` sets the trace and recording shares for each app.

## Better Stack

Better Stack (free plan) checks that the site can be reached and sends an alert when it can't. It isn't set up in the repo, and Sentry's uptime checks now watch the same addresses. Better Stack stays until the owner trusts Sentry's checks. Which addresses it checks, how often, and who gets the alerts are all set in the Better Stack account:

<Private name="better-stack-account" label="Better Stack" />

When you take over, open the account and check two things:

- **It checks every live app.** Each of these should have a check. Add any that's missing:
  - `https://biso.no/api/health`
  - `https://admin.biso.no/api/health`
  - `https://api.biso.no/api/health`
  - `https://docs.biso.no/api/health`, once docs is live
- **The alerts reach you.** Add yourself, and remove anyone who no longer works on the platform.

Every check costs something. A check on `/api/health` costs one Site execution. A check on `/api/health/ready` also costs an Appwrite request. Keep a few minutes between checks.

## Umami

Umami is BISO's visitor analytics. It's self-hosted, it isn't in the repo, and the repo doesn't say where it runs. Who owns it is listed under <Private name="account-owners" label="Account owners" />.

- The website and the admin each load Umami's script with a fixed website id (`apps/web/src/app/layout.tsx`, `apps/admin/src/app/_components/analytics-script.tsx`). The script loads after the page, so an Umami outage doesn't stop either site from working.
- The admin's **Analyse** (Analytics) page reads Umami's API with `UMAMI_API_URL`, `UMAMI_USERNAME` and `UMAMI_PASSWORD`. If those are missing, or Umami doesn't answer, the page shows empty numbers and the admin logs `[Umami] GET … failed` or `[Umami] GET … threw`.
- The website's own page-view endpoint, `/api/analytics/page-view`, is switched off. It always answers `204`.

Umami counts visitors. It sends no alerts, so don't count on it to notice an outage.

## Health endpoints

| Endpoint | On | What it checks | Answers |
|---|---|---|---|
| `GET /api/health` | web, admin, api, docs | Nothing. It only shows that the app is running. | `200` with `{"status":"ok",…}` |
| `GET /api/health/ready` | web, admin, api | That the app's `APPWRITE_API_KEY` can list one Appwrite user within 3 seconds | `200` with `{"status":"ready","latencyMs":…}`, or `503` with `{"status":"error",…}` |
| `GET /api/health/teams` | admin | That the Appwrite teams the admin needs exist | `200`, or `503` with a list of the missing teams. Needs a signed-in global admin. Anyone else gets `401` or `403`. |

[Deploying](/developers/keep-it-running/deploying#health-endpoints) has the commands to call them.

Read the answers with care:

- **`/api/health` can answer `200` while the site is broken.** When Appwrite fails, most of the website's data reads log the error and return an empty list. Pages still load, with empty sections (`apps/web/src/app/actions/events.ts`). If pages look empty, check `/api/health/ready`.
- **`/api/health/teams` can't be used by a monitor.** Its code says it's meant for one, but a monitor can't sign in as a global admin. Open it in a browser where you're signed in to the admin.
- **`/api/health/teams` lists `biso-members` as required.** That team isn't used. Ignore it if it's reported missing.

## The admin's operations page

Global admins can open **Innstillinger** (Settings), then **Driftshelse** (Operations health), at `/settings/operations`. It shows three things:

- For Appwrite, Microsoft 365, SharePoint, Vipps, the scheduler secrets and Umami, whether their variables are set on the admin's Site. It only checks that a value exists. It doesn't try the value.
- The same team check as `/api/health/teams`.
- The Sentry row and the button that sends a test error. See [Send a test error](#send-a-test-error).

Three parts of it mislead:

- **Vipps** is checked through the `VIPPS_*` variables on the admin. The real credentials are in the `payment_settings` table, and payments run on the api, so Vipps can show as missing while payments work.
- **The scheduler secrets** entry wants `ENTUR_SYNC_SECRET` and `TICKSTER_SYNC_SECRET` as well as `CRON_SECRET`. Leave those two unset, as [Secrets and environment](/developers/keep-it-running/secrets-and-environment#scheduled-jobs) says.
- **The runbook links** point at old docs pages that no longer exist. The runbooks are now [When things break](/developers/keep-it-running/when-things-break).

## Logs

The apps write their logs to standard output. Sentry gets a scrubbed copy of the `warn` and `error` lines (see [What is sent](#what-is-sent)), but the full logs, at every level and unscrubbed, are only in the Appwrite console.

### Sites

Open the Appwrite console (<Private name="appwrite-console-url" label="Appwrite console" />), then BISO's production project, then **Sites**, then the Site. Its logs are there, and each deployment has its own build log.

### Functions

Open **Functions**, then the function, then **Executions**, then a run. The output is split across the **Logs** and **Errors** tabs. Keep logging switched on in each function's settings, as the functions' READMEs say, or the runs keep no output.

Appwrite deletes execution logs after 14 days unless its server is set otherwise (`_APP_MAINTENANCE_RETENTION_EXECUTION` in Appwrite's server settings). The production value isn't recorded. Copy what you need from an incident before it's gone.

[Scheduled jobs](/developers/keep-it-running/scheduled-jobs#check-that-its-working) explains scheduled-dispatch's log lines.

### What to search for

| Line | Written by | What it means |
|---|---|---|
| `[request-error]` | web, admin, api, docs | A request failed with an error nothing caught. The JSON that follows names the app, the method, the path without its query string, and the error with its stack. Cookies, keys, `Authorization` and client IP headers are replaced with `[redacted]`, and the referer loses its query string. The same error also goes to Sentry, with IP addresses and queries removed. |
| `[appwrite] slow request` | Server code using `@repo/api` | One Appwrite call took 2 seconds or more (`APPWRITE_SLOW_REQUEST_MS`). |
| `[appwrite] request timed out` | Server code using `@repo/api` | One Appwrite call was cut off after 8 seconds (`APPWRITE_REQUEST_TIMEOUT_MS`). The caller gets a `504` error of type `appwrite_timeout`. Many of these at once usually mean Appwrite itself is struggling. |
| `[web] …` or `[admin] …` when the Site starts | web, admin | A start-up check failed. The line names the variable that's wrong. |
| `[admin] Falling back to production Appwrite defaults for unset env: …` | admin | An Appwrite setting is unset. See [Secrets and environment](/developers/keep-it-running/secrets-and-environment#unset-appwrite-settings-mean-production). |
| `Error fetching events:` and similar | web | A data read failed and the page showed an empty list instead |
| `M365 Sync Failed:` | admin | Copying someone's Microsoft groups to their Appwrite teams failed when they signed in. They're signed in, with the teams they had before. |
| `Failed to send announcement push:` | admin, content-notifier | Appwrite refused a push. See [Push notifications aren't sent](/developers/keep-it-running/when-things-break#push-notifications-arent-sent). |
| `AI screening failed for application …` | web, api | Screening a job application failed. See [AI features fail](/developers/keep-it-running/when-things-break#ai-features-fail). |
| `[payment/credentials] vipps row not found in DB — falling back to env` | api | There's no `payment_settings` row for Vipps, so the api uses the `VIPPS_*` variables. The same line exists for Stripe. |

When the Appwrite console itself won't load, its logs won't either. Read Appwrite's own logs on the server, as in [Appwrite is down](/developers/keep-it-running/when-things-break#appwrite-is-down).

## What isn't monitored

Sentry and Better Stack cover errors, scheduled jobs, the functions and whether the sites can be reached. Nothing tells anyone about these:

- **Appwrite failing behind a running app.** `/api/health` answers `200` while the pages are empty, as described above. Sentry's `appwrite.timeout` count and the `api.biso.no/api/health/ready` check catch a bad key or a dead Appwrite, but not every empty page.
- **Payments stuck as pending.** The `orders.stuck` alert fires when an order stays stuck for an hour. Order reconciliation retries them on its own, and nobody is told about a payment that never reached BISO at all.
- **The server.** The repo has nothing that watches disk space, memory or CPU, and whether Webdock sends alerts isn't recorded. Sentry has no agent for it.
- **Appwrite's own internals.** Sentry doesn't watch the self-hosted Appwrite server.
- **The nightly backup.** Nobody checks that it ran. See [Backups and recovery](/developers/keep-it-running/backups-and-recovery).
- **Expiry dates.** Nothing tracks when certificates and secrets run out. The [Yearly calendar](/developers/keep-it-running/yearly-calendar) lists the ones that are known.
- **A Site built without its DSN.** It sends nothing, and no alert says so. After each deploy, check the [after-deploy list](/developers/keep-it-running/deploying#sentry-after-a-deploy).

A quiet inbox is only good news if Sentry is switched on for every Site. Once a week, open the **BISO platform health** dashboard and the **Crons** page in Sentry, and look at the latest scheduled-dispatch execution (it should end with `"failed":0`).
