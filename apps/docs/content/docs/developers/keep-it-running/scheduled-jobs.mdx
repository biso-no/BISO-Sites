This page lists everything that runs without someone pressing a button, and every webhook. Use it when something that should happen on its own didn't: an announcement wasn't sent, an order stayed pending, a push never went out. Three Appwrite functions do all the scheduling. A fourth, search-sync, runs on row changes and by hand, and isn't a scheduled job. See [Site search](/developers/reference/search). The work itself happens in the apps, behind endpoints that only accept a shared secret.

## The three functions

| Function | When it runs | What it does |
|---|---|---|
| scheduled-dispatch | Every 5 minutes, on its Appwrite schedule | Calls the apps' background endpoints |
| content-notifier | On every row change in `events`, `news` and `jobs`, and each time scheduled-dispatch calls it | Sends the automatic push when content goes live |
| member-roster-sync | Every night on its own schedule, and when staff press **Oppdater nå** (Refresh now) | Rebuilds the admin's member list from 24SevenOffice |

## scheduled-dispatch

### How it works

- Appwrite runs it every 5 minutes (`*/5 * * * *`). The schedule is set in the console. `packages/api/appwrite.config.json` keeps a copy.
- Each run sends a `POST` to every target URL set on the function, all at the same time, with the header `x-cron-secret`. A target whose variable is empty is skipped.
- Each target compares that header with its own `CRON_SECRET`, so the value must be the same on scheduled-dispatch, content-notifier, web, admin and api. A different value gets `401`. If `CRON_SECRET` is missing on admin, api or content-notifier, or on the website in production, the target answers `500`.
- Each call gets 30 seconds (`CRON_TIMEOUT_MS`). Order reconciliation, expense posting, the Finago project sync, the expense check backstop and big event messages get 300 seconds. Big event deliveries get 60. To change one target's limit, set `<VARIABLE>_TIMEOUT_MS`, for example `ORDERS_RECONCILE_URL_TIMEOUT_MS`.
- The function's own timeout limits the whole run. It's 330 seconds in the console. The repo copy says 60, but the console value is the real one. Keep it above the longest target limit.
- The run answers `200` when every call worked and `502` when any failed. A `2xx` reply still counts as failed if its body has `ok: false`, `success: false` or a `failed` count above 0.
- The function also has a domain. A run started through it must send `CRON_SECRET` as `x-cron-secret` or `Authorization: Bearer`, or it gets `401`. Scheduled runs don't need it.

### What it calls

Which targets are set in production is only in the console, under the function's variables. Check there.

| Variable | Calls | What it does | If it stops |
|---|---|---|---|
| `CONTENT_NOTIFIER_URL` | content-notifier's domain | Sends the automatic pushes that are due | No automatic push for new events, news or jobs |
| `ANNOUNCEMENTS_DISPATCH_URL` | admin `POST /api/announcements/dispatch` | Sends scheduled announcements whose time has passed | Scheduled announcements never go out |
| `JOBS_PUBLISH_SCHEDULED_URL` | admin `POST /api/recruitment/publish-scheduled` | Publishes vacancies whose publish time has passed | Scheduled vacancies stay unpublished |
| `TURNOVER_RETENTION_STOP_URL` | admin `POST /api/it/turnover/stop-retention` | Stops Azure Automation retention runs after their 7-day hold, and retries failed stops | Retention runs from a board turnover stay open |
| `ORDERS_RECONCILE_URL` | api `POST /api/cron/reconcile-orders` | Re-checks payments still pending after 10 minutes with Vipps or Stripe, resolves pending refunds, and retries membership fulfilment. When the feature flag `shop_ledger_posting` is on, it also retries missing 24SevenOffice ledger postings. | An order whose payment webhook was missed stays pending: stock isn't reduced and revenue isn't posted. Pending refunds stay pending, and membership invoices stay missing. |
| `EXPENSES_POST_PENDING_URL` | api `POST /api/expenses/post-pending` | Backstop for reimbursements that are still approved but not posted. The api posts each one as soon as its last approver approves, so this only catches one cut short by a restart or approved while the flag was off. It books the oldest approved reimbursements first and reports ones already in progress as skipped. A booking claim that died before marking itself is marked failed after 15 minutes. Does nothing unless the feature flag `expenses_ledger_posting` is on. | Such a reimbursement stays approved and isn't posted |
| `TICKSTER_SYNC_URL` | api `POST /api/tickster/sync` | Imports Tickster ticket buyers into `event_attendees` | Attendee lists stop updating |
| `TICKSTER_EVENTS_SYNC_URL` | api `POST /api/tickster/events/sync` | Copies the events BISO publishes on Tickster into `events` | New Tickster events don't appear on the website or in the app |
| `DEPARTURES_SYNC_URL` | api `POST /api/departures/sync` | Refreshes public-transport departures from Entur | Departures in the app go stale |
| `MEMBER_PASS_CLEANUP_URL` | api `POST /api/cron/cleanup-member-pass` | Deletes member-pass scan logs after 90 days, and scanner links 30 days after they expired | That data is kept longer than the stated retention |
| `FINAGO_PROJECTS_SYNC_URL` | api `POST /api/cron/sync-finago-projects` | Reads Finago projects and two years of booking lines, and keeps each project's history and each department's project share up to date. The dispatcher ticks every 5 minutes, but this runs once a day: only when the last complete sync is over 20 hours old. It reads Finago for `FINAGO_PROJECTS_SYNC_BUDGET_MS` (default 20 seconds, so the run fits the api's 30-second limit). A run that times out or fails waits 2 hours, then continues from the account where it stopped. Progress is kept in `finago_sync_state` (row `projects`). Add `?force=1` to skip the 20-hour and 2-hour checks; it still doesn't run when another attempt started in the last 5 minutes | Expense projects and edition suggestions go stale |
| `EXPENSE_CHECK_BACKSTOP_URL` | api `POST /api/cron/expense-check-backstop` | Finishes reimbursement checks the background run lost. A check that is still `queued` or `running` 10 minutes after it was queued or started (the api's own limit is 5 minutes) is taken over, oldest first, at most 5 per tick, side by side so each run gets the whole 300 seconds: the approvers are told once, or accounting is emailed. A check that gets stuck a second time skips the AI agent and runs the fixed steps only. After three takeovers the backstop stops trying that one and records an approval issue for IT. The target is allowed 300 seconds. See [The expense check](/developers/reference/ai#the-expense-check) | Reimbursements whose check was cut off wait without their approvers being told |
| `RECRUITMENT_RETENTION_CLEANUP_URL` | api `POST /api/cron/cleanup-recruitment` | Deletes job applications, with their résumé, answers and interviews, and candidate profiles, once their 180-day retention has passed | Applicant data outlives the retention BISO promises |
| `BIG_EVENT_DELIVERIES_URL` | api `POST /api/cron/big-event-deliveries` | Queues connect reminders that are due, then sends the big-event connect emails waiting in `big_event_deliveries` at `BIG_EVENTS_EMAILS_PER_MINUTE` (default 25) for up to 45 seconds. While mail is still due, it starts one more run of itself at `NEXT_PUBLIC_API_BASE_URL` (or the address the request came in on, when that's unset), so a large batch keeps flowing between ticks. Answers `500` on every tick until `BIG_EVENTS_CONNECT_SECRET` and a web base URL are set on the api. With those set but no SMTP, it answers `200` and sends nothing. The target is allowed 60 seconds | Connect emails and reminders stay queued |
| `BIG_EVENT_MESSAGES_URL` | api `POST /api/cron/big-event-messages` | Sends big-event messages whose scheduled time has passed, finishes a send that has made no progress for 10 minutes, and tries again an automatic message that failed at least 10 minutes ago and was due within the last 2 hours (a manual one waits for "Try again" in the admin). For a published big event with Travel on and its bus lists published, that hasn't ended more than 24 hours ago, it tells everyone whose bus changed at least 10 minutes ago, so a second move within those minutes replaces the first: "You're on Bus 2" the first time, "Your bus seat has changed" after that, or "no seat" without a bus out on their own campus. Both name the trip home when it is on another bus. One message per kind and campus; a group too large for one message's audience is split into several messages. The "You're on" and "moved" kinds each have a switch in the big event's settings. "No seat" has none of its own: it follows the "moved" switch for someone who was told before and the "You're on" switch otherwise. With the switch off, the person is marked as told without a message. Someone moved again while the run is working keeps their notice for the next run. It also sends one reminder per bus leg 2 hours before it leaves, only for a leg that has people on it. Pushes go out in the run, four at a time; emails and SMS are queued for `BIG_EVENT_DELIVERIES_URL`. After 40 seconds no new send starts and no further message is written; the rest waits for the next tick. A send already going may run on, so the target is allowed 300 seconds | Scheduled messages, bus messages and departure reminders don't go out |
| `BIG_EVENTS_CLEANUP_URL` | api `POST /api/cron/cleanup-big-events` | Deletes a big event's participants, group memberships, email deliveries, each person's copy of its messages, and the pushes sent about it (`announcements` with its `biso://big-event` link) with their app inbox rows in `user_notifications`, 30 days after it ends. The event, its messages and its groups stay, the groups without names: a room takes its room number, or "Rom", in place of the buyer's name, and every group loses its buyer and contact person. At most 1,000 rows deleted or groups changed a run; the next run goes on | Participants' personal data is kept longer than the stated retention |
| `RESERVATIONS_CLEANUP_URL` | web `POST /api/cron/cleanup-reservations` | Deletes expired cart reservations, which hold stock for 10 minutes | Expired reservation rows pile up in `cart_reservations`. Stock isn't affected, because availability already ignores expired holds. |

Two things to know about the targets:

- **A target fails on every run if the feature behind it isn't set up.** The ticket-buyer sync answers `500` without `TICKSTER_API_KEY` and `TICKSTER_EOG_CODE`, the event sync without `TICKSTER_API_KEY`, and the retention stop without `AZURE_RETENTION_STOP_WEBHOOK_URL`. Leave a target's variable empty until the feature is configured.
- **There are two order-reconciliation routes.** The api route is the current one. The website still has a deprecated copy at the same path, `/api/cron/reconcile-orders`. Check that `ORDERS_RECONCILE_URL` points at `api.biso.no`. Running both does no harm, because every payment update claims the order first.

### Check that it's working

In the console, open **Functions**, then scheduled-dispatch, then **Executions**, and open a recent run. Its output is split across the **Logs** and **Errors** tabs, and every line starts with `[scheduled-dispatch]`. A healthy run looks like this:

```text
[scheduled-dispatch] start trigger=schedule method=POST
[scheduled-dispatch] config secretSet=true fallbackTimeoutMs=30000 configured=[…] skipped=[…]
[scheduled-dispatch] dispatching … ping(s): …
[scheduled-dispatch] OK ANNOUNCEMENTS_DISPATCH_URL https://admin.biso.no/api/announcements/dispatch -> 200 (812ms)
[scheduled-dispatch] done {"durationMs":…,"failed":0,"succeeded":…,"total":…}
```

| What you see | What it means | Fix |
|---|---|---|
| No executions at all | The schedule is empty or the function is disabled | Set the schedule to `*/5 * * * *` and enable the function |
| No `start` line | The deployment never ran the code | Check the build log, the entrypoint and the runtime |
| `CRON_SECRET is not configured` | The function has no `CRON_SECRET` | Set it on the function |
| `configured=[]` or `nothing to do` | No target URL is set | Set the target variables |
| `FAIL <NAME> <URL> -> 401 (…ms): …` | The target's `CRON_SECRET` differs from the function's | Set the same value on both, then redeploy as in [Redeploy without shipping new code](/developers/keep-it-running/deploying#redeploy-without-shipping-new-code) |
| `FAIL <NAME> <URL> -> 500 (…ms): …` | The target answered with an error: a missing setting, or the job itself failed | Read the body at the end of the log line, then the target app's logs |
| `FAIL <NAME> <URL> -> 200 (…ms): {"ok":false…}` | The target answered `200` but its body reports a failure, for example `ok: false` or a `failed` count above 0 | Read the body, then the target app's logs |
| `FAIL <NAME> <URL> -> no-response (…ms): request aborted after …` | The target took longer than its limit | Raise its `<VARIABLE>_TIMEOUT_MS`, and keep the function timeout above it |
| `FAIL <NAME> <URL> -> no-response (…ms):` followed by any other error | The function couldn't reach the target: the app is down, or the URL is wrong | Check the target app's `/api/health`, and the URL in the function's variables |
| `uncaught error` | An unexpected error | The stack trace in **Errors** points at the cause |

### How Sentry watches them

With `SENTRY_DSN` set on the function, each run reports to the `biso-functions` project in Sentry. Without it nothing is reported and the function runs as before.

- **`scheduled-dispatch`** is one cron monitor for the whole run, expected every 5 minutes.
- **`dispatch-<target>`** is one monitor per target, named after its variable in lower case with dashes: `CONTENT_NOTIFIER_URL` becomes `dispatch-content-notifier`, `ORDERS_RECONCILE_URL` becomes `dispatch-orders-reconcile`. The dispatcher checks in before it calls the target and closes the check-in when the target answers, so a monitor shows which target is slow or failing. A target's monitor is created the first time that target runs in production. After the first week, check that the "site is down or a scheduled job failed" alert covers it ([Monitoring and health](/developers/keep-it-running/monitoring-and-health#the-alerts)). A target with no URL set has no monitor.
- A failed target also sends an error event tagged `target`. The alerts leave those events out, because the monitor already alerts.
- **A monitor goes red** when a run fails, when no check-in arrives within 2 minutes of the expected time, or when a run takes longer than its limit. The limit is the target's timeout plus one minute, and at least 2 minutes: 2 for most targets and 6 for the 300-second ones, such as orders-reconcile, expenses-post-pending and big-event-messages. scheduled-dispatch's own monitor allows 6. member-roster-sync's monitor allows 30 minutes of lateness and 20 minutes of run time.
- **It takes two.** Every monitor opens an issue, and so emails the owner, only after two failed or missed runs in a row. One good run closes the issue. For member-roster-sync, the first email comes after the second failed night.
- **Finding the function's errors.** Error events from the functions carry the tag `function_name`. Filter on it in `biso-functions` to see one function's errors.

A failed target's error says which target failed and the HTTP status. The response body isn't sent. The events and the check-ins go through the scrubber anyway. The code is in `packages/observability/src/functions/reporter.ts`. member-roster-sync and content-notifier each have a `src/report.ts` for what they report. scheduled-dispatch has none: its reporting, including every monitor's settings, is in `src/main.ts`.

### Run a job by hand

To run every target now, send the secret to the function's domain. The domain is shown on the function in the console, and `CRON_SECRET` is in Infisical.

```bash
curl -X POST "https://<scheduled-dispatch's domain>/" -H "x-cron-secret: $CRON_SECRET"
```

To run one job, call its endpoint directly:

```bash
curl -X POST https://api.biso.no/api/cron/reconcile-orders -H "Authorization: Bearer $CRON_SECRET"
```

Both run the real job against production, the same as the next scheduled run would.

A run started through the domain may be cut off after 30 seconds, which is Appwrite's limit for domain executions (`functions/scheduled-dispatch/README.md`). Order reconciliation, expense posting, the Finago project sync, the expense check backstop and big event messages can take up to 300 seconds, so call those directly.

### Add a job

1. Write the endpoint in the app that owns the work. Check `CRON_SECRET` from `x-cron-secret` or `Authorization: Bearer` with `safeSecretCompare` from `@repo/shared/utils/secrets`, as the existing targets do.
2. Add the new variable name to `TARGET_ENV_VARS` in `functions/scheduled-dispatch/src/main.ts`. The function only reads the names in that list.
3. Deploy the app. See [Deploying](/developers/keep-it-running/deploying).
4. Set the new variable on scheduled-dispatch in the console, and add it to `functions/scheduled-dispatch/.env.example`.
5. Deploy the function. If you set the variable after deploying it, redeploy it.
6. Check the next run. Its `configured=[…]` line lists the new name, and its result line shows `OK`.

## content-notifier

- **On row events.** Any row change in `events`, `news` or `jobs` runs it. It keeps one lock row per item in `content_notifications`, with the state `pending`, `sent`, `cancelled` or `skipped`. A new lock is due after `NOTIFY_DELAY_MINUTES`, 3 minutes by default. An item that stops being eligible has its lock cancelled, and the lock reopens if the item becomes eligible again.
- **On each scheduled-dispatch run.** The ping starts a dispatch pass. It sends every lock that's due, combines two or more items on the same channel into one notification, and marks the locks `sent` before pushing, so a failure never sends twice.
- **At night.** Nothing is pushed during the Oslo night. Anything due after 22:00 waits until 08:00.
- **On failure.** A pass with any failure answers `500` with its counts, so scheduled-dispatch logs it as failed. The details are in content-notifier's own execution log.
- **One dispatcher only.** The function has no schedule of its own. Don't add one, and don't add a second copy of the function.

If it stops, nothing new gets an automatic push. Pending locks go out at the next pass that works.

With `SENTRY_DSN` set, it reports its own errors to Sentry, except a refusal for a wrong `CRON_SECRET` (`401` or `403`), which isn't an error in the function. Its pass is also watched through the dispatcher's `dispatch-content-notifier` monitor.

To check it, save a news item in the admin. An execution with the trigger `event` should appear under the function's executions, and it shouldn't answer `400`.

## member-roster-sync

- It runs every night on its own schedule. Its README suggests `0 3 * * *`, and the real schedule is in the console. Staff can also start it with **Oppdater nå** (Refresh now) on the admin's members page (`/members`).
- It copies every membership product in 24SevenOffice into `memberships`, then rebuilds `member_roster`, the list on the members page.
- The roster is for display only. Live membership checks don't read it.
- A run that overlaps another one stops at once. A failed run answers `500`, and the members page shows **Siste oppdatering feilet** (Last refresh failed). A run still `processing` after 15 minutes counts as stuck.

If it stops, the members page goes stale. New membership plans added in 24SevenOffice also don't reach `memberships`, which decides what's for sale. Nothing else fills that table.

With `SENTRY_DSN` set, it has its own cron monitor, `member-roster-sync`, that expects a run on `MEMBER_ROSTER_SYNC_SCHEDULE` (default `0 3 * * *`). A failed run sends an error event whose stack names files and functions but never a member. If you change the schedule in the console, change that variable too, or Sentry reports a missed run every night.

Don't run it from your machine against production. A local run uses the Appwrite settings in `apps/admin/.env.local`, skips the overlap guard, and can delete the rows of a run that's in progress.

## Webhooks and calls between services

### Calls into BISO

| From | Endpoint | What it's for | Notes |
|---|---|---|---|
| Vipps | api `POST /api/payment/vipps/callback` | Payment status updates | Checked with the webhook secret stored in the `payment_settings` table, or `VIPPS_WEBHOOK_SECRET` as a fallback. The webhook is registered once per merchant and mode from the admin's payment settings (`/settings/payments`). Register it again after switching between test and live, or after changing the merchant. |
| Stripe | api `POST /api/payment/stripe/callback` | Checkout session events: completed, expired, and async payment succeeded or failed | No code registers this endpoint. It's set up in Stripe's dashboard. |
| Microsoft Teams | api `POST /api/teams/bot` | The expense-approval bot | |
| Appwrite, for BI sign-in | api `/api/auth/bi-oidc/openid-configuration` and `/api/auth/bi-userinfo` | Appwrite's BI sign-in provider reads these | If the api is down, BI sign-in fails on the website and in the app |
| Old links | web `/api/checkout/webhook` and `/api/checkout/return` | Left over from when checkout ran on the website | The webhook answers `410`. The return route forwards buyers to the api's `/api/payment/return`. |

A missed Vipps or Stripe webhook isn't lost as long as `ORDERS_RECONCILE_URL` is set: order reconciliation re-checks the order once it has been pending for 10 minutes.

### Calls out of BISO

| From | To | When | If it fails |
|---|---|---|---|
| admin | web `POST /api/revalidate`, at `NEXT_PUBLIC_WEB_BASE_URL`, with `x-cron-secret` | After an editor saves benefits, benefit partners, membership texts, pages or site logos | The website shows old content until its cache expires. It gives up after 3 seconds and never blocks the save. It's skipped, with a warning in the log, if `NEXT_PUBLIC_WEB_BASE_URL` or `CRON_SECRET` is unset. |
| admin | api `/api/payment/vipps/webhooks/register`, with `CRON_SECRET` | A global admin registers the Vipps webhook | The settings page shows the error |
| admin | api `/api/expenses/resend-approval`, with `CRON_SECRET` | IT resends an expense approval | The admin shows the error |
| admin | Azure Automation, at `AZURE_RETENTION_START_WEBHOOK_URL` | A board turnover of a Microsoft role account starts | The turnover job is left as `retention_start_failed` |
| admin's retention stop job | Azure Automation, at `AZURE_RETENTION_STOP_WEBHOOK_URL` | 7 days after the start | The job is left as `stop_failed` and retried on the next run |

The Azure Automation URLs carry their own token. Treat them as secrets.

## Endpoints with no schedule

These look like scheduled jobs, but nothing runs them on a timer.

- **api `/api/cleanup-anon-users`** deletes anonymous Appwrite users with no email, not verified, and not updated for 14 days. The only schedule for it is in `apps/api/vercel.json`, and Vercel's cron doesn't run on Appwrite. scheduled-dispatch has no target for it, so anonymous users pile up. The website only creates them when a visitor uses the cart. To schedule it, add a target as described in [Add a job](#add-a-job), and expect the first run to delete a backlog.
- **api `/api/admin/account-turnover`** and its `/bulk` route post to `AZURE_ACCOUNT_TURNOVER_WEBHOOK_URL`. Both need a global admin. Nothing in the repo calls them. The admin's board turnover uses the retention webhooks above instead.
- **web `/api/cron/reconcile-orders`** is deprecated. It runs only if `ORDERS_RECONCILE_URL` still points at the website. Delete it, and the `/api/checkout/return` forwarder, once that variable points at the api.
- **admin `POST /api/units/sync`** copies departments from 24SevenOffice. It isn't scheduled. A global admin runs it with the sync button on the admin's departments page when 24SevenOffice's chart of departments changes.
