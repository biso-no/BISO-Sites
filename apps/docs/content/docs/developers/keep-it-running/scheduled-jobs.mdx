This page lists everything that runs without someone pressing a button, and every webhook. Use it when something that should happen on its own didn't: an announcement wasn't sent, an order stayed pending, a push never went out. Three Appwrite functions do all the scheduling. The work itself happens in the apps, behind endpoints that only accept a shared secret.

## The three functions

| Function | When it runs | What it does |
|---|---|---|
| scheduled-dispatch | Every 5 minutes, on its Appwrite schedule | Calls the apps' background endpoints |
| content-notifier | On every row change in `events`, `news` and `jobs`, and each time scheduled-dispatch calls it | Sends the automatic push when content goes live |
| member-roster-sync | Every night on its own schedule, and when staff press **Oppdater nå** (Refresh now) | Rebuilds the admin's member list from 24SevenOffice |

## scheduled-dispatch

### How it works

- Appwrite runs it every 5 minutes (`*/5 * * * *`). The schedule is set in the console. `packages/api/appwrite.config.json` keeps a copy.
- Each run sends a `POST` to every target URL set on the function, all at the same time, with the header `x-cron-secret`. A target whose variable is empty is skipped.
- Each target compares that header with its own `CRON_SECRET`, so the value must be the same on the function and on web, admin and api. A different value gets `401`. If `CRON_SECRET` is missing on admin or api, the target answers `500`.
- Each call gets 30 seconds (`CRON_TIMEOUT_MS`). Order reconciliation and expense posting get 300 seconds. To change one target's limit, set `<VARIABLE>_TIMEOUT_MS`, for example `ORDERS_RECONCILE_URL_TIMEOUT_MS`.
- The function's own timeout limits the whole run. It's 330 seconds in the console. The repo copy says 60, but the console value is the real one. Keep it above the longest target limit.
- The run answers `200` when every call worked and `502` when any failed. A `2xx` reply still counts as failed if its body has `ok: false`, `success: false` or a `failed` count above 0.
- The function also has a domain. A run started through it must send `CRON_SECRET` as `x-cron-secret` or `Authorization: Bearer`, or it gets `401`. Scheduled runs don't need it.

### What it calls

Which targets are set in production is only in the console, under the function's variables. Check there.

| Variable | Calls | What it does | If it stops |
|---|---|---|---|
| `CONTENT_NOTIFIER_URL` | content-notifier's domain | Sends the automatic pushes that are due | No automatic push for new events, news or jobs |
| `ANNOUNCEMENTS_DISPATCH_URL` | admin `POST /api/announcements/dispatch` | Sends scheduled announcements whose time has passed | Scheduled announcements never go out |
| `JOBS_PUBLISH_SCHEDULED_URL` | admin `POST /api/recruitment/publish-scheduled` | Publishes vacancies whose publish time has passed | Scheduled vacancies stay unpublished |
| `TURNOVER_RETENTION_STOP_URL` | admin `POST /api/it/turnover/stop-retention` | Stops Azure Automation retention runs after their 7-day hold, and retries failed stops | Retention runs from a board turnover stay open |
| `ORDERS_RECONCILE_URL` | api `POST /api/cron/reconcile-orders` | Re-checks payments still pending after 10 minutes with Vipps or Stripe, retries missing 24SevenOffice ledger postings, resolves pending refunds, and retries membership fulfilment | An order whose payment webhook was missed stays pending: stock isn't reduced and revenue isn't posted. Pending refunds stay pending, and membership invoices stay missing. |
| `EXPENSES_POST_PENDING_URL` | api `POST /api/expenses/post-pending` | Posts approved reimbursements to the 24SevenOffice ledger. Does nothing unless the feature flag `expenses_ledger_posting` is on. | With the flag on, approved reimbursements aren't posted |
| `TICKSTER_SYNC_URL` | api `POST /api/tickster/sync` | Imports Tickster ticket buyers into `event_attendees` | Attendee lists stop updating |
| `TICKSTER_EVENTS_SYNC_URL` | api `POST /api/tickster/events/sync` | Copies the events BISO publishes on Tickster into `events` | New Tickster events don't appear on the website or in the app |
| `DEPARTURES_SYNC_URL` | api `POST /api/departures/sync` | Refreshes public-transport departures from Entur | Departures in the app go stale |
| `MEMBER_PASS_CLEANUP_URL` | api `POST /api/cron/cleanup-member-pass` | Deletes member-pass scan logs after 90 days, and scanner links 30 days after they expired | That data is kept longer than the stated retention |
| `RECRUITMENT_RETENTION_CLEANUP_URL` | api `POST /api/cron/cleanup-recruitment` | Deletes job applications, with their résumé, answers and interviews, and candidate profiles, once their 180-day retention has passed | Applicant data outlives the retention BISO promises |
| `RESERVATIONS_CLEANUP_URL` | web `POST /api/cron/cleanup-reservations` | Deletes expired cart reservations, which hold stock for 10 minutes | Held stock isn't released |

Two things to know about the targets:

- **A target fails on every run if the feature behind it isn't set up.** The Tickster syncs answer `500` without their Tickster variables, and the retention stop answers `500` without `AZURE_RETENTION_STOP_WEBHOOK_URL`. Leave a target's variable empty until the feature is configured.
- **There are two order-reconciliation routes.** The api route is the current one. The website still has a deprecated copy at the same path, `/api/cron/reconcile-orders`. Check that `ORDERS_RECONCILE_URL` points at `api.biso.no`. Running both does no harm, because every payment update claims the order first.

### Check that it's working

In the console, open **Functions**, then scheduled-dispatch, then **Executions**, and open a recent run. Its output is split across the **Logs** and **Errors** tabs, and every line starts with `[scheduled-dispatch]`. A healthy run looks like this:

```text
[scheduled-dispatch] start trigger=schedule method=POST
[scheduled-dispatch] config secretSet=true fallbackTimeoutMs=30000 configured=[…] skipped=[…]
[scheduled-dispatch] dispatching … ping(s): …
[scheduled-dispatch] OK ANNOUNCEMENTS_DISPATCH_URL https://admin.biso.no/api/announcements/dispatch -> 200 (812ms)
[scheduled-dispatch] done {"durationMs":…,"failed":0,"succeeded":…,"total":…}
```

| What you see | What it means | Fix |
|---|---|---|
| No executions at all | The schedule is empty or the function is disabled | Set the schedule to `*/5 * * * *` and enable the function |
| No `start` line | The deployment never ran the code | Check the build log, the entrypoint and the runtime |
| `CRON_SECRET is not configured` | The function has no `CRON_SECRET` | Set it on the function |
| `configured=[]` or `nothing to do` | No target URL is set | Set the target variables |
| `FAIL … -> 401` | The target's `CRON_SECRET` differs from the function's | Set the same value on both, then redeploy |
| `FAIL … -> 500` | The target's app is missing a setting | Open the body in the log line. It names the setting, for example `CRON_SECRET is not configured`. |
| `FAIL … -> no-response: request aborted` | The target took longer than its limit | Raise its `<VARIABLE>_TIMEOUT_MS`, and keep the function timeout above it |
| `uncaught error` | An unexpected error | The stack trace in **Errors** points at the cause |

### Run a job by hand

To run every target now, send the secret to the function's domain. The domain is shown on the function in the console, and `CRON_SECRET` is in Infisical.

```bash
curl -X POST "https://<scheduled-dispatch's domain>/" -H "x-cron-secret: $CRON_SECRET"
```

To run one job, call its endpoint directly:

```bash
curl -X POST https://api.biso.no/api/cron/reconcile-orders -H "Authorization: Bearer $CRON_SECRET"
```

Both run the real job against production, the same as the next scheduled run would.

### Add a job

1. Write the endpoint in the app that owns the work. Check `CRON_SECRET` from `x-cron-secret` or `Authorization: Bearer` with `safeSecretCompare` from `@repo/shared/utils/secrets`, as the existing targets do.
2. Add the new variable name to `TARGET_ENV_VARS` in `functions/scheduled-dispatch/src/main.ts`. The function only reads the names in that list.
3. Deploy the app, then the function. See [Deploying](/developers/keep-it-running/deploying#scheduled-dispatch).
4. Set the new variable on the function in the console, and add it to `functions/scheduled-dispatch/.env.example`.

## content-notifier

- **On row events.** Any row change in `events`, `news` or `jobs` runs it. It keeps one lock row per item in `content_notifications`, with the state `pending`, `sent`, `cancelled` or `skipped`. A new lock is due after `NOTIFY_DELAY_MINUTES`, 3 minutes by default. An item that stops being eligible has its lock cancelled, and the lock reopens if the item becomes eligible again.
- **On each scheduled-dispatch run.** The ping starts a dispatch pass. It sends every lock that's due, combines two or more items on the same channel into one notification, and marks the locks `sent` before pushing, so a failure never sends twice.
- **At night.** Nothing is pushed during the Oslo night. Anything due after 22:00 waits until 08:00.
- **On failure.** A pass with any failure answers `500` with its counts, so scheduled-dispatch logs it as failed. The details are in content-notifier's own execution log.
- **One dispatcher only.** The function has no schedule of its own. Don't add one, and don't add a second copy of the function.

If it stops, nothing new gets an automatic push. Pending locks go out at the next pass that works.

To check it, save a news item in the admin. An execution with the trigger `event` should appear under the function's executions, and it shouldn't answer `400`.

## member-roster-sync

- It runs every night on its own schedule. Its README suggests `0 3 * * *`, and the real schedule is in the console. Staff can also start it with **Oppdater nå** (Refresh now) on the admin's members page (`/members`).
- It copies every membership product in 24SevenOffice into `memberships`, then rebuilds `member_roster`, the list on the members page.
- The roster is for display only. Live membership checks don't read it.
- A run that overlaps another one stops at once. A failed run answers `500`, and the members page shows **Siste oppdatering feilet** (Last refresh failed). A run still `processing` after 15 minutes counts as stuck.

If it stops, the members page goes stale. New membership plans added in 24SevenOffice also don't reach `memberships`, which decides what's for sale. Nothing else fills that table.

Don't run it from your machine against production. A local run uses the Appwrite settings in `apps/admin/.env.local`, skips the overlap guard, and can delete the rows of a run that's in progress.

## Webhooks and calls between services

### Calls into BISO

| From | Endpoint | What it's for | Notes |
|---|---|---|---|
| Vipps | api `POST /api/payment/vipps/callback` | Payment status updates | Checked with the webhook secret stored in the `payment_settings` table, or `VIPPS_WEBHOOK_SECRET` as a fallback. The webhook is registered once per merchant and mode from the admin's payment settings (`/settings/payments`). Register it again after switching between test and live, or after changing the merchant. |
| Stripe | api `POST /api/payment/stripe/callback` | Checkout session events: completed, expired, and async payment succeeded or failed | No code registers this endpoint. It's set up in Stripe's dashboard. |
| Microsoft Teams | api `POST /api/teams/bot` | The expense-approval bot | |
| Appwrite, for BI sign-in | api `/api/auth/bi-oidc/openid-configuration` and `/api/auth/bi-userinfo` | Appwrite's BI sign-in provider reads these | If the api is down, BI sign-in fails on the website and in the app |
| Old links | web `/api/checkout/webhook` and `/api/checkout/return` | Left over from when checkout ran on the website | The webhook answers `410`. The return route forwards buyers to the api's `/api/payment/return`. |

A missed Vipps or Stripe webhook isn't lost as long as `ORDERS_RECONCILE_URL` is set: order reconciliation re-checks the order once it has been pending for 10 minutes.

### Calls out of BISO

| From | To | When | If it fails |
|---|---|---|---|
| admin | web `POST /api/revalidate`, at `NEXT_PUBLIC_WEB_BASE_URL`, with `x-cron-secret` | After an editor saves benefits, benefit partners, membership texts, pages or site logos | The website shows old content until its cache expires. It gives up after 3 seconds and never blocks the save. It's skipped, with a warning in the log, if `NEXT_PUBLIC_WEB_BASE_URL` or `CRON_SECRET` is unset. |
| admin | api `/api/payment/vipps/webhooks/register`, with `CRON_SECRET` | A global admin registers the Vipps webhook | The settings page shows the error |
| admin | api `/api/expenses/resend-approval`, with `CRON_SECRET` | IT resends an expense approval | The admin shows the error |
| admin | Azure Automation, at `AZURE_RETENTION_START_WEBHOOK_URL` | A board turnover of a Microsoft role account starts | The turnover job is left as `retention_start_failed` |
| admin's retention stop job | Azure Automation, at `AZURE_RETENTION_STOP_WEBHOOK_URL` | 7 days after the start | The job is left as `stop_failed` and retried on the next run |

The Azure Automation URLs carry their own token. Treat them as secrets.

## Endpoints nothing calls

- **api `/api/cleanup-anon-users`** deletes anonymous Appwrite users with no email, not verified, and not updated for 14 days. The only schedule for it is in `apps/api/vercel.json`, and Vercel's cron doesn't run on Appwrite. scheduled-dispatch has no target for it, so anonymous users pile up. The website only creates them when a visitor uses the cart. To schedule it, add a target as described in [Add a job](#add-a-job), and expect the first run to delete a backlog.
- **api `/api/admin/account-turnover`** and its `/bulk` route post to `AZURE_ACCOUNT_TURNOVER_WEBHOOK_URL`. Nothing in the repo calls them. The admin's board turnover uses the retention webhooks above instead.
- **web `/api/cron/reconcile-orders`** is deprecated. Delete it, and the `/api/checkout/return` forwarder, once `ORDERS_RECONCILE_URL` points at the api.
- **admin `POST /api/units/sync`** copies departments from 24SevenOffice. It isn't scheduled. A global admin runs it with the sync button on the admin's departments page when 24SevenOffice's chart of departments changes.
