Use this page when you set up a Site or a function, add a variable, or rotate a secret. It explains where each value is kept, how it gets to the apps, and which app reads which variable. Nothing copies values between these places for you, so most problems here come from a value changed in one place and not the other.

## Where values are kept

- **Infisical** is the developers' store. Fetch credentials from it, for example when you set up a new machine. Address: <Private name="infisical-url" label="Infisical" />. Where each app's values are: <Private name="infisical-layout" label="Infisical layout" />.
- **The Appwrite console** holds the values the apps use. Each Site and each function has its own variables. They're copied there from Infisical by hand.
- **Nothing keeps the two in step.** When you change a value in the console, change it in Infisical too, or the next person copies the old one.

Some values live elsewhere:

- **Vipps and Stripe credentials** are in the `payment_settings` table, encrypted, and edited on the admin's payment settings page (`/settings/payments`). The `VIPPS_*` variables are used only when the table has no complete Vipps set for the active mode, and the `STRIPE_*` variables only when it has no Stripe secret key for the active mode. So changing those variables may change nothing. The api reads them for checkout and payment updates, and the admin for refunds. One exception: `VIPPS_WEBHOOK_SECRET` is also used when the table's set is complete but has no webhook secret for the active mode.
- **Function API keys** come from Appwrite. Each run gets its own key with the function's scopes. Never set `APPWRITE_*` variables on a function.
- **The admin's Microsoft sign-in secret** is set in Appwrite's Microsoft sign-in provider, in the console. It isn't a variable. The same goes for the BI sign-in's client id and secret, on Appwrite's `oidc` provider.
- **Docs** read their private values from Infisical while they run, through a read-only machine identity (the `INFISICAL_*` variables). The website, admin and API never read Infisical.
- **The Android build's signing values** are GitHub secrets in the BISO-Flutter repository.
- **The BISO app** has no settings to change. Its Appwrite address, project and API address are written into its code.

## Build time and run time

- **`NEXT_PUBLIC_*` variables** are copied into the app by `next build`, in both the server and the browser code. Set them on the Site before you deploy, and deploy again after you change one. Never put a secret in one: it ends up in the browser.
- **Every other variable** is read while the app runs. After you change one, redeploy the Site or function anyway. That's the sure way to have the running app use the new value. Redeploy without shipping new code, as in [Deploying](/developers/keep-it-running/deploying#redeploy-without-shipping-new-code).
- **`turbo.json`** matters for builds. The `build:*` scripts build through Turbo, which runs in strict mode: the build sees only the variables listed under `tasks.build.env`, plus every `NEXT_PUBLIC_*` variable, which Turbo adds by itself for Next.js apps. If a build needs a new variable, add it to that list. Turbo also uses the list to decide when it can reuse a cached build. It never sets a value.
- **Locally**, put values in `apps/<app>/.env.local`. Turbo drops variables you `export` in the shell, except `NEXT_PUBLIC_*` ones, because the `dev` task lists none. [Your first day](/developers/start-here/your-first-day#run-the-apps-against-a-non-production-appwrite-project) has the steps.

## Unset Appwrite settings mean production

<Callout type="warn">
If `NEXT_PUBLIC_APPWRITE_ENDPOINT` or `NEXT_PUBLIC_APPWRITE_PROJECT` is unset, the apps use the production value for it, without saying so. Only the admin prints a warning.
</Callout>

How the fallback works:

- **The two values fall back one at a time.** Server code tries `NEXT_PUBLIC_APPWRITE_PROJECT`, then `APPWRITE_PROJECT_ID`, then the production project `biso`. The endpoint tries `NEXT_PUBLIC_APPWRITE_ENDPOINT`, then `APPWRITE_ENDPOINT`, then production Appwrite (`packages/api/server-env.ts`). Browser code and file links skip the second choice (`packages/api/client.ts`, `packages/api/storage.ts`). So setting only the project still talks to the production server, and setting only the endpoint uses the production project id.
- **The admin's warning checks the variables while it runs.** It says `[admin] Falling back to production Appwrite defaults for unset env: …`. But Next.js fixes each `NEXT_PUBLIC_*` value that was set at build time, on the server too. A value changed after the build doesn't reach the app at all. A value that was unset at build time and added later reaches the server but never the browser, which keeps using production, and the warning won't tell you. Set both before you build.
- **The website and the API don't warn at all.**
- **Functions fall back too.** content-notifier and member-roster-sync use the same code, and the settings in their READMEs include none of these variables, so they call the production project. That's right in production. A copy of a function in another project would call production with that project's key, and fail.

How to avoid it:

1. Set both `NEXT_PUBLIC_APPWRITE_ENDPOINT` and `NEXT_PUBLIC_APPWRITE_PROJECT` everywhere you run an app: in `.env.local` locally, and on the Site before you build anywhere else, such as a restore or a test Site.
2. Use an `APPWRITE_API_KEY` from the same project. A key from another project fails, which is the safe outcome.
3. After a start, check the admin's log for the `Falling back` line. In the browser's network tab, check that Appwrite requests go to your server, with your project in the `X-Appwrite-Project` header.
4. Scripts that run with `bun --env-file=apps/admin/.env.local`, such as the content-notifier backfill and a local member-roster-sync run, write to whatever project that file names. If it names none, that's production. Check the file before you run them.

## The variables that matter most

If one of these is wrong, a whole app or feature stops. The [full list](#all-variables-by-service) follows.

| Variable | Read by | What happens if it's wrong |
|---|---|---|
| `NEXT_PUBLIC_APPWRITE_ENDPOINT`, `NEXT_PUBLIC_APPWRITE_PROJECT` | All four apps | Unset means production. See above. |
| `APPWRITE_API_KEY` | web, admin, api | The admin won't start. Server actions and `/api/health/ready` fail. |
| `APPWRITE_SESSION_COOKIE` | web (`a_session_biso_web`), admin and docs (`a_session_biso_admin`) | web and admin refuse to start. Docs reads the wrong cookie and doesn't recognise admins. |
| `NEXT_PUBLIC_BASE_URL` | Each app's own address | The admin refuses to start without it, and sends Microsoft sign-in back to this address. |
| `NEXT_PUBLIC_API_BASE_URL` | web, admin, api | Shop checkout and membership purchase fail on the website. Its API client falls back to `http://localhost:3003`. |
| `CRON_SECRET` | web, admin, api, scheduled-dispatch, content-notifier | Scheduled jobs fail, and the admin's calls to the website and the API fail. It must be the same everywhere. |
| `ANTHROPIC_API_KEY` | admin, api, web | The AI features fail. It's in no `.env.example` and named nowhere in the code: the AI library reads it by itself. |
| `TFSO_APP_ID`, `TFSO_USERNAME`, `TFSO_PASSWORD` | admin, api, member-roster-sync | Membership checks, membership purchases and the member roster fail. |
| `MEMBER_PASS_SECRET` | web, admin, api | The member pass and scanning stop. It must be the same everywhere and at least 32 characters, or the apps treat it as unset. |

## Rotate a secret

Rotate a secret when it expires, when it has leaked, or when someone who knew it leaves. Do it in this order:

1. **Make the new value.** Get it from where the secret comes from: the Azure portal, the Appwrite console, or the provider's dashboard. For a secret BISO makes up itself, such as `CRON_SECRET`, generate one:

   ```bash
   openssl rand -base64 48
   ```

2. **Store it in Infisical** (<Private name="infisical-layout" label="Infisical layout" />).
3. **Set it in the Appwrite console** on every Site and function in the table below. For an Azure secret, first find every variable that holds a secret of the same app registration (see [Azure secrets](#azure-secrets)), and set the new value on all of them.
4. **Redeploy** each of those Sites and functions without shipping new code, as in [Deploying](/developers/keep-it-running/deploying#redeploy-without-shipping-new-code).
5. **Check** that the feature works. The table says how.
6. **Remove the old value** where it came from. Do this last, so the apps keep working while you switch.

Where the provider allows two values at once, as Azure app registrations and Appwrite API keys do, step 6 gives you a gap-free switch.

Some secrets have only one value at a time, so the apps fail from the moment it changes until every place has the new one:

- **Secrets BISO makes up itself**, such as `CRON_SECRET`. Each app accepts only its own current value.
- **Account passwords at a provider**, such as `TFSO_PASSWORD`, `SMTP_PASSWORD` and `UMAMI_PASSWORD`. The old password stops working as soon as you change it at the provider.

Change those at a quiet time and in one sitting. Have the new value, the console and the redeploys ready before you change anything, and set and redeploy straight after.

### Azure secrets

Where each Azure app registration lives and who owns it: <Private name="azure-app-registration" label="Azure app registrations" />.

One registration's secret can sit in several variables. Before you rotate one, find all of them:

1. Note the registration's application id in the Azure portal.
2. In the console, find every Site whose client-id variables hold that id: `AZURE_GRAPH_CLIENT_ID`, `AZURE_APP_ID`, `AZURE_CLIENT_ID`, `SHAREPOINT_CLIENT_ID`, `BI_AZURE_CLIENT_ID` and `TEAMS_BOT_APP_ID`.
3. Update the matching secret variable next to each of them. Watch the fallbacks: the api's admin user routes use `SHAREPOINT_CLIENT_SECRET` when `AZURE_GRAPH_CLIENT_SECRET` is unset (`apps/api/src/app/api/admin/users/route.ts`), and interview scheduling uses `AZURE_CLIENT_SECRET` the same way.

In October 2026 the owner was rolling the secret of the "BISO Sites" registration. Find which variables use it the same way.

### Secrets to leave alone

<Callout type="warn">
Changing `MEMBER_PASS_SECRET` stops every pass already in Apple Wallet or Google Wallet from scanning. The Apple Wallet code is signed with it and never changes, and the Google Wallet code is worked out from it. The pass on the website recovers by itself, because it fetches fresh codes. Only rotate this secret if it has leaked.
</Callout>
