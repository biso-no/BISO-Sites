Read this before you add or change an AI feature, or when one stops working. Every AI feature in the apps runs on Anthropic's models, through the Vercel AI SDK. The model choice lives in one file, `packages/ai/src/models.ts`. OpenAI is called only by the one-off WordPress import, and Pinecone isn't used at all. [AI features fail](/developers/keep-it-running/when-things-break#ai-features-fail) is the runbook for a live problem.

## Account and cost

BISO pays Anthropic for what the apps use. Its non-profit Team plan comes with about USD 160 of credit a month. The [docs assistant](#the-docs-assistant) spends from the same credit, at up to about USD 0.07 a question.

## Models

`packages/ai/src/models.ts` defines two tiers:

| Tier | Model | Export | Used for |
|---|---|---|---|
| Balanced | `claude-sonnet-5-5` | `balancedModel` | Tool loops, multi-step work, and judgements a person will act on |
| Fast | `claude-haiku-5-5` | `fastModel` | Translation, short drafts, matching names, summaries |

`resolveModel()` turns a tier name, or an exact model id, into a model. To move to a newer model, change the ids in `MODEL_IDS`, then try every feature in the table below.

`apps/admin/src/lib/content-translation.test.ts` still expects an old model id and fails today. [Local setup](/developers/change-it/local-setup#tests) lists it as a known failure.

| Feature | App | Tier | Code |

| Translating content | admin | Fast | `apps/admin/src/lib/content-translation.server.ts` |

| Recruitment AI | admin | Both | `apps/admin/src/app/(portal)/jobs/[id]/applications/_actions/recruitment-ai.ts` |
| Department audit of Microsoft users | admin | Fast | `apps/admin/src/app/(portal)/_actions/it-remediation.ts`, `packages/ai/src/server/department-resolver.ts` |
| Reading receipts | api | Balanced | `apps/api/src/app/api/expenses/ocr/route.ts` |
| Summarising an expense | api | Fast | `apps/api/src/app/api/expenses/summary/route.ts` |
| Screening job applications | web, api | Balanced | `packages/ai/src/server/recruitment-screener.ts`, called from `packages/shared/recruitment/apply.ts` |
| [Docs assistant](#the-docs-assistant) | docs | Balanced, or fast with `DOCS_ASSISTANT_MODEL=fast` | `apps/docs/app/api/ask/route.ts`, `apps/docs/lib/assistant/` |

Applications sent from the website are screened by the web Site. Applications sent from the app go through `apps/api/src/app/api/recruitment/applications/route.ts` and are screened by the api Site.

Recruitment AI never sends a candidate's name. It sends each candidate as a label, `Candidate 1`, `Candidate 2` and so on, with contact details removed, and puts first names back into the answer afterwards (`recruitment-ai-prompts.ts`, next to `recruitment-ai.ts`).

## The admin assistant

The assistant reads and changes content for the signed-in staff member, within their roles (`packages/ai/src/assistant/authz.ts`). Vacancies are open to it only for HR and global admins. A tool that changes data runs only after the person confirms that exact call on the card the chat shows for it:

- The card is built from the call's real tool name and input, never from text the model wrote, and shows the fields the call will write (`apps/admin/src/app/(portal)/_components/assistant/parts/confirm-action-card.tsx`).
- The server checks the click before the tool runs: the same user, the exact call and its input, and within 10 minutes (`createConfirmationGate` in `packages/ai/src/assistant/tools/confirmation.ts`). A call without a valid confirmation answers `Not run:` with the reason, and changes nothing.
- Every tool with a server `execute` is gated, unless its name is in `READ_ONLY_TOOL_NAMES` (`packages/ai/src/assistant/tools/read-only-tools.ts`). A new tool is gated until you add it there, so add only tools that change nothing.
- The confirmations are signed with keys derived from `APPWRITE_API_KEY`. Without that variable, the assistant answers `503` with `The AI assistant is not configured.`

## The page editor copilot

The copilot is the chat panel in the page editor (**Ask AI**, or **Build me a section**). Its route is `apps/admin/src/app/api/page-editor/ai/chat/route.ts`, its instructions are `buildSystemPrompt` in `packages/editor/src/ai/prompt.ts`, and its eight tools are in `packages/editor/src/ai/tools/index.ts`: `insert_section`, `insert_block`, `set_theme`, `remove_block`, `set_prop`, `bind_collection`, `generate_copy` and `list_blocks`.

- **What it reads.** When the volunteer sends a message, the browser builds the page state with `serializePageForAI` in `packages/editor/src/editor/serialize.ts` and sends it along. It lists the sections and blocks, with every text block's body as HTML. A body over 2,000 characters (`AI_BODY_CHARS`) is cut after the last end tag inside that limit, with a note that `set_prop` replaces the whole body, so the model should ask the volunteer to select the block before it rewrites part of it. The bodies share a budget of 20,000 characters (`AI_BODY_TOTAL_CHARS`), spent in document order. Once a body doesn't fit in what's left, it and every later body that isn't empty show only `(N characters, select the block to read it)`. The selected block's full props come last, with its whole body. The state isn't sent again during an answer, so the model learns about its own changes only from its tools' answers.
- **Where the tools run.** All eight have an `execute` on the server, and that answer is what the model gets. The tools that change the page answer `applied` at once, before the browser has tried the change. Only `set_theme` checks its input on the server (`validateSetTheme` in `packages/editor/src/ai/tools/theme.ts`), so only its refusals reach the model. `generate_copy` returns a placeholder, and `list_blocks` a note pointing back to the page state: the model writes copy itself and reads the page from its instructions.
- **How the page changes.** The browser applies each call as it streams in: `onToolCall` in `packages/editor/src/components/editor-shell/copilot/chat-panel.tsx` calls `applyToolCall`, which changes the editor store. What `applyToolCall` returns never goes back to the model. When it refuses a call, the page stays as it was and the model isn't told. That happens for a block type or section that doesn't exist, a `columnIndex` outside the section, or a path inside a text body such as `body.0.text`. The model may then say it made the change, and the chat shows ✓ for the call, because the ✓ follows the server's answer. The prompt steers the model away from these calls. For example, it says to set a text body whole, with the path `body`.
- **Steps.** The model's turns, its tool calls and the server's answers all run in one request, at most 12 steps (`stopWhen: isStepCount(12)` in the route). The loop ends at the first step with no tool call. The browser never sends a follow-up request by itself.
- **Text bodies.** `set_prop` with the path `body` stores the HTML as the model wrote it, then the form the Rich text field would write (`canonicalBodyHtml` in `packages/editor/src/blocks/text/canonical-body.ts`), under the same undo key, so the volunteer undoes it in one step. The server sanitises the body again when the draft is saved.

## Settings

- **`ANTHROPIC_API_KEY`** on the admin, the api, the website and docs. The owner sets it in the Appwrite console. The AI SDK reads it by itself. Only docs names it: its ask route checks that it's set, to switch the assistant on, and `apps/docs/.env.example` lists it. The other apps' `.env.example` files don't.
- **`OPENAI_API_KEY`** switches job-application screening on. Screening runs only when it's set, and then runs on Anthropic and never sends the key anywhere (`isAutoScreened` in `packages/shared/recruitment/apply.ts`). Any value works.
- **`DOCS_ASSISTANT_MODEL`** and **`DOCS_ASSISTANT_DAILY_LIMIT`** on docs. See [The docs assistant](#the-docs-assistant).

[AI](/developers/keep-it-running/secrets-and-environment#ai) in Secrets and environment lists them all.

## Kill switches

A global admin can turn two AI features off under **Innstillinger** (Settings), then **Funksjonsbrytere** (Feature flags), without a deploy:

| Flag | Default | When off |
|---|---|---|
| `ai_admin_copilot` | On | The assistant is hidden, and its endpoint answers `403` with `The AI assistant is currently disabled.` |
| `expenses_ocr` | On | Receipt reading answers `403` with `Receipt scanning is currently disabled`. Students can still fill in the form by hand. |

Receipt reading is also off whenever the whole reimbursements module (`expenses_module`) is off.

The docs assistant has no flag. Unset `ANTHROPIC_API_KEY` on docs and redeploy to switch it off. The rest of docs keeps working.

## What users see when it fails

- An AI feature in the admin shows an error, and the Site's log shows Anthropic's error, such as `authentication_error` or `rate_limit_error`. The runbook has a table of them.
- Receipt reading fails, and the student fills in the form by hand.
- A job application is saved without an AI score. The log says `AI screening failed for application <id>:`. If `OPENAI_API_KEY` is unset, screening is skipped without a log line.
- The docs assistant says "The assistant couldn't answer right now. Try the search instead." It logs nothing, not even Anthropic's error, so check the key and the account in Anthropic's console.

## The docs assistant

Readers of these docs can ask a question on the landing page, or with **Ask about this page** at the foot of a page's contents. The assistant searches the docs, sends up to six whole pages and the question to Anthropic in one call, and streams back a short answer that cites the pages it used. When the pages don't cover the question, its instructions tell it to say so in one sentence and point to the search. `apps/docs/CLAUDE.md` is the runbook: how it works step by step, the owner's steps before it goes live, and what to check when it fails.

- **What it sends.** Public page text only. Every private detail is replaced with `[private detail, shown only to signed-in staff]` first, whether or not the reader is signed in, and the assistant code never reads the private source.
- **What it keeps.** Nothing. The question, the answer and any error are never logged or stored.
- **What it lists.** Under **Pages used**, the pages the answer cites. An answer that cites none, such as one saying the docs don't cover the question, lists none.
- **Model.** `DOCS_ASSISTANT_MODEL` picks the tier: `balanced` (Sonnet 5.5) when unset or empty, or `fast` (Haiku 5.5). Balanced was chosen over fast because the worst failure is a confident wrong answer.
- **Limits.** 8 questions per visitor per 10 minutes, and `DOCS_ASSISTANT_DAILY_LIMIT` questions a day (default 50). Both counts live in memory in each server process and start again when it restarts or redeploys, so the daily total isn't a spend cap. The hard cap is the monthly spend limit on the docs key's own workspace in the Anthropic Console, which the owner sets before go-live. Visitors are told apart by the first address in `x-forwarded-for`, so the owner must confirm that the proxy in front of docs sets it. Otherwise every visitor shares one count. If the proxy appends to an `x-forwarded-for` the client sent instead of replacing it, a visitor can choose their own key and get round the per-visitor limit. Then only the daily total and the spend limit hold. Questions are capped at 500 characters and request bodies at 4 KB.
- **Off switch.** With no `ANTHROPIC_API_KEY` on docs there is no assistant: the ask field and the page buttons disappear, and the landing field is a search button again.
- **Known gap.** The search dialog has no item for asking. Fumadocs 16.7.10 renders the dialog's footer outside the dialog, and adding one would mean forking it. The landing field and the page button cover asking.

### What a question costs

Each call sends at most 120,000 characters of sources, about 30,000 tokens at roughly 4 characters a token, plus about 500 tokens of instructions and question. Markdown tables, code and Norwegian words can take more tokens per character, so real input can run higher. It gets back at most 1,200 tokens, the model's thinking included. That holds for the `fast` and `balanced` tiers. An older model id in `DOCS_ASSISTANT_MODEL` can use more, because the AI SDK gives it a thinking budget on top of the 1,200.

| Model | Input, about | Output at most | Per question, about | At 50 questions a day |
|---|---|---|---|---|
| Sonnet 5.5 (`balanced`): USD 2 in, USD 10 out, per million tokens | 30,500 × 2 / 1M ≈ USD 0.061 | 1,200 × 10 / 1M = USD 0.012 | USD 0.07 | About USD 3.50 a day |
| Haiku 5.5 (`fast`): USD 0.10 in, USD 0.50 out, per million tokens | 30,500 × 0.10 / 1M ≈ USD 0.003 | 1,200 × 0.50 / 1M = USD 0.0006 | USD 0.004 | About USD 0.20 a day |

Most questions use fewer pages, so they cost less, and a question that finds no page costs nothing. On Sonnet at the caps, the monthly credit of about USD 160 would pay for about 2,200 questions if nothing else used it. One server process that reaches the daily total every day would cost about USD 105 a month. Each restart starts the count again, so restarts or extra processes can spend more. The workspace spend limit stops that. If the spend climbs, lower `DOCS_ASSISTANT_DAILY_LIMIT` or set `DOCS_ASSISTANT_MODEL=fast`.

These are Anthropic's list prices in October 2026, and they change. Check Anthropic's pricing page before you rely on them.

## Test it safely

Anthropic has no test mode, so every call is paid for, whichever key you use.

- **Use your own key for development,** not the production one. Ask the account owner for a separate key, so it can be revoked when your work ends and its spend can be told apart.
- **Point the apps at your own Appwrite project** ([Local setup](/developers/change-it/local-setup#point-the-apps-at-your-own-appwrite-project)). AI features that save their results, such as screening and the assistant's actions, then write only there.
- **Use made-up data,** such as the screenshot seed, never real applicants or receipts. Screening sends the application's text to Anthropic. It first removes emails, links, phone numbers and similar, but `packages/shared/utils/screening-anonymizer.ts` calls that best effort.
- **Run the unit tests.** They use a mock model where they need one, and make no calls to Anthropic:

  ```bash
  cd packages/ai && bun run test
  cd packages/editor && bun run test
  cd apps/docs && bun run test
  ```

- **Check the docs assistant's screens without a real key.** Run docs with `ANTHROPIC_API_KEY=test` and don't submit a question. To see an answer, intercept `/api/ask` in the browser, for example with Playwright's `page.route`, and return a canned answer. `apps/docs/CLAUDE.md` says what the response looks like.

## Leftovers

These look like AI integrations but do nothing, or less than their names suggest. Leave them, or remove them in a clean-up.

- **OpenAI in the apps.** `apps/admin`, `apps/api` and `packages/ai` list `@ai-sdk/openai` as a dependency, but only test mocks in the admin refer to it. `apps/web/CLAUDE.md` still says receipt reading uses OpenAI. It uses Anthropic, in the api.
- **The translation script.** `bun run translate` in `packages/i18n` refuses to start without `OPENAI_API_KEY`, but translates with Anthropic's fast model, so it needs `ANTHROPIC_API_KEY` too.
- **The WordPress import** is the only code that calls OpenAI. `bun run load --apply` in `packages/wp-import` translates with `gpt-5-nano` and needs a real `OPENAI_API_KEY`. See [Events and content sources](/developers/reference/events-and-content-sources#wordpress-and-woocommerce).
- **Pinecone.** `PINECONE_API_KEY` and `PINECONE_INDEX_NAME` are in `turbo.json` and three `.env.example` files, and `packages/ai/src/utils/vector-store.types.ts` describes a vector store, but no code uses Pinecone or any vector store.
- **Unused exports of `@repo/ai`.** No app imports `@repo/ai/config`, `@repo/ai/prompts` or `@repo/ai/utils`, though `packages/ai/README.md` shows the first two. `document-utils.ts` in the last one still reads `NEXTAUTH_URL`.
