Read this before you change anything that reads from or writes to 24SevenOffice, BISO's accounting system, which the code also calls Finago. It's the source of truth for who is a member, and it receives the platform's invoices and ledger postings. So a bug here can invoice a student twice or put wrong numbers in BISO's books. Every call goes to 24SevenOffice's production service, and there's no test company, so read [Test it safely](#test-it-safely) before you run anything.

## Two APIs

The connector in `packages/connectors/src/24sevenoffice/` talks to two separate 24SevenOffice APIs with separate credentials.

| API | Used for | Variables | Sign-in |
|---|---|---|---|
| SOAP | Membership checks, customers, categories, membership invoices, products and departments | `TFSO_APP_ID`, `TFSO_USERNAME`, `TFSO_PASSWORD` | A session token, kept for 23 hours in the `auth_tokens` table of the `24so` database (`auth.ts`) |
| REST | Ledger postings for shop sales, refunds and reimbursements, file uploads, the chart of accounts, and departments | `TFSO_REST_CLIENT_ID`, `TFSO_REST_CLIENT_SECRET`, `TFSO_REST_ORG_ID` | An OAuth token, kept in memory until shortly before it expires (`rest/auth.ts`) |

Both addresses are written into the code: `api.24sevenoffice.com` for SOAP (`client.ts`) and `rest.api.24sevenoffice.com/v1` for REST (`rest/client.ts`). No variable points them anywhere else. Reimbursement postings also need `TFSO_EXPENSE_TRANSACTION_TYPE_NUMBER`, `TFSO_SUPPLIER_DEBT_ACCOUNT`, `TFSO_DEPARTMENT_DIMENSION_TYPE` and `TFSO_CAMPUS_DIMENSION_TYPE`. All of them are listed under [24SevenOffice](/developers/keep-it-running/secrets-and-environment#24sevenoffice) in Secrets and environment. `TFSO_PASSWORD` is an account password with only one value at a time, so read the rotation notes there before you change it.

## Membership checks

**What it does.** A student is a member while they're in a 24SevenOffice customer category that matches a row in `memberships`, between that row's start and end dates. The api looks up the student's categories by student number, with a 3-second limit (`MEMBERSHIP_FINAGO_TIMEOUT_MS`), and keeps the answer for 60 seconds. The website and the app ask the api's `/api/membership`, and never call 24SevenOffice themselves. The admin's member-pass scanner does its own check, with its own 60-second cache (`apps/admin/src/lib/member-pass/membership-lookup.ts`).

**When it fails.** A failed or slow lookup is never cached as "not a member".

- Across the website, the student is shown as a non-member for that page view. The site-wide read gives up after 2 seconds (`apps/web/src/lib/actions/membership.ts`).
- The membership page shows **Vi kan ikke sjekke medlemskapet ditt akkurat nå** (We can't check your membership right now) and offers no plans, so nobody pays twice for the same period.
- The member pass shows **Kan ikke bekrefte akkurat nå** (Can't verify right now).

## Membership purchases

**What it does.** When a membership order is paid ([Payments](/developers/reference/payments#how-a-payment-flows)), the api creates or updates the student's customer in 24SevenOffice, puts them in the plan's category, and posts an invoice. The customer is found by the student's BI `employeeId` ([BI directory](/developers/reference/microsoft#bi-directory)), so a student without one can't buy. A membership order is never also posted as a shop sale. After fulfilment, the api drops the student's cached status, so the new membership shows straight away.

**When it fails.** The buyer has paid, but the membership doesn't show yet. Order reconciliation retries fulfilment on each run ([Scheduled jobs](/developers/keep-it-running/scheduled-jobs#what-it-calls)). If 24SevenOffice may already have the invoice when the error comes, the order is marked `fulfilling` and left alone for a person to check, so nothing is invoiced twice. Look for these in the api's logs:

- `[Membership] Fulfilment attempted for order <id>; leaving marker for manual recovery:`
- `[Membership] Order <id> was invoiced in Finago as <invoice> but recording it failed; reconcile manually.`
- `[Membership] Order <id> has no usable BI identity; manual follow-up required.`

Check the order and the invoice in 24SevenOffice before you change anything by hand.

Membership plans also depend on 24SevenOffice: before each season, next season's products and categories must exist there. See [Membership seasons](/developers/keep-it-running/yearly-calendar#membership-seasons).

## Shop sales and refunds

**What it does.** Each paid shop order is posted to the ledger as one voucher, against the sales type of each product. This only happens while ledger posting is switched on. A global admin or campus admin sets it up in the admin under **Regnskap for nettbutikken** (Shop accounting), at `/shop/accounting`. That page holds the sales types, the voucher settings, the chart of accounts synced from 24SevenOffice, and the **Automatisk bokføring** (Automatic posting) switch, which sets the `shop_ledger_posting` flag. It's off by default, and it refuses to switch on until the settings, the sales types and their accounts are complete. While it's off, paid orders wait, and they're posted once it's on.

**Refunds.** A refund made in the admin reverses the order's posting only if the order was already posted. It then posts a reversal voucher to 24SevenOffice and records it on the refund. Otherwise nothing is reversed automatically:

- **The order wasn't posted yet,** for example because ledger posting was off. After a full refund the order is never posted. After a partial refund, automatic posting won't post the order once posting is on, because the full total would book money that was already given back. The api then logs `[Reconcile Orders] Order <id> needs manual Finago posting: …` on every run. Book the net sale in 24SevenOffice by hand, then put that transaction's id in the order's `finago_transaction_id` column in the Appwrite console, which stops the message. If posting was on when the refund was made, the refund also shows a note on the order's page in the admin.
- **The posting was still in progress, the reversal can't be worked out safely, or the call to 24SevenOffice fails.** An example of the second is an earlier refund on the order that posted no reversal. The refund shows a note on the order's page in the admin. Post the reversal in 24SevenOffice by hand.
- **The order is a membership.** It was booked as an invoice, so its refund needs a credit note made by hand in 24SevenOffice.

In each case the buyer still gets the money back. Only the bookkeeping is left to you.

**When it fails.** Buyers notice nothing. The order stays without a posting:

- If something is missing in the settings, the order is released and posted on a later run, once the settings are fixed. The api logs `[Finago] Order <id> not posted yet: <reason>`.
- If the call to 24SevenOffice fails, the voucher may already exist there. So the order keeps the marker `posting` in `finago_transaction_id`, and nothing posts it again by itself. The api logs `[Finago] Post attempted for order <id>; leaving marker for manual recovery:`.

To recover an order left with the marker, use the script in `packages/api`. It refuses unless 24SevenOffice has no transaction line that mentions the order. It runs as a dry run unless you add `--apply`:

```bash
cd packages/api
bun run finago:reset-stranded-posting -- <order id>
bun run finago:reset-stranded-posting -- <order id> --apply
```

It reads its settings from `apps/admin/.env.local`, so it works on whichever Appwrite project that file names. Check the file first.

## Reimbursements

**What it does.** The feature flag `expenses_ledger_posting` decides how a submitted reimbursement reaches accounting. It's off by default.

- **Off:** the api emails the cover sheet and receipts to the student and to accounting, through Appwrite Messaging. Accounting's inbox is the Appwrite user named in `INVOICE_USER_ID`. See [Messaging and wallets](/developers/reference/messaging-and-wallet#appwrite-messaging-email).
- **On:** the reimbursement goes through an approval chain in Teams and email ([Teams approval bot](/developers/reference/microsoft#teams-approval-bot)). Once approved, scheduled-dispatch's `EXPENSES_POST_PENDING_URL` target posts it to the ledger, with one PDF of the cover sheet and the receipts attached.

**Dates.** Each receipt is booked on its own date, read as a calendar day in Oslo. The transaction has one supplier-debt line per date, all with the same reference and bank account. A receipt with no date, or a date in the future, is booked on the posting day. A receipt in a year that 24SevenOffice has locked moves to the first period of the next open year. The lock flag comes from SOAP `GetFiscalYears`, because the REST `/fiscalperiods` call doesn't have one. If 24SevenOffice rejects a closed month and its message names a date, the posting moves every line in the period holding that date to the next period and tries again, up to 12 times. It never moves a line past the current period. A rejection that names no date fails like any other error. If either lookup fails, the posting goes ahead without it and relies on that retry. Every move, the booking and any failure are written to `expense_events`. Each receipt with an amount gets its final date in `expense_attachments.booked_date`. Receipts without an amount are not posted and get no date. A failed history write is only logged and never changes the result of a posting.

**When it fails.** With the flag off and `INVOICE_USER_ID` unset, every submission fails. With it on, a posting that fails, or one that was interrupted, gets the status `failed` and is never posted again by itself, because 24SevenOffice may already have it. Check in 24SevenOffice before you post it by hand. If 24SevenOffice accepted the posting but saving the `success` status failed, the row is never set to `failed` at once. The api retries the save twice, then logs the transaction id and writes a `booked` event that says the status write failed. The status stays `approved` and `ledger_transaction_id` holds the claim marker `posting` until the 15-minute stale check marks it `failed`, so look at that event before you post it again.

**Retry.** A person can retry a failed booking from the expense's page in the admin, after checking 24SevenOffice. The admin calls `POST /api/expenses/admin/retry-booking` on the api with `CRON_SECRET`, and it runs `retryExpenseBooking` in `expense-posting.ts`. It refuses unless the status is `failed`, refuses when the row holds a real transaction id, and refuses when a `booked` history row exists, because 24SevenOffice already has the posting. Those refusals answer `already_booked`. It never resets the `posting_lock` counter. It takes the next value with an atomic increment, so two overlapping retries can't both post: the one that no longer holds the latest value answers `retry_in_progress`. It then sets the status back to `approved` with the claim marker in `ledger_transaction_id`, so the scheduled run leaves it alone, writes a `booking_retried` event and posts. A crash during the retry is cleaned up by the stale check like any other claim. The route is behind the same `expenses_ledger_posting` flag as scheduled posting and answers `posting_disabled` when it's off.

### Types and AI

**Types.** Each receipt is booked on the account of its expense type. The types live in the `expense_cost_types` table, which a global admin edits in the admin ([Manage expense types](/guide/access-and-settings/expense-types)). While the table is empty, the api uses the starting list in `packages/shared/utils/expense-cost-types.ts` (`STARTING_EXPENSE_COST_TYPES`). While any slug of that list has no row, the admin shows **Last inn {count} manglende starttyper** (`missingStartingCount` from `getExpenseTypesView`). It adds only the missing slugs and never overwrites a row that exists. So a table the old seed route filled keeps `academic` on 7315 and `other` on 7790 until someone changes them on the page. The guide says how. `loadAllCostTypes` returns every type, inactive ones included, so an old slug still resolves. `activeCostTypes` is what the AI and a new submission pick from.

**Eval and re-run check.** The admin's AI tab (`expenses/settings/ai`, global admins only) reads `expense_attachments` rows that have an `ai_cost_type`, newest first, up to 5000, and leaves out those of draft expenses. A receipt counts as kept when `cost_type` still equals `ai_cost_type` and `cost_type_text` is empty. Own texts are grouped by their lowercased, whitespace-collapsed form, and shown from 3 uses within 90 days. The re-run check calls `POST /api/expenses/admin/eval-rerun`, which takes `CRON_SECRET` like the other internal routes and an optional `{ limit }` of 1 to 200 (`AI_RERUN_LIMIT`, the default). It answers 409 `ai_disabled` unless `expenses_module` and `expenses_ocr` are both on, 401 without the secret, and 500 on any other failure. `runRerunCheck` in `expense-eval.ts` reads the latest `expense_type_examples`, classifies each one that has a `final_cost_type` with the active types and `selectExamples`, with the example itself left out, 8 calls at a time. A hit is the same type at `AI_TYPE_CONFIDENCE_THRESHOLD` (0.8) or more. A call that times out or throws counts in `failed`, not in the score. It stops starting new calls after a 120 second budget and answers `stoppedEarly`, and the route has `maxDuration` 300. The result holds `checked`, `considered`, `failed`, `hits`, `hitRate` and up to 50 misses. Nothing is stored. Examples with only an own text have no type and aren't scored. The admin page and its server action set `maxDuration` 300 too.

**Scans.** A scan is stored in `expense_receipt_scans`, keyed by the SHA-256 of the file (`file_hash`). A row holds the extracted fields, the amount in NOK, the AI's type and the model names. It is kept within 8000 characters by cutting the address and the long text fields. A second save of the same hash is ignored, so the first scan of a file stays. The OCR route answers from a stored scan, with no model call, only when that scan is a receipt with a classification and the upload is for `receipt` or `auto`. Otherwise it reads the file again. Submission uses any stored scan. With the AI on, it classifies a stored receipt scan that has no classification (text only) for a receipt with an amount, and doesn't save it again.

**The two AI calls** (`receipt-scan.ts`):

1. `extractReceipt` reads the file with the balanced model and returns the fields: vendor, date, amount, currency, a description, an OCR category and any `receiptIssues`.
2. `classifyReceipt` is a second, text-only call on the fast model. It gets the active types (slug, English name and the admin's note for the AI), up to 10 examples (below) and the extracted fields, and answers with one slug, a confidence from 0 to 1 and a reason. An unknown slug counts as no answer. The OCR route runs it only for documents read as receipts, not bank statements. A failed classification gives no type and never fails the scan.

**Time limits.** The app gives up on an upload after 30 seconds and on a submission after 20. Every classification gets 8 seconds (`CLASSIFY_TIMEOUT_MS`, passed as an `abortSignal`). A stopped one is logged and gives no type, and the scan is stored without a classification, so a submission can classify the receipt later. At submission, reading a file the upload never scanned gets 12 seconds (`EXTRACT_TIMEOUT_MS` in `expense-submission.ts`). A stopped read is logged, and the receipt goes on without a scan. The whole enrichment also has a 14 second budget from its start (`ENRICHMENT_BUDGET_MS`). Once it is spent, no new read, classification or account choice starts: a receipt keeps the scan already stored, and the student's own text gets no AI account and the hint `account_missing`. Calls in flight keep their own caps. The OCR route's read has no limit, and the route loads the active types while the file is read.

A type is applied without the student asking for it only at a confidence of 0.8 or more (`AI_TYPE_CONFIDENCE_THRESHOLD`). The same number decides whether an account the AI chose is marked unsure.

`POST /api/expenses/ocr` runs both calls, stores the scan, looks for a duplicate and returns `costType`, `costTypeConfidence`, `ocrAmount` and `possibleDuplicate` with the fields. `ocrAmount` is the amount in NOK, and null for a foreign amount that couldn't be converted, as at submission. It answers 403 unless both `expenses_module` and `expenses_ocr` are on. The same two flags decide whether submission may scan a file: with the AI off, `enrichSubmission` still reads a stored scan, for the amount and the issues, but ignores its type and makes no new scan.

**What submission decides.** Before a reimbursement is submitted, `enrichSubmission` settles each receipt that has an amount. It reads or makes the scan, so a receipt the OCR route never saw is scanned here, then writes the result on the attachment row (`cost_type`, `account_number`, `tax_code`, `account_source`, `type_source`, the AI's type and confidence, `file_hash`, `ocr_amount`, `receipt_issues`):

- **A client that sends `cost_type_chosen`.** The web form does, for every receipt, including a type the AI filled in, because the student saw and kept it (`attachmentTypeFields` in `receipt-types.ts`). A listed type the student chose stands. Otherwise the student's own words (`cost_type_text`) stand, and the AI picks the account. Otherwise the AI's type is used when it is at 0.8 or more. Otherwise the receipt gets the type `other` and the hint `type_defaulted`. `type_source` is `ai` only when the final type is the AI's and the AI was at 0.8 or more on an active type. Otherwise it is `student`.
- **A legacy client.** App versions 2.2.15 and 2.2.16 send no `cost_type_chosen`. Their choice is only a default, so the AI replaces it when it is at 0.8 or more and names another type, and the reimbursement gets the hint `app_type_replaced`. Its `type_source` is `legacy_app`. A draft's own text is kept as the student's.
- **The account is a snapshot.** The type's account and tax code are copied onto the attachment when the reimbursement is submitted, and posting uses `account_number` first. A change on the admin page doesn't move a reimbursement already submitted. A receipt with the student's own words and no account is never booked on `other`: building the lines throws `Receipt <id> has no account for the student's own type "<text>"`, before anything is sent to 24SevenOffice, so the reimbursement gets the status `failed`.
- **The student's own words.** `chooseAccountForText` gives the fast model the cost accounts (4000 to 7999, from `ledger_accounts`), the existing types and the text, and takes one account number. Below 0.8 the reimbursement gets the hint `ai_account_unsure`. With no usable answer, or with the AI off, it gets `account_missing`.
- **Occasion.** If a receipt's type has `ask_occasion` and the submission has no occasion, the submit route answers 400 with `field: "occasion"` before any account is chosen. The draft is saved before that check, so the 400 also carries the draft's `expenseId`. The web answers it: it asks the student, and pressing submit while the occasion is empty takes the student to the field and shows its error instead of sending. If the api still answers 400 with that field (`submitErrorKind`), the web shows the question again and keeps the `expenseId` (`rejectedDraftId`), so a report that was never saved updates that draft next time instead of making a second one. A legacy client can't answer that, so it gets the hint `occasion_missing` instead. A draft save writes `occasion`, `event_id` and each receipt's `cost_type_text` only when the payload has them (`buildExpenseRowInput`), so a client that never sends them keeps working against a schema without those columns. A key the payload leaves out keeps the stored value on an update. A client clears the occasion or event by sending `null` (an empty string also clears it). `submitter_is_controller` is kept the same way: an update that leaves it out keeps the stored flag, so a controller's own report switched on from the web isn't sent to the controller when the app submits it ([Microsoft](/developers/reference/microsoft#teams-approval-bot)). `eventName` is cut to 100 characters, the column's size, rather than refused.
- **Approver hints.** They are stored as JSON in `expense.approver_hints`, within 4000 characters, with `account_missing`, `ai_account_unsure`, `occasion_missing` and `app_type_replaced` kept first when they don't fit. The codes and their parsers are in `packages/shared/utils/expense-hints.ts`. No screen reads them yet. The others are `amount_differs` (more than 1 NOK from the amount read), `old_receipt` (over 90 days old), `possible_duplicate`, `receipt_issue` and `type_defaulted`. A `possible_duplicate` hint has `match` (`file` or `date_amount`) and either the other reimbursement's `reimbursementNumber` or `sameExpense: 1`.
- **Occasion suggestion.** `POST /api/expenses/summary` writes the general description with the fast model and returns `occasionSuggestion` beside `summary`: the occasion and who it was for, only when the receipts make it evident, otherwise `null`. The request may carry `locale` (`en` or `no`). With `no` the model writes the suggestion in Norwegian (bokmål). Without it, or with any other value, the suggestion is in English, so the app, which sends none, is unchanged. The description itself is always English, for finance. It is one model call, and it is gated by the same two flags as the OCR route. The web sends its locale and fills the occasion field with the suggestion only while the field is visible, empty and untouched (`shouldPrefillOccasion`), cut to the column's 1000 characters (`prefilledOccasion`). Until the student changes the text, the field says it is a suggestion (`occasionFromAi` in the store).
- **History.** `expense_events` gets `submitted`, then `ai_classified` for each receipt typed by the AI at 0.8 or more (`type_source` `ai`, or an app type it replaced) and `ai_account_chosen` for each account it chose, with the confidence and reason.

**The web form.** The student form is a new client. `getExpenseTypeOptions` (`apps/web/src/lib/data/expense-types.ts`) gives it the active types, with only the slug, the two names and `askOccasion`, never accounts or tax codes. Like the api, it counts a type as active unless `active` is `false`. It falls back to the starting list when the table is empty or the read fails, not when every type is inactive. Every row with an amount needs a type, a bank statement uploaded on its own included, because submission books it. A statement attached to a receipt does not (`needsType` in `receipt-types.ts`). Each such receipt has a type picker (`expense-type-combobox.tsx`) in the list and the detail pane. The AI's type is applied at 0.8 or more (`typeFromOcr`), otherwise the receipt needs a choice. A reopened draft keeps own text and active slugs as chosen. A slug that is no longer active asks again, because submission honours only active slugs (`typeFromAttachment`). Pressing submit while a receipt still needs a type takes the student to the first one instead of sending. Receipt-check issues and `possible_duplicate` from the OCR answer show as notices. The description is written again when every receipt has a type and the inputs changed, never over text the student edited (`shouldRegenerate`). The inputs must rest for 800 ms first (`SUMMARY_SETTLE_MS` in `expense-split-view.tsx`), so typing sends one request. Each request is counted as it starts, and only the latest one's answer is applied. The "Was this for {event}?" question comes from the server action `findNearbyDepartmentEvents`, which reads published events of the department that start within 7 days of a receipt date (`EVENT_MATCH_WINDOW_DAYS`), nearest first, at most 3, directly from the `events` table with the session client. `ApiError` (`api-error.ts`) keeps the status and body of a failed api call, so the form can tell a missing occasion from other failures. The app stays an older client until it sends `cost_type_chosen` too.

**Duplicates** (`expense-duplicates.ts`). A receipt is a possible duplicate when another reimbursement that isn't a draft or rejected has an attachment with the same `file_hash`. Otherwise it is one with the same amount (within 0.01) on the same calendar day in Oslo. The OCR route and `enrichSubmission` both ask. The lookup reads `file_hash` and `expense_id` on attachment rows, and only submission writes them, so it finds only reimbursements submitted since this check came in. Within one submission, `computeApproverHints` also flags a receipt that repeats one listed before it, by file or by day and amount. It only warns, in the upload response and as a hint, and never blocks.

**Examples** (`expense-examples.ts`). After a posting succeeds, `writeBookedExamples` in `expense-posting.ts` writes one row to `expense_type_examples` for each posted receipt that has a `file_hash`: the vendor in a normalised form, the description read from the receipt, the AI's type and confidence, the final type or text, the account and who decided it (`student`, or `approver` or `admin` when the account was changed). Examples go into other students' prompts, so the description comes from the stored scan only, never from what the student typed, and is empty without a scan. A receipt with `type_source` `legacy_app` is skipped unless the AI picked the same type at 0.8 or more, because an old app sends its default unasked. With ledger posting off, nothing is posted, so the AI has no examples to learn from. It never stores who submitted, a name or the expense id. A failure is logged and doesn't change the posting. `selectExamples` gives the next classification up to 6 examples for the same vendor, then the newest example of each other type, 10 in all, only for types that are still active. Examples from an approver or admin come before the student's own.

## Roster, plans and departments

These read from 24SevenOffice and write only to Appwrite.

- **The member roster and the plans.** The member-roster-sync function copies the membership products into `memberships` and rebuilds `member_roster` every night. Staff can also run it with **Oppdater nå** (Refresh now) on the admin's members page. [Scheduled jobs](/developers/keep-it-running/scheduled-jobs#member-roster-sync) has the details. When it fails, the page shows **Siste oppdatering feilet** (Last refresh failed), and new plans don't go on sale.
- **Departments.** A global admin presses the sync button on the admin's departments page, which calls `POST /api/units/sync`. It copies 24SevenOffice's departments into `departments`, and picks each one's campus from its department number.
- **The chart of accounts.** The shop accounting page and `POST /api/expenses/ledger-accounts/sync` copy the accounts and VAT codes into `ledger_accounts`.

## Test it safely

There's no safe way to test against 24SevenOffice. Every address in the connector is the production service, no test company is recorded, and nothing marks an order as a test. So:

- **Leave every `TFSO_*` variable unset** in your own project and on your machine. The features above then fail cleanly, with the messages on this page.
- **Never pay for an order with real `TFSO_*` values set,** even in Vipps or Stripe test mode. A test membership becomes a real invoice to a real student, and a test shop order becomes a real ledger posting once posting is on.
- **Reads change nothing in 24SevenOffice,** such as a membership check, the roster sync or a department sync. They still need the production credentials: get them from the account owner for the session, and don't keep them in `.env.local` afterwards. They also write what they read into whichever Appwrite project you point them at. Don't run member-roster-sync from your machine against production ([Scheduled jobs](/developers/keep-it-running/scheduled-jobs#member-roster-sync) says why).

The logic around 24SevenOffice has unit tests that need no network:

```bash
cd packages/connectors && bun run test
cd packages/shared && bun run test
```
