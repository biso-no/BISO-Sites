Read this on your first day with the BISO platform, whether you're a consultant or a new hire. It gives the reading order, the access to ask for, and the first things you can do safely. The platform runs on one production server, and the repo has no staging environment, so be careful with anything that talks to Appwrite.

## Reading order

The sidebar lists the four sections in reading order. Work through them like this:

1. **Start here.** Read this page, then [What BISO runs](/developers/start-here/what-biso-runs) and [Getting access](/developers/start-here/getting-access). The section opens with [If you're hiring someone](/developers/start-here/if-youre-hiring-someone), which is for the BISO board. Skim it to see what they'll give you.
2. **Keep it running.** Deploying, scheduled jobs, secrets, monitoring, backups, what to do when things break, and the yearly calendar. Read the pages on deploying and on when things break before you change anything live.
3. **Change it.** Local setup, code layout, data model, auth and roles, common changes, and the mobile app. Read [Local setup](/developers/change-it/local-setup) before you run an app.
4. **Reference.** The outside services, the shared packages, design decisions, known limitations and history. Look things up when you need them.

Where to go next:

- [Deploying](/developers/keep-it-running/deploying) and [When things break](/developers/keep-it-running/when-things-break), before you touch anything live.
- [Local setup](/developers/change-it/local-setup), before you run an app.
- [Known limitations](/developers/reference/known-limitations), for what is still wrong.

## First safe things to do

### Clone the code and type-check it

You need Bun 1.3.1. npm and pnpm don't work with this repo, because its workspaces and shared `catalog:` versions need Bun.

```bash
git clone https://github.com/biso-no/BISO-Sites.git
cd BISO-Sites
bun install
bun run check-types
```

None of this talks to Appwrite. It worked when Turbo's summary reports every task as successful.

### Read what BISO runs

[What BISO runs](/developers/start-here/what-biso-runs) shows every part of the platform, where it runs, and where its code lives.

### Run the apps against a non-production Appwrite project

<Callout type="warn">
`NEXT_PUBLIC_APPWRITE_ENDPOINT` and `NEXT_PUBLIC_APPWRITE_PROJECT` fall back to production one at a time. If either is unset or empty, that value silently becomes the production one. Only the admin prints a warning. Infisical holds the production values, so don't copy its Appwrite values into a local env file.
</Callout>

The repo has no local Appwrite and no staging project, so make an Appwrite project of your own before you run anything. [Local setup](/developers/change-it/local-setup) has the full steps and the usual first-run failures. In short:

1. Create your own project, push the tables to it and make an API key in it, as steps 1 to 3 of `apps/docs/scripts/screenshots/README.md` describe. Never run `appwrite push` from `packages/api`: its config names the production project.
2. For each app you run, copy `apps/<app>/.env.example` to `apps/<app>/.env.local`, then fill in your project's `NEXT_PUBLIC_APPWRITE_ENDPOINT`, `NEXT_PUBLIC_APPWRITE_PROJECT` and `APPWRITE_API_KEY`. The website needs `APPWRITE_SESSION_COOKIE=a_session_biso_web` and the admin `APPWRITE_SESSION_COOKIE=a_session_biso_admin`. Their templates already hold those values. The admin also needs `NEXT_PUBLIC_BASE_URL=http://localhost:3001`.
3. Start one app from the repo root, for example `bun run dev --filter=admin`. Don't set the values with `export` instead: Turbo drops shell variables that a task doesn't declare, apart from `NEXT_PUBLIC_*` ones.
4. Check that it worked. The admin prints no `Falling back to production Appwrite defaults` line, and `/api/health/ready` on the website, the admin or the API answers `{"status":"ready", …}`.

This gets the apps running. Signing in also needs the sign-in providers set up in your project, such as Microsoft for the admin.

### Look at the known issues

The owner keeps the current issues list outside the repo. The GitHub issue tracker isn't used for this. Ask the owner for the list if you can. These are the issues to know on day one:

- **Admin roles aren't safe yet.** Admin roles can currently be granted in a way that isn't safe. The issue is tracked, the owner plans to fix it, and it must be fixed before anyone relies on admin roles to protect data. [Auth and roles](/developers/change-it/auth-and-roles#known-issues) has the details.
- **Unset Appwrite settings mean production**, as described above.
- **Deploys are manual.** The owner deploys each app by hand in the Appwrite console. Pushing to `main` doesn't deploy the apps, and a GitHub workflow is planned. Only scheduled-dispatch's README says it deploys through the console's Git integration. The other two functions' READMEs don't say how their code reaches Appwrite. Check each function's deployment settings in the console before you push function code. [Deploying](/developers/keep-it-running/deploying#deploy-a-function) has the details.
- **Nothing checks your changes for you.** CI runs no tests, lint or type-check, and the lefthook pre-commit hook is off (every line of `lefthook.yml` is commented out). Run `bun run check-types` yourself before you deploy, and lint the files you changed with `bun x ultracite check <paths>`. The repo-wide `bun run check` currently reports about 150 errors that were already there.
