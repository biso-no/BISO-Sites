# @repo/i18n

`@repo/i18n` is the shared i18n surface for the two Next.js user-facing
apps. It pins the supported locales, exposes a type guard, and ships
the message bundles. Both `apps/web` and `apps/admin` wire it into
`next-intl` and share the same translation files, which keeps user-facing
copy consistent across the public site and the CMS.

## Entrypoints

| Entrypoint           | Purpose                                                       |
|----------------------|---------------------------------------------------------------|
| `@repo/i18n`         | Same as `./config` — re-exports constants and helpers         |
| `@repo/i18n/config`  | `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, locale detection       |
| `@repo/i18n/types`   | `Locale` type, `isLocale()` guard                             |
| `@repo/i18n/messages`| `loadMessages(locale)` — dynamic message loader               |

## Locales

```ts
import { SUPPORTED_LOCALES, DEFAULT_LOCALE } from "@repo/i18n/config";

SUPPORTED_LOCALES; // ["no", "en"] as const
DEFAULT_LOCALE;    // "no"
```

Norwegian (`"no"`) is the primary locale. English (`"en"`) is a
secondary translation generated largely by the translation tooling
described below.

### Type guard

```ts
import { isLocale } from "@repo/i18n/types";

if (!isLocale(maybeLocale)) {
  notFound();
}
```

Use `isLocale()` to validate route parameters or cookie values before
narrowing them to the `Locale` type.

## Loading messages

```ts
import { loadMessages } from "@repo/i18n/messages";

const messages = await loadMessages("no");
```

`loadMessages()` returns the merged set of namespaces for a locale.
Internally it dynamically imports each JSON file under
`packages/i18n/messages/<locale>/<namespace>.json` so namespaces stay
code-splittable.

In an app, this is plugged into `next-intl`'s request config:

```ts
// apps/web/src/i18n/request.ts
import { getRequestConfig } from "next-intl/server";
import { loadMessages } from "@repo/i18n/messages";

export default getRequestConfig(async ({ requestLocale }) => {
  const locale = (await requestLocale) ?? "no";
  return { locale, messages: await loadMessages(locale) };
});
```

## Message file layout

```
packages/i18n/messages/
├── no/
│   ├── common.json
│   ├── auth.json
│   ├── events.json
│   └── … (43 namespaces total)
└── en/
    ├── common.json
    ├── auth.json
    ├── events.json
    └── …
```

Each namespace is a flat key-value JSON file. **There is no
nested-object structure** — keys use dots in the file but values are
plain strings. Pick the keys to match where the copy is used so it's
easy to find:

```json
{
  "page.hero.title": "Velkommen til BISO",
  "page.hero.cta": "Bli medlem"
}
```

## Translation tooling

```bash
bun run translate
```

The root script translates any missing English keys from their
Norwegian counterparts using OpenAI through
[`@parvineyvazov/json-translator`](https://github.com/parvineyvazov/json-translator).
The translator walks each namespace, diffs Norwegian against English,
and asks the model to fill in the gaps while preserving placeholders
(`{name}`, `{count, plural, …}`).

> Note: English copy is therefore *AI-generated by default* for any
> newly added key. For high-visibility surfaces (header, footer,
> marketing copy on the home page), have a bilingual reviewer pass
> over the result before shipping.

### Conventions

- **Norwegian is the source of truth.** Always add keys to the
  `no/<namespace>.json` first, then run `bun run translate`.
- **Don't translate placeholders.** Wrap dynamic values in
  `{variable}` syntax — both `next-intl` and the translator preserve
  them verbatim.
- **Pluralization** uses ICU MessageFormat (handled by `next-intl`).
- **Keep keys flat.** Nested object keys are harder to grep and
  harder to translate consistently.

## Consumers

| App           | How it uses the package                                            |
|---------------|--------------------------------------------------------------------|
| `apps/web`    | Wires `loadMessages` into `next-intl` request config; reads via `useTranslations()` and `getTranslations()` |
| `apps/admin`  | Same pattern; the editor reads block-level copy from the `editor` and `blocks` namespaces |
| `apps/api`    | Does not consume; the JWT REST service is locale-agnostic           |
| `apps/docs`   | Does not consume; docs are English-only                             |
