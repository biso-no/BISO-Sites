# Managed production readiness

This page is the handover-oriented production readiness roadmap. It treats
"managed" as **admin-configurable and operationally sustainable without a
developer**, while keeping secrets, payment settlement truth, Appwrite schema
changes, and vendor credentials outside the admin UI.

The immediate deliverable is this audit and roadmap. It does **not** introduce
runtime API changes, schema changes, or new dependencies.

## Evidence checked

- Repository layout and application ownership in `README.md`.
- Existing production findings in `PRODUCTION_CHECKLIST.md`.
- Admin app scope, route structure, settings, roles, audit log, and feature flag
  code under `apps/admin`.
- Public web and API risk areas, especially checkout, cron, and API admin auth.
- Appwrite schema in `packages/api/appwrite.config.json`, including
  `feature_flags`, `audit_logs`, `notifications`, and content tables.
- Operations, architecture, admin handbook, and handover docs under
  `apps/docs/content/docs`.

## Priority roadmap

### P0 before production

These items protect launch safety. They should be closed or explicitly accepted
before production cutover.

| Ticket | Acceptance criteria |
|---|---|
| Add deploy-blocking quality gates | Production deploy workflow runs app lint plus app/dependency type-checks before upload, or a documented equivalent gate exists. `apps/web` and `apps/api` `ignoreBuildErrors` risk is either removed or explicitly compensated by CI. **Initial gate is implemented; watch the first production run.** |
| Resolve admin-auth policy conflict | API label-based global-admin gating is removed. Admin and API agree that global admin comes from National + Operations Unit team membership. **Initial code path is resolved; verify real production admins have the required teams before cutover.** |
| Verify staging behavior fixes | Checklist in `PRODUCTION_CHECKLIST.md` is executed with dates/results: Vipps order page, reservation stock math, purchase limits, legacy campus-admin team names, and cron/sync authentication. |
| Confirm cron and secrets | `CRON_SECRET`, `ENTUR_SYNC_SECRET`, and `TICKSTER_SYNC_SECRET` are set in production and schedulers send them in headers, not query strings. The scheduler, cadence, owner, and login location are documented. **Initial auth hardening is implemented for `departures/sync` and `cleanup-anon-users`; production scheduler config still needs verification.** |
| Close or accept recruitment permission follow-ups | **Implemented:** restricted recruitment tables are stamped with per-row staff permissions and table grants are narrowed to Operations Unit + HR create-only, with no direct user-create path and no literal `admin` team dependency. Staging must still verify required teams and backfill any pre-existing recruitment rows before legacy table grants are removed. |
| Add first auth regression tests | Initial coverage now includes shared team-role helpers, API `getAdminScope`, admin team parsing/nav pseudo-role gating, recruitment scope helpers, recruitment schema permissions, row-stamping paths, representative admin content update scoping, and checkout `vipps-order-ops.ts` coverage for item-shape normalization, legacy `productId` parsing, and stock/reservation state transitions. Add more route-gating and payment/checkout route tests as those areas change. |

### P1 before handover

These items make the platform manageable by administrators after the original
developer leaves.

| Ticket | Acceptance criteria |
|---|---|
| Split personal preferences from platform settings | **Implemented:** Settings is framed as personal preferences (locale, timezone, notifications) with a Platform section that links global admins to the two operational surfaces. Global operational config lives in those audited, typed, global-admin-only screens — Feature flags (typed validation in `feature-flags-model.ts`, defaults, `feature_flag.*` audit events) and Operations health (read-only status). A speculative global-settings table was intentionally not added; feature flags are the concrete audited global setting. |
| Build feature flag management | **Implemented:** global admins manage `feature_flags` at `/feature-flags` in the admin app — list, toggle on/off, and create flags. Writes are global-admin gated, key/title validated (`feature-flags-model.ts`, unit-tested), and audited (`feature_flag.toggle` / `feature_flag.create`). Rollback is toggling the flag off. Rollout policy/ownership conventions remain a documentation follow-up. |
| Add integration health/status surface | **Implemented:** `/operations` (global admin) shows read-only config status for Appwrite, Microsoft 365, SharePoint, Vipps, and scheduler secrets — presence only, never values — each linking to its runbook, plus the live required-team health report. Logic is unit-tested in `apps/admin/src/lib/integration-health.ts`. Per-app `/api/health` liveness is documented in operations/monitoring-and-health. |
| Add role/team health checks | **Implemented (endpoint + tested core):** global admins and monitors can `GET /api/health/teams` in the admin app to verify the required teams exist — `biso-members`, `sg-app-campus-national`, `sg-app-dept-operationsunit`, `sg-app-dept-hr`, plus a campus + `Ledelsen{City}` leadership pair per city. It returns `503` listing each missing team and its operational fix; the canonical registry and check logic live in `apps/admin/src/lib/team-health.ts` and are unit-tested. A friendly in-portal screen consuming the same core remains a follow-up. |
| Complete handover fill-ins | Ownership, third-party accounts, domains/hosting, scheduler configuration, alert recipients, and renewal/billing details have no `[FILL IN]` placeholders for production-critical vendors. |
| Add admin runbooks | Runbooks exist for failed payment checkout, stale reservations, failed cron, broken SharePoint documents, recruitment data access, failed announcement dispatch, and emergency access recovery. |

### P2 after launch

These items improve long-term maintainability but should not block a safe launch
unless one becomes directly tied to a production incident.

| Ticket | Acceptance criteria |
|---|---|
| Remove or activate dormant integrations | Anthropic, WooCommerce, chat tables, large-event tables, analytics stubs, and unused feature scaffolds are either removed or documented as active with real owners. **Stripe is now activated** — Phase C added the checkout/webhook backend and managed credentials; it stays behind the `payments_stripe` flag (OFF) until the staging E2E in `docs/plans/payments-phase-c.md` passes. |
| Decide search and analytics | Leadership chooses whether public-site search and analytics are needed. If yes, add a product and privacy decision before implementation. |
| Simplify admin studio editors | Deduplicate shared editor components in small, tested passes. Protect current autosave, translation, upload, and publish behavior before refactoring. |
| Improve observability | Resolve docs conflict on Sentry status, add error-tracking/APM if not actually wired, and centralize alert ownership outside a single person. |
| Normalize action result shapes | New actions follow the canonical result shape; old actions are migrated opportunistically when touched for feature work. |

## Future interface policy

- Prefer existing Appwrite tables where they already exist:
  `feature_flags`, `audit_logs`, content tables, translation tables, and
  notification tables.
- New operational settings should be global-admin-only server actions with
  typed input/output models, explicit defaults, validation, revalidation, and
  `audit_logs` entries.
- Campus and department users should manage scoped content, not platform-wide
  controls.
- Do not expose secrets, vendor credentials, Appwrite schema migrations, or
  payment settlement controls as editable admin settings.
- Read-only operational status is safe to expose when it avoids leaking secret
  values and has clear runbook links.

## Verification model for each implementation ticket

Before coding a managed-control ticket, define these acceptance checks:

1. **Auth scope:** who can view and who can write.
2. **Validation:** accepted values, defaults, and rejection behavior.
3. **Audit event:** action name, resource type, resource ID, and safe payload.
4. **Rollback:** how an admin restores the previous value or disables the
   feature.
5. **Docs:** admin handbook and handover/runbook pages updated.
6. **Staging test:** exact path, account role, and expected result.

Production-readiness verification should include the relevant subset of:

```bash
bun run check-types
bun x ultracite check
bun run build:web
bun run build:admin
bun run build:api
```

Focused tests should be added around auth, checkout/payment, admin scoping, and
the managed-control model as those areas change.
