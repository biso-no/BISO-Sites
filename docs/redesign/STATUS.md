Completed: RD-033. **All 34 packages are done.** Full comparison in `03-results.md`.
In progress: none
Blocked: none
Deviations from plan: two, both about method.
  - **The recorded baseline could not be compared against.** `baseline/README.md` warned that RD-001's vitals were captured under `node`, where every Appwrite read fails silently, so those pages rendered empty. Comparing today's populated pages against blank ones would have manufactured regressions everywhere. Since `HEAD` is still `c82f70d3` and the whole redesign is uncommitted, I rebuilt the pre-redesign app in a **detached worktree at `HEAD`** and re-measured it under `bun`, on the same machine, in the same session, with both servers running at once. **The rebuild reproduces `bundle.md` byte for byte** — 3.3 MB static, 89 JS files, 2,555.7 KB JS, 332.8 KB CSS — which is what makes it a trustworthy stand-in.
  - **FINDING-D was understated and its remedy was not enough.** It says desktop LCP is bimodal and mobile is stable, so take a median of 3 desktop runs. Mobile is bimodal too. A median-of-3 pass reported `/shop` mobile LCP at +107%, and a single re-run immediately returned 1,420 ms against that median's 3,048. LCP is therefore reported from a **paired sampler at n = 7** that alternates new/old/new/old so machine drift lands on both arms equally; every individual sample is printed in `03-results.md`. Committed as `baseline/paired-lcp.js`.
Headline numbers (baseline re-measured under `bun`, n = 7 paired):

Checked across eight routes including both 404 shapes: one `<main>`, one `<h1>`, correct `<html lang>` on every one.
  - **FINDING-E is confirmed pre-existing, and is now proven unfixable from page code.** Seven not-found URLs answer HTTP 200 on **both** builds — fourteen checks, fourteen 200s, every one carrying `x-nextjs-postponed: 1`. Four throwaway probe routes were built, served and removed to settle it: a bare `notFound()` as a page's first statement → 200; `await connection()` (the `cacheComponents` prerender opt-out) then `notFound()` → 200; `prefetch = "force-disabled"` → 200; a route handler returning a 404 Response → **404**. Two more never built at all: `dynamic = "force-dynamic"` and `revalidate = 0` are both rejected outright by `cacheComponents`. It is not about *when* `notFound()` runs, nor about PPR shells — `/campus/[slug]` is classified `ƒ` Dynamic and still answers postponed. **Under `cacheComponents`, no page in this app can set a 404; only route handlers can.** The config levers are no better: `partialPrefetching: false` alone changes nothing, and `cacheComponents: false` does not build — it fails first on `partialPrefetching requires cacheComponents`, then on **22 route files** using the `instant` segment config, behind which sit **13 files using `"use cache"`**, two of them in `packages/`. So this is an architectural migration, not a patch. RD-034's two aliases were fixable only because a fixed path can become a route handler; a 404 that depends on a database lookup cannot. Users see the correct not-found UI; crawlers see a 200. **Recommend carrying it as a known issue.**

**Following that gate to the document turned up the biggest performance item left in `apps/web`, and it is pre-existing.** `NextIntlClientProvider` serialises the **entire** message bundle into every page, and it lands **twice** — once in the SSR HTML, once in the RSC flight payload. It is also the mechanism behind baseline FINDING-E: grepping page HTML for a translated string always matches, because every string is in every page. **The fix — give the provider only the namespaces a page's client components read — is out of scope here and needs nothing from this redesign.**
**A second, separate defect found while isolating that:** on `/shop?category=clothing` the `<h1>` sits at byte **491,514 of 500,227**, 98% through the document behind 455 KB of inline script, where `/contact` and `/press` put theirs at byte 17,173 behind 756 bytes. ## 2026-09-01 — RD-031: accessibility sweep
Completed: RD-031
In progress: none
Blocked: none. RD-032 (locale) is next.
**Method first, because every number below depends on it.** A browser harness runs on every route: axe-core 4.10.2 injected into the page (fetched to the scratchpad — an audit tool, not a repo dependency) across `wcag2a/aa`, `wcag21a/aa`, `wcag22aa` and `best-practice`; a Tab walk that records whether each focused element has a real ring or outline in its *computed* style; `document.getAnimations()` under emulated `prefers-reduced-motion: reduce`; and heading level, `<h1>` and landmark counts. Contrast is axe's `color-contrast`, computed against the composited background rather than the declared one — which is how the two contrast bugs below were found at all.
**The first pass covered 17 routes and came back nearly clean. Widening it to 42 found five more defects, three of them critical.** That gap is the finding: an accessibility audit is only as good as its route list.
The nine defects, all pre-existing:
  - **The sun marker failed contrast at 1.49:1.** `bg-marker` was the heading span's own `background-image`, so the text's computed background *was* the marker yellow and axe scored white-on-`#fecd45` wherever a section heading sat on a deep band. It is a `::after` bar now — same 3px stroke, same position, `z-index: -10` — and the span's background is transparent. Verified in-browser: `::after` still paints `rgb(254, 205, 69)` at 3px.

## 2026-09-01 — Membership accrual: three defects in the invoice path
Approved and fixed after RD-024, in `packages/shared`, `apps/api` and `apps/web`. All three sat between the `memberships` catalogue and the 24SevenOffice invoice, and all three were invisible because every test fixture used ISO dates while the live rows do not.

**The rule, as stated by BISO:** a membership accrues from the half-year boundary containing the **purchase** — bought in the summer half it accrues from **1 July**, in the spring half from **1 January**.

  1. **The 350 kr Semester plan could not be bought.** `deriveAccrualMonths` parsed dates with `new Date()`, which does not understand the `DD.MM.YYYY` that `syncMembershipsFrom24SO` writes. Semester's expiry `31.12.2026` came back as an **Invalid Date**, so `toMembershipPlan` returned null and the plan was dropped from the catalogue — `/membership/join` offered only 1 Year and 3 Years while the marketing page advertised the semester price. The other two survived **by accident**: `01.07.20XX` was misread as *January 7* on both sides, so the month difference was still right; any day past the 12th was not so lucky. Dates are now parsed explicitly, in UTC, accepting both `DD.MM.YYYY` and ISO, and rejecting impossible ones (`31.02.2026`).
  2. **Every invoice booked the same accrual date regardless of when it was bought.** `AccrualDate` was `plan.startDate` — the catalogue row's own fixed value — so a membership bought in March 2027 still booked accrual from `01.07.2026`. It is now derived from the purchase: `membershipAccrualStart()` returns the 1 January or 1 July boundary containing it.
  3. **That date was sent in the wrong format.** The 24SO API documents `Accrual.startDate` as an ISO `date` (`2023-06-01`); the live rows hold `01.07.2026`, and it was passed through verbatim. The existing invoice test never caught it because its fixture plan used `2026-08-01`. The accrual start is now always ISO by construction.

**Where the value is computed, and why.** Checkout snapshots the accrual start onto the order item (`membership-checkout/route.ts`) rather than fulfilment deriving it. Fulfilment can lag payment — a webhook retry, the reconcile cron — and a purchase made on 30 June must not book into July because it was fulfilled the next day. The invoice builder prefers that snapshot and recognises it by it being **its own accrual start** (`membershipAccrualStart` is idempotent), so an order placed before this change, carrying the catalogue's `01.07.2026`, fails the check and falls back to deriving from the invoice date rather than reaching 24SO in a format it does not document. The boundary is read in **UTC**, so the accounting period does not depend on the timezone of whichever host fulfils the order.
